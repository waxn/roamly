# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Collaboration

**When in doubt, ask.** If there is any ambiguity about what is wanted — scope, approach, which file to edit, whether a change is intentional — ask before proceeding. Never make a judgment call silently when a quick question would resolve it.

## Versioning

This project uses [Semantic Versioning](https://semver.org/) via git tags (`v1.2.3`). The tag triggers Docker Hub publish in CI.

| Change type | Version bump | Example |
|---|---|---|
| Bug fix, security patch, copy/style tweak | patch (`1.2.x`) | `v1.2.4` |
| New feature, new model/field, new endpoint | minor (`1.x.0`) | `v1.3.0` |
| Breaking change to backup format, API contract, or non-rollback migration | major (`x.0.0`) | `v2.0.0` |

After finishing a set of changes: `git tag v1.2.3 && git push origin v1.2.3`

The backup JSON format version (in `backup_tasks.py`) must also be bumped whenever the backup schema changes.

## Commits

**Every individual fix or change gets its own commit — no batching.** Commit messages must be **properly capitalized** — capital letter after the `type(scope):` prefix (e.g. `fix(ai): Correct displayed URL`). Each commit must be signed:

```
Co-Authored-By: Claude <model> <noreply@anthropic.com>
```

Use the model that actually wrote the commit (e.g. `Claude Opus 4.8`), not a fixed name.

Also update this CLAUDE.md whenever something architectural or behavioural is added or changed.

## Running the app

Everything runs inside Docker. Never run `python manage.py` directly on the host. Do not attempt to run `docker compose` or `sudo docker compose` commands — these require a password and an interactive terminal. Tell the user to run these themselves.

```bash
# Start (builds if needed)
sudo docker compose up -d --build

# Restart without rebuild (picks up template/static changes immediately)
sudo docker compose restart web

# View logs
sudo docker compose logs web --tail=50

# Django shell
sudo docker compose exec web python manage.py shell
```

**`migrate` runs automatically on every container start** — the `web` service's `command:` in `docker-compose.yml` is `migrate --noinput && collectstatic --noinput && gunicorn ...`, so `up -d --build` (or even a plain `restart web`) already applies any pending migration. There is no separate manual migrate step in the normal workflow.

**`makemigrations` is never a deploy-time step either.** Migration files are written (by hand or via `makemigrations`) at *development* time and committed straight to git alongside the model change — `tracker/migrations/` is volume-mounted (along with `staticfiles/` and `media/`), so a rebuild already has the file; there's nothing left to generate on the deployed container. Only run `makemigrations` yourself if you've hand-edited a model with no migration file for it yet, which shouldn't happen in the normal flow.

**Templates are not volume-mounted** — a template edit needs `up -d --build` to reach the container. Python file changes need at least a `restart web`; a new model/migration needs `up -d --build` so the fresh migration file and any new dependency are both picked up.

## Architecture

Single Django app (`tracker/`) inside the `roamly` project. No separate services — background work (geocoding, backups, POI download) runs in Python threads launched from views.

**Geocoding is local, never on the push path.** `push_location` (`/api/push/`) creates points with `city=''` and returns immediately; labelling happens in a background thread. Reverse geocoding lives in `tracker/offline_geocode.py`:

- **`local_reverse_geocode(lat, lon)`** — for US points, does **point-in-polygon** against the `Boundary` table (PostGIS `MultiPolygonField`, GiST-indexed): incorporated places / CDPs first (`kind='place'`), then county subdivisions (`kind='cousub'`), so a point resolves to the town that *contains* it, not nearest centroid.
- **`offline_reverse_geocode(coords)`** — international / no-US-match fallback: nearest city from the bundled-GeoNames `reverse_geocode` package (numpy/scipy), no network.

Boundaries are loaded by **`import_boundaries`** (`tracker/management/commands/`): downloads US Census TIGER shapefiles (`cb_<year>_<fips>_{place,cousub}_500k.zip`) per state, transforms to 4326, `bulk_create`s into `Boundary`. `--states ME,VA` limits states; `--regeocode` relabels all stored locations (caches one lookup per ~111m cell).

`geocoding_tasks._geocode_worker` drains the `city=''` backlog in chunks (one UPDATE per place), busting user cache after each chunk. Kicked fire-and-forget from `push_location` via `ensure_auto_geocode(user_id)` (debounced, no-op while a thread already runs), and on demand from Settings. **Adding `reverse-geocode` dep + migration + boundary import requires `docker compose up -d --build`** (the new dependency needs the image rebuilt; the migration applies automatically as part of that — see "Running the app") **then a manual `import_boundaries --regeocode`**, since boundary import is a one-off data load, not something a migration can do on its own.

**Database:** SQLite (dev); PostgreSQL + PostGIS when `DATABASE_URL` is set. Code checks `HAS_POSTGIS` at runtime and falls back gracefully.

**Caching:** Redis when `REDIS_URL` is set, in-memory otherwise. `_bust_user_cache()` increments `cache_gen:{user_id}`, invalidating all cached API responses for that user.

**Stats snapshots.** Stats / Visits / Places aggregate entire history — too slow live, and `_bust_user_cache` fires constantly from pushes. Served from a **per-user `StatsSnapshot`** row (migration `0029`) holding precomputed JSON (`stats_json`, `visits_json`, `yearly_json`, `places_json`, `transport_json`) + `status`/`computed_at`. The snapshot is **decoupled from `cache_gen`** — refreshes nightly, not per push. `tracker/stats_tasks.py` starts a daemon thread from `apps.ready()` (`start_stats_scheduler`) that sweeps every ~15 min and recomputes users whose `computed_at` is before today's local date. The thread runs in every gunicorn worker; `compute_snapshot` uses a **PostgreSQL session advisory lock** (`pg_try_advisory_lock`, namespace `_LOCK_NAMESPACE`; SQLite falls back to atomic `status='running'`) so only one heavy recompute runs per user across all workers — Postgres auto-releases on process death, so a killed compute never wedges. Shared helpers (`_compute_overview_from_qs`, `_compute_distance_from_qs`, `_compute_visits_from_qs`, `_compute_yearly_payload`, `_compute_places_payload`, `_compute_transport_breakdown_from_qs`) are called by both the snapshot worker and live views. `visits_api`/`stats_api`/`yearly_overview_api`/`distance_api`/`places_api`/`transport_breakdown_api` serve the snapshot for default all-time unfiltered requests (via `_get_snapshot_or_kick`) and compute live for device/date-range filters. `CustomPlace` mutations call `_refresh_places_snapshot` for immediate updates. On-demand recompute: `POST /api/stats/recompute/` + `GET /api/stats/recompute/status/`, surfaced in Stats/Visits/Places headers and Settings → Background Jobs. **New model ⇒ build + migrate.**

**Stats "Daily Distance" heatmap.** A GitHub-contributions-style grid on `stats.html` — one square per day for the trailing year (53 Mon-first week columns), shaded by gated distance travelled; hover for the day + distance, click through to `/map/?start=&end=`. Purely client-side: it fetches `/api/distance/?all=1&granularity=daily` (**the one distance request `distance_api` serves straight from the snapshot**) and slices the last year in the browser, so it costs one extra snapshot read and no new endpoint. It is **deliberately independent of the page's range filter** — always the last year, regardless of the toolbar. Shading buckets by **quartile of the non-zero days**, not linearly: daily distance is heavily skewed (a year of commutes plus a few travel days), so a linear ramp would flatten nearly every day into the lowest level. Respects `roamly_speed_unit`. Pure template change — no rebuild/migration.

**Stats deep-links.** Unlike `map.html`, `stats.html` didn't read its own URL on load — the toolbar range picker (`#stats-range`/`#stats-start`/`#stats-end`, read by `getFilterParams()`) only ever reflected in-page clicks. An IIFE before the initial `loadStats()` call now reads `?start=YYYY-MM-DD&end=YYYY-MM-DD` (mirroring `map-core.js`'s `?start=&end=` handling) and seeds the date inputs + flips the range select to "All time" before the first fetch, so a link like `/stats/?start=...&end=...` (e.g. from a summary email) opens pre-filtered. Pure template change — no rebuild/migration.

**Admin accounts:** `UserProfile.is_admin` marks an instance admin (distinct from `is_staff`/`is_superuser`). Migration `0028` backfills `is_admin=True` for pre-existing accounts. New admins register via the signup form's `<details>` section using `ADMIN_SIGNUP_KEY` (validated in `SignUpForm.clean_admin_key`; section only shows when env key is set). Exposed to templates as `IS_ADMIN` by `tracker.context_processors.custom_js_snippet`.

**Admin panel** (`/admin-panel/`, `admin_panel_view` → `admin_panel.html`, admin-only): nine client-side tabs — **Monitoring**, **Access Log**, **Events**, **Retention** (all logging, below), **Users** (list every account; toggle `is_admin`; delete another user and all their data), **Custom JS** (edit the instance snippet), **Contact** (contact address), **CAPTCHA** (Turnstile config, below), **Downloads** (road/subway/POI data — below). User endpoints: `GET /api/admin/users/`, `POST /api/admin/users/<id>/toggle-admin/`, `POST /api/admin/users/<id>/delete/`. All guarded by `_require_admin`. Tabs support deep-linking via a URL hash matching the tab name (e.g. `/admin-panel/#downloads`) — read once on page load, since nothing else in this file uses `location.hash` for routing.

**Downloads (Admin Panel → Downloads).** Road, subway and POI data (`RoadSegment`, `RailSegment`/`RailStation`, `POI`) are instance-wide reference tables with no user FK, but the three background jobs that populate them (`RoadDownloadJob`, `RailDownloadJob`, `POIDownloadJob`) used to be per-user (`OneToOneField(User)`), triggered from each person's own Settings → Background Jobs, with the download AREA scoped to *that user's own* device history. That was architecturally backwards once the data itself is shared — two users on the same instance could each run their own download, racing to populate one table neither of them owns alone. All three are now **admin-only, instance-wide singletons** (`pk=1`, `SiteConfig`-style — migration `0067`, which also deletes any pre-existing per-user rows since job *status* has no value worth carrying across the shape change), and the download area for each now covers **every user's combined travel history**, not just one person's:

- `road_download_tasks._visited_boxes()` (shared verbatim by `rail_download_tasks.py`, per its own docs) scans `Device.objects.all()` instead of `Device.objects.filter(user_id=user_id)`.
- `poi_tasks.py`'s city list comes from `Location.objects.exclude(city='')` across every device, not one user's.
- Each module's `_running_thread` is a single module-level variable (was a `{user_id: Thread}` dict) — there is now only ever one run to track per job type, instance-wide.
- Every API endpoint (`road_download_api`/`_status_api`/`_stop_api`, `road_data_delete_api`, the `subway_*` and `poi_*` equivalents) gained `err = _require_admin(request); if err: return err` as its first check. URL paths are unchanged (`/api/roads/download/` etc., not moved under `/api/admin/...`) — only the view-level gating changed, to keep the URL churn to zero.
- **New:** `POST /api/poi/delete/` (`poi_delete_api`) — POI never had a delete endpoint before this; added for parity with road/subway's existing `TRUNCATE`-based delete. `POIDownloadJob` also gained `worker_token` and `failed` fields it didn't have before (migration `0067`), bringing it up to the same cross-process-ownership and failure-reporting standard road/subway already had — it previously only had a bare 60-second staleness check with no token-based ownership at all, and no way to surface a partial-failure count.
- `rail_download_tasks._download_boxes` gained the same `HTTPError`-vs-everything-else split and `unreachable` return value `road_download_tasks._download_boxes` has (see Road snapping below) — it forked its own retry loop originally rather than reusing the road version's, so it had not received that fix.
- Settings → Background Jobs keeps **Reverse Geocoding**, **Match POIs to Points**, **Detect Transport Modes** and **Recalculate Stats** (all genuinely per-user, operating on that user's own points) — only the three download cards moved out, replaced with a note pointing non-admins at "ask your instance admin" and admins at a link to `/admin-panel/#downloads`.

**Auto-download new regions** (migration `0068`). All three downloads are now also **incremental and automatic**, not just admin-triggered. `DownloadedRegion` (`kind` = `road`/`subway`/`poi`, `key` = a `"gy,gx"` grid-cell coordinate for road/subway or `"city|state"` for POI) records what's already been fetched from Overpass, so any run — manual button or automatic — only asks about growth since last time:

- `road_download_tasks._visited_cells()` (the raw cell-set scan, unchanged) feeds `_visited_boxes(kind, beat=None)`, which now diffs against `DownloadedRegion.objects.filter(kind=kind)` before merging into query boxes, and returns `(boxes, box_cells)` — the cell keys behind each box, so the caller can mark them covered once that box's batch actually succeeds. `rail_download_tasks` calls the same function with `kind='subway'` (road and subway are tracked independently despite sharing the cell grid, since a cell can have one without the other). A batch's cells are marked covered via `_mark_covered(kind, keys)` **only when that batch's `failed_boxes == 0`** — a partial failure leaves its cells uncovered so the next run retries them, rather than silently skipping a corridor forever because it happened to share a batch with a cell that failed. `_visited_cells()` itself is cached 10 minutes (`road_download:visited_cells`) since road and subway both call it with an identical result — without this, an auto-download sweep (which checks both kinds) or an admin clicking both buttons paid for the full per-device location scan twice in a row for the same answer.
- `poi_tasks.py` filters its per-city list against `DownloadedRegion(kind='poi')` before downloading, and `get_or_create`s a `(city, state)` row after each city Overpass genuinely answered for (even with zero results) — an unreachable city stays unmarked and is retried.
- All three delete endpoints (`road_data_delete_api`/`subway_data_delete_api`/`poi_delete_api`) now also clear the matching `DownloadedRegion` rows, so deleting the data really does mean starting over rather than leaving every cell/city marked "already covered" against an empty table.
- This makes the **manual** button itself incremental too (re-clicking "Download Roads" after nothing has changed now costs one DB scan and zero Overpass requests, not a full re-query) — there's no separate code path for "auto" vs "manual", both call the same `start_road_download()`/`start_subway_download()`/`start_poi_download()`.

`tracker/auto_download_tasks.py` is the scheduler that actually triggers unattended runs: a daemon thread from `apps.ready()` (mirroring `log_cleanup_tasks.py`'s pattern exactly — PG advisory lock namespace `0x52414d44` 'RAMD', `close_old_connections()` each pass, every exception swallowed) sweeps every 6 hours and, for whichever of `SiteConfig.auto_download_roads`/`auto_download_subway`/`auto_download_pois` are enabled (**all three default on**), calls the same `start_*_download()` entry point the manual button uses — skipping a kind only if its job row already looks genuinely mid-run (`status='running'` and updated within `STALE_AFTER_S`, the same staleness grace each job's own status endpoint uses to decide whether to resurrect a run). Because the downloads are incremental, a sweep against a fully-covered instance is nearly free — the cost is a full-history DB scan (no Overpass calls), not a re-download. The three toggles are editable from **Admin Panel → Downloads** (one checkbox per card, auto-saving via `POST /api/site/auto-download/`, admin-only) for an instance that would rather trigger downloads by hand — e.g. one whose Overpass mirror is flaky enough that unattended retries aren't welcome. **New model + `SiteConfig` fields ⇒ build + migrate.**

**Logging & monitoring** (admin-only; migration `0048`). Restored + extended from the pre-`0036` logging that was removed (the connection-leak that motivated that removal was already fixed by the batched writer). Three tables, all **operational data → excluded from backups** (never referenced by the backup builders, so no `meta.version` bump):
- **`AccessLog`** — one row per request (ip/path/method/status/response_ms/user/user_agent/timestamp). High-volume; written off the request path by a **batched single-consumer background writer** (`tracker/log_writer.py`, `enqueue_access`/`enqueue_action` — bounded queue, `bulk_create`, drop-on-overflow, `close_old_connections` per flush) fed by **`RequestLoggingMiddleware`** (`tracker/middleware.py`, registered right after `ApiKeyAuthMiddleware` so `request.user` is resolved; skips `/static/`, `/api/tiles/`, etc.). Pruned by retention.
- **`ActionLog`** — low-volume significant events: `login`/`logout`/`signup`/`login_fail`, `error` (traceback in `description`), `admin_toggle`/`admin_delete_user`/`custom_js_save`, `delete_data`/`delete_account`, `api_key_create`/`api_key_delete`. Written via `_log_action(request, action, description='', user=None)` in `views.py` (uses `_client_ip`; `user=False` forces a null FK when the acting user is being deleted). Kept long-term.
- **`DailyLogRollup`** — per-day aggregate (requests/unique_ips/unique_users/logins/signups/errors), computed by the cleanup sweep **before** pruning so long-range graphs survive row deletion. **Kept forever.**

**500-error capture:** `settings.LOGGING` attaches `tracker.error_log_handler.ActionLogErrorHandler` to the `django.request` logger; on a 5xx it pulls the traceback + path/IP/user and enqueues an `error` `ActionLog` row (best-effort, never raises).

**Retention + rollups:** `tracker/log_cleanup_tasks.py` runs a daemon thread (started from `apps.ready()`, mirroring `stats_tasks.py`), hourly, under a **PG advisory lock** (namespace `0x52414d47` 'RAMG', key `0` — single sweeping worker), `close_old_connections()` each pass. Each sweep: (a) upserts `DailyLogRollup` for every completed day up to yesterday, then (b) prunes `AccessLog` older than `SiteConfig.access_log_retention_days` (default 30) and (c) `ActionLog` older than `SiteConfig.event_log_retention_days` (default 0 = forever). Both retention knobs live on `SiteConfig`, edited from **Admin Panel → Retention** (`GET/POST /api/admin/log-config/`).

**Admin log endpoints** (all `_require_admin`): `GET /api/admin/overview/?range=24h|7d|30d|all` (`admin_overview_api` — stat tiles, a request-volume time series + logins/signups/errors series, status/top-path/top-IP/top-country breakdowns, recent events; hourly buckets for 24h/7d, daily from rollups+live tail for 30d/all via `_admin_daily_series`), `GET /api/admin/access-logs/` (paginated, ip/path/user/hours filters), `GET /api/admin/action-logs/` (paginated; `action=auth|admin` group filters + per-action), `GET/POST /api/admin/log-config/`. The template's charts reuse the app's **hand-rolled Canvas helpers** (`monotoneSpline`/`hexA`/`attachChartHover` + a generic `drawLineChart`, reading CSS vars at draw time for light/dark) — no charting library — and CSS width-% bars.

**Country breakdown (Monitoring tab).** `admin_overview_api` additionally aggregates every distinct `AccessLog.ip_address` in the selected range (not just the top-10 `top_ips` list) and resolves each to a country via `tracker/geoip_utils.py`, returning `top_countries` (`[{code, name, count}]`, sorted desc) + `unknown_country_count` (private/invalid/unresolvable IPs, bucketed separately rather than dropped). Resolution is **offline** — `geoip2fast` (the bundled `geoip2fast-ipv6.dat.gz` country database, IPv4+IPv6, ~41 MiB resident once loaded) — no external geolocation API call, consistent with the app's offline-first stance elsewhere (`offline_geocode.py`). The `GeoIP2Fast` instance is a **lazy module-level singleton** loaded on first lookup, not at import time, so a gunicorn worker that never serves an admin request never pays the load cost. The template renders it two ways from the same `top_countries` payload: a **MapLibre GL choropleth** (`tracker/static/tracker/data/world-countries.json`, the same dataset the map's "Scratch" feature uses, joined on the `cc` ISO-alpha-2 property — a blank `{version:8,sources:{},layers:[]}` style with no basemap tiles, just country fill/line layers, so the widget makes no third-party tile requests) shaded by a log-scaled opacity ramp on `--primary`, plus a `renderBars` bar-list card (`#country-bars`) for exact counts, matching the existing top-paths/top-IPs pattern. **New Python dependency (`geoip2fast`) ⇒ `docker compose up -d --build`** (no migration — no schema change, resolution happens at query time only).

**Analytics / custom JS:** Instance-wide HTML injected verbatim before `</body>` via `{{ CUSTOM_JS_SNIPPET|safe }}` (paste snippets as-given, including their `<script>` tags). Lives in the `SiteConfig` singleton (`SiteConfig.load()`, pk=1), edited from **Admin Panel → Custom JS** (admin-only, `POST /api/site/custom-js/`). The `custom_js_snippet` context processor exposes `CUSTOM_JS_SNIPPET` to **every** template, but the injection line must exist in each top-level template: `base.html` (all app pages) **and** the standalone public templates that don't extend it — `landing.html`, `login.html`, `signup.html`, `docs.html`, `privacy.html`, `terms.html`. Analytics must reach the public pages, so any new standalone template needs the injection line too. `context_processors.get_custom_js()` reads it cached (`site_custom_js`, 1h TTL); the save endpoint busts that key.

**Contact address + form.** `SiteConfig.contact_email` (migration `0047`, admin-only, edited from **Admin Panel → Contact**, `POST /api/site/contact-email/`) drives a **contact** link in the footer of the landing and settings pages. The context processor exposes it cached as `CONTACT_EMAIL` (`site_contact_email` key, 1h TTL, busted on save) plus `EMAIL_ENABLED`. When SMTP is configured the footer link opens a modal contact form (`tracker/templates/tracker/_contact.html`, a reusable partial `{% include %}`d by both pages, styled with shared CSS vars, square-cornered); otherwise it's a plain `mailto:`. The form POSTs `{name,email,message,website}` to `contact_api` (`POST /api/contact/`, **public, `@csrf_exempt`** because the landing page is per-visitor cached so an embedded token would mismatch, and a forged submit only mails the admin), which `send_contact_email`s to `contact_email` from `DEFAULT_FROM_EMAIL` with the sender as **Reply-To**. `website` is a spam honeypot (a filled value returns ok without sending). Blank `contact_email` hides the link entirely. Config only ⇒ **excluded from backups**, no `meta.version` bump. **New `SiteConfig` field ⇒ build + migrate.**

**AI "Ask" (per-user, BYO OpenAI-compatible LLM).** Optional **Ask** tab (`/ask/`, `ask_view` → `ask.html`) for natural-language questions over the user's location history. Config on `UserProfile` (`ai_ask_enabled`, `ai_base_url`, `ai_api_key`, `ai_model`, `ai_system_prompt`; migration `0031`), edited from **AI Ask** card in Settings (`POST /api/profile/ai-config/`). API key is masked as `••••••••` on GET, only overwritten on POST when value ≠ mask. `UserProfile.ai_configured` = enabled + base_url + key + model all set. The Ask tab only renders when `AI_ASK_ENABLED` is true (set in `context_processors.custom_js_snippet`); `ask_view`/`ask_api` re-check it (403 guard).

`tracker/ai_tasks.py` runs an OpenAI-compatible tool-call loop (`run_ask`): system prompt + client turns → `POST {base_url}/chat/completions` with `tools`/`tool_choice:auto` → execute tool calls scoped to `request.user`, append `role:"tool"` results, repeat ≤5×. All tools are strictly **read-only** ORM reads. `TOOL_DISPATCH` maps: `search_history`→`_run_history_search`, `get_day_detail`→`_compute_day_detail`, `list_visited_places`→`_compute_visits_from_qs`, `list_custom_places`→`_compute_places_payload`, `get_custom_place_detail`→`_compute_place_detail`, `get_distance`→`_compute_distance_from_qs`, `get_history_overview`→`_compute_overview_from_qs`. Journal tools (`search_journals`, `read_journal_entry`) are **opt-in**: only offered when `UserProfile.ai_allow_journals` is set (migration `0032`). `ask.html`'s `format()` renders only internal `/`-prefixed markdown links and `**bold**` after HTML-escaping — dates link to `/map/?date=YYYY-MM-DD` without XSS risk. Chat is ephemeral (browser-only). AI config excluded from backups. **New model field ⇒ build + migrate.**

**Response compression:** `GZipMiddleware` (first after SecurityMiddleware) gzips all dynamic responses. WhiteNoise handles its own pre-compressed statics, so no double-compression occurs.

**Design system (Field Journal, dark-first).** The web UI uses a cartographic-editorial system defined by CSS custom properties in `base.html`'s `:root` (dark, default) and `[data-theme="light"]` (paper). Palette: warm-ink backgrounds, trail-blaze orange `--primary` (#e8763d), and an earthy categorical set exposed through the **legacy clay-* token names** (`--clay-mint`=moss, `--clay-coral`=rust, `--clay-amber`=ochre, `--clay-lavender`=mauve, `--clay-sky`=map-blue) — the names were kept so all 18 base-extending templates restyle centrally; only values changed. Type: **Fraunces** (`--font-display`, serif), **IBM Plex Sans** (`--font-body`), **IBM Plex Mono** (`--font-mono`, used for all numerals/coordinates/micro-labels). Flat plates with 1px borders and hairline rules — the `--clay-shadow*` tokens now hold subtle/flat values (no puffy shadows), radii are 5–14px, and a faint topographic-contour SVG data-URI on `body::before` replaces the old gradient blobs. No `text-transform: lowercase` (removed globally), no glass blur, no gradient text/buttons. **The six standalone pages** (`landing`, `login`, `signup`, `docs`, `privacy`, `terms`) don't extend `base.html`, so each carries its own copy of the token block + `@font-face` and is dark-only (no theme toggle). Theme switches via `roamly_theme` localStorage (default `dark`) → `data-theme`, read in `base.html` and set in `settings.html`. **Map JS accents** (markers/lines/device+member track palettes) are hardcoded to the new hexes; the **speed-gradient (blue→green→amber→red) and heatmap density ramps are functional encodings and deliberately left unchanged** in `map.html`/`trips.html`/`adventures.html`/`trip_public.html`.

**Custom form controls (`RoamlyForms`).** `base.html` ships a global framework-free progressive-enhancement layer (one IIFE + `.rly-*` CSS, both inline). The native element stays in the DOM as source of truth (hidden via `.rly-hidden-native`); a flat button trigger + `<body>`-attached fixed-position popup render the custom UI, dispatching real `input`+`change` events on selection. Programmatic `el.value = x` / `el.selectedIndex = i` are intercepted via `Object.defineProperty` to keep the visible label in sync. Custom `<select>` rebuilt from live `<option>`s on each open (keyboard: ↑/↓/Enter/Esc/type-to-open); date picker is Monday-first with `min`/`max`, today/clear, and month/year grid jump. A `MutationObserver` re-runs `RoamlyForms.enhance()` for controls injected later. Opt out: `class="rly-native"`. `<select multiple>` and `<input type="datetime-local">` left native. Pure template change — no rebuild/migration.

**`RoamlyDialog` — alert()/confirm() replacement.** `base.html` ships a global themed dialog (one IIFE + `.rly-dialog-*` CSS, both inline, same flat-plate/square-corner language as `RoamlyForms`/`_contact.html`) so no page shows a native browser popup. `window.roamlyAlert(message, {title})` and `window.roamlyConfirm(message, {title, danger, confirmText, cancelText})` both return Promises (`confirm` resolves `true`/`false`) — call sites `await` them, same shape as native `confirm()` but async, so the surrounding function needs `async`. A single lazily-created overlay is reused; opening a second dialog while one is open resolves the first as cancelled rather than stacking. Escape resolves false/undefined, Enter resolves true/undefined, backdrop click cancels. `danger: true` swaps the confirm button to `--danger` red — used for anything destructive (delete/remove/permanently). Every template that used `window.alert`/`window.confirm` (adventures, adventure_edit, adventure_plan, adventure_public, admin_panel, data_table, diagnostics, editor, journals, map, places, settings) now calls these instead. Pure template change — no rebuild/migration.

**`RoamlyToast` — non-blocking success/error confirmation.** `base.html` ships a global toast (one IIFE + `.rly-toast-*` CSS, same flat-plate language as `RoamlyDialog`), for the many small confirmations that don't warrant a blocking modal. `window.roamlyToast(message, {type: 'success'|'error', duration})` returns a `dismiss()` function; `duration: 0` disables auto-dismiss (default 3200ms success / 5000ms error). Stacks bottom-right, dismissible by the × or auto-timeout. Most per-page "saved ✓" / "copied" inline-text feedback is left as-is — it's debounced-autosave feedback next to the field being saved, which is better UX right there than in a corner toast — `roamlyToast` is for actions with no natural inline anchor (e.g. the public adventure page's copy-link, which previously misused a blocking `roamlyAlert` for this).

**Flash-on-load convention.** A redirect can carry `?flash=<key>` (e.g. `?flash=joined`, `?flash=welcome`) and `base.html` shows the matching canned `roamlyToast` once on load, then strips the param via `history.replaceState` so a refresh doesn't re-show it. Used by `trip_join_view` (only on an actually-new `AdventureMember`, not a revisit of an old invite link) and both signup-completion paths in `signup_view`/`verify_view` (only for `purpose == 'signup'`, never a returning user's new-device login check). New keys go in `base.html`'s `FLASH_MESSAGES` map.

**`RoamlyIntro` — first-run welcome tour.** A guided, page-by-page walkthrough of the app's main sections (Map, Adventures, Journals, Places, Search, Ask when enabled, Stats, Visits, Settings), shown automatically once to a genuinely new signup and replayable anytime after. Built the same way as `RoamlyForms`/`RoamlyDialog`/`RoamlyToast` — one self-contained IIFE + `.rly-intro-*` CSS, both inline in `base.html`, no external tour library. Unlike those components it has no single overlay to keep mounted: the pages it explains are separate Django views, so the tour spans real full-page navigations rather than one modal sequence. A fixed bottom bar (`.rly-intro-bar`, docked above `--bottom-nav-height`) shows the current step's title + one-paragraph copy and a "Skip intro" control, visible and clickable on every step; the **"Next" button is a separate fixed-position element outside the bar's flow** (`.rly-intro-next`, pinned to the same `right`/`bottom` coordinates regardless of page) so it never moves even when a step's copy wraps to a different number of lines. Clicking Next writes the next step index to `localStorage` and navigates (`window.location.href`) to that step's URL; the next page load re-reads the state and re-renders the matching step.

Two-tier persistence, deliberately split by durability: **`UserProfile.intro_seen`** (migration `0065`, `BooleanField(default=True)`) is the durable, server-side, cross-device "has this account ever had the tour auto-triggered" flag — `default=True` backfills every pre-existing profile so a tour added later never retroactively interrupts anyone, and `signup_view` explicitly passes `intro_seen=False` when creating a brand-new profile so only that signup gets the automatic trigger. The **`roamly_intro_active`/`roamly_intro_step`** localStorage keys (see User-facing preferences below) hold the ephemeral in-progress state — whether a tour is currently running and which step — since that's per-browser navigation state a server round-trip on every page load would be wasteful for, not a durable account preference. The moment the tour auto-starts, `base.html` fires a background `POST /api/profile/intro-seen/` (`profile_intro_seen_api`) to flip the server flag immediately — so an abandoned tour (tab closed mid-walkthrough) still never re-triggers on a later visit, matching "must only trigger automatically once" even though the localStorage progress itself could otherwise be cleared or lost.

Per-request tour data (step list + `INTRO_PENDING`, the server flag's negation) is rendered into `window.__RLY_INTRO__` by `base.html` itself, guarded by `{% if user.is_authenticated and not standalone %}` (so it's absent on `editor`/`adventure_public`, the only two `standalone: True` pages, and on the anonymous standalone templates that don't extend `base.html` at all) — `context_processors.custom_js_snippet` exposes `INTRO_PENDING` alongside the other per-user flags. `window.RoamlyIntro.start()` (used by Settings → General Preferences → **"Replay intro"**) resets the localStorage state and navigates to the first step regardless of `intro_seen` — replay is purely client-side and never touches the server flag, so it can be repeated indefinitely. If the tour is active but the user navigates to a page with no matching step (e.g. Diagnostics), the bar simply doesn't render that load; state is untouched, so landing back on a tour page resumes it. **New `UserProfile` field ⇒ build + migrate.**

**Global JS error safety net + offline banner.** `base.html` also registers `window.onerror`/`unhandledrejection` listeners that surface a generic `roamlyToast('Something went wrong on this page.', {type:'error'})`, capped to one per page load — it doesn't fix root causes, it just stops a page failure from being silently invisible (a frozen skeleton with no indication anything broke). A separate `navigator.onLine`/`online`/`offline` listener pair drives a persistent top `.rly-banner` ("You're offline — showing cached data where available"), sitting below the sticky navbar on pages that have one (`body:has(.navbar) .rly-banner`). Pairs with the service worker's existing cache-fallback behavior, which previously had no accompanying UI explanation.

**Custom error pages.** `roamly/urls.py` registers `handler400/403/404/500` pointing at thin views in `views.py` (`error_400`/`error_403`/`error_404`/`error_500`) that all render a shared standalone `tracker/_error.html` (own copy of the token block, no nav chrome, no DB/session dependency — the 500 page in particular has to render when something is actually broken). These only take effect in the deployed environment when `DEBUG=False`; with `DEBUG` defaulting to `True`, a production deploy needs the env var set explicitly for them to ever be seen.

**Breadcrumbs.** `tracker/_breadcrumb.html` (`{% include %}`d with a `crumbs` list of `{label, url}` dicts, last entry has no `url`) is wired into `adventure_edit.html`, the one genuinely nested page that previously had only a bare back-arrow overlaid on its cover image with no visible trail. `adventure_plan.html` already has an equivalent back-link + trip-title bar and doesn't need it; `adventure_public.html` renders `standalone: True` (deliberately chrome-free for anonymous/shared visitors) so breadcrumbs there would fight that design intent.

**Skeleton loaders.** `base.html` ships a shared shimmer primitive (inline CSS): `.skeleton` gives any block the animated placeholder tint (a `::after` gradient sweep over `--bg-elevated`; light theme brightens the sheen via `--skeleton-sheen`, reduced-motion swaps the sweep for a gentle opacity pulse). Shape helpers: `.skel-line`(`.sm`/`.lg`), `.skel-circle`, `.skel-statval` (inline em-sized bar for big numeric stat tiles, scales with the element's font-size), `.skel-card`. Applied on initial page-load content across the data-driven pages — `stats` (stat tiles, timeline, states, transport bars), `places` (card grid + detail-modal stat grid), `visits` (table rows, all three tabs), `adventures`/`pals` (list cards), `journals` (stat chips + recent entries), `data_table` (table rows). User-triggered actions (search, load-more, recompute, diagnostics analysis) deliberately keep the `.spinner` — skeletons are for predictable-shape content that loads on page load, not one-off actions. Containers carry `aria-busy="true"`, cleared when data lands. Pure template change — no rebuild/migration.

**Landing page performance:** Hero stats read from `site_stats` cache key (1h TTL). Anonymous responses get `Cache-Control: public, max-age=300, stale-while-revalidate=86400` + `Vary: Cookie, Accept-Encoding`. Fonts are self-hosted (`tracker/static/tracker/fonts/{fraunces-latin-var,plex-sans-latin-{400,500,600,700},plex-mono-latin-{400,600}}.woff2`), the two LCP faces (`plex-sans-latin-400`, `fraunces-latin-var`) `<link rel="preload" as="font" crossorigin>`-ed, all served by WhiteNoise with 1-year immutable cache; no Google Fonts CDN anywhere (zero third-party). **New font files need `collectstatic` or `{% static %}` 500s on a missing manifest entry.** All CSS is inline and minified — edit it knowing it's a single line, re-minify after heavy edits. Heading order is strictly h1→h2→h3.

**SEO (`robots.txt` + `sitemap.xml`).** `robots_txt` (`/robots.txt`) allows the public marketing/legal pages, `Disallow`s the login-gated app + `/api/`, and points to `Sitemap: <site>/sitemap.xml`. `sitemap_xml` (`/sitemap.xml`, `views.sitemap_xml`) emits a plain `application/xml` `<urlset>` (built by hand, no `django.contrib.sitemaps`): the four public standalone pages (`/`, `/docs/`, `/privacy/`, `/terms/`) plus every published adventure (`Adventure.public_slug` non-null/non-empty → `/adventure/<slug>/`, `lastmod` from `updated_at`). Everything else stays out to match `robots.txt`'s Disallow list. Both build absolute URLs from `request.build_absolute_uri`. Python change ⇒ restart `web`.

**Auth:** Session-based for web. `ApiKeyAuthMiddleware` also accepts `Authorization: Bearer <key>` for mobile apps (GPSLogger, OwnTracks).

**Auth rate limiting.** The unauthenticated access endpoints are throttled per client IP via `_rate_limited(request, scope, limit, window_s)` in `views.py` (cache-backed — Redis in prod, LocMem in dev; **fails open** so a cache outage never locks users out). `_client_ip` reads the first `X-Forwarded-For` entry (behind the reverse proxy) and falls back to `REMOTE_ADDR`. Over-limit returns **HTTP 429** — mobile (`_is_app_client`) gets a JSON `{"status":"error",…}`, web re-renders the page with an error banner. Scopes/limits: `login` 10/5min, `signup` 5/hr, `pwreset` (reset request, sends email) 5/hr, `pwconfirm` (reset token submit) 10/15min, `verify` (email-code entry, brute-force guard) 10/15min, `verify_resend` (email-code flood guard) 4/15min. Not a persistent config — no model, no migration; **Python change ⇒ restart `web`** (templates for the 429 banners are live).

**Optional CAPTCHA (Cloudflare Turnstile) on login/signup.** A second, human-vs-bot layer on top of rate limiting — admin-configured, not env-based, mirroring the Contact Email pattern: `SiteConfig.turnstile_enabled`/`turnstile_site_key`/`turnstile_secret_key` (migration `0063`), edited from **Admin Panel → CAPTCHA** (`POST /api/site/turnstile/`, admin-only). The secret key is masked as `••••••••` on render and only overwritten on POST when the submitted value differs from the mask — same convention as `UserProfile.ai_api_key` (`_AI_KEY_MASK`). The context processor exposes only `TURNSTILE_ENABLED`/`TURNSTILE_SITE_KEY` (cached 1h, busted on save, mirroring `get_contact_email()`) — the secret is **never** added to a context processor or sent to any template; it's read once, server-side, via `SiteConfig.load()` inside `_verify_turnstile`. `login.html`/`signup.html` (both standalone, no shared base) load the Turnstile script and render the `cf-turnstile` widget div only when `TURNSTILE_ENABLED` is true, so a disabled instance loads no third-party script at all. `_verify_turnstile(request)` in `views.py` is called in `login_view`/`signup_view` right after the existing `_rate_limited` check: it **exempts mobile app clients unconditionally** (`_is_app_client` — the Android app posts to the same `login_view` but never renders the widget, so gating it would lock the app out regardless of the toggle), and otherwise POSTs the submitted `cf-turnstile-response` token to Cloudflare's `siteverify` endpoint. Unlike `_rate_limited`, it **fails closed** — a network error talking to Cloudflare is not proof of humanity, and the admin's escape hatch is the enabled toggle itself, not a silent bypass. Config only ⇒ **excluded from backups**, no `meta.version` bump. **New `SiteConfig` field ⇒ build + migrate.**

**Email verification (opt-in via SMTP).** All email behaviour is **gated on `settings.EMAIL_ENABLED`** (true only when `EMAIL_HOST` is set; SMTP config read from env in `settings.py`, passed through `docker-compose.yml`, documented in `.env.example`). With no SMTP configured the app behaves exactly as before — no verification, invites shown as copyable links. `tracker/email_utils.py` holds `email_enabled()`, `gen_code()`, `send_code_email()`, `send_invite_email()`, `send_password_reset_email()` (all sends are best-effort — a mail outage never 500s an auth request). Emails are **multipart text + branded HTML** — `_shell()` wraps content in a table-based, inline-styled dark layout matching the site palette; `_code_box()`/`_button()` render the code/CTA. The branded logo lockup is embedded as an inline `multipart/related` image referenced by Content-ID (`cid:roamlylogo`) via `_InlineImageEmail` (an `EmailMultiAlternatives` subclass that, after Django builds the message, `add_related`s the logo bytes onto the `text/html` part). **Django 6.0 rewrote `django.core.mail` on Python's modern `email.message.EmailMessage` and removed the undocumented `mixed_subtype` attribute** the old code set to force the related part — setting it now *raises*, silently killing every send (caught by `_send`'s broad except). `requirements.txt` pins `Django>=6.0,<7.0`, so a rebuild can pull a newer 6.0.x; the fix uses only supported API (`MIMEPart.add_related`). When enabled: **signup is verify-to-activate** (new account's `UserProfile.email_verified` set False; must enter an emailed 6-digit code before sign-in) and **login from a new/unrecognised device requires an emailed code**. `UserProfile.email_verified` defaults **True** (existing accounts + no-SMTP instances are never blocked). Known devices are tracked in the **`KnownDevice`** model (migration `0044`): the raw token lives in the long-lived `roamly_device` cookie, only its SHA-256 hash is stored; `_is_known_device`/`_trust_device` in `views.py`. Codes live in the cache (`email_code:{purpose}:{user_id}`, 15-min TTL); the pending flow is stashed in `session['pending_verify']`. Flow views: `verify_view` (`/verify/`) + `verify_resend` (`/verify/resend/`) render `verify_code.html`; `login_view`/`signup_view` carry a `?next=` through (`_safe_next`, used by trip invite links). **Password reset** (also SMTP-gated, standard Django token): `password_reset_request` (`/reset/`, `password_reset_request.html`) emails a link via `default_token_generator` (generic response — never reveals whether an account exists); `password_reset_confirm` (`/reset/<uidb64>/<token>/`, `password_reset_confirm.html`) validates the token and sets the new password (runs `validate_password`). The login page shows "forgot your password?" only when `email_enabled`. **Mobile:** the app sends `X-Roamly-Client: app` on login/verify (`_is_app_client`); a **successful** login stays the historical 302 (older builds keep working), but a **new-device challenge** returns `{"status":"verify",…}` JSON instead of redirecting. `AuthRepository.login()` returns a `LoginResult` (`Success`/`NeedsVerification`/`Error`); `verifyCode()` POSTs the code to `/verify/`. The app persists the `roamly_device` trust token in `UserPreferences.deviceCookie` (kept across logout) and replays it on login so a verified phone skips the code; the pending session id is held in memory (not `prefs.sessionId`) so "logged in" doesn't flip true before verification. `LoginScreen` shows a code-entry card. **New model + field ⇒ build + migrate; mobile change ⇒ rebuild APK + tag.**

**TOTP two-factor authentication (alternate to the emailed code).** An authenticator-app second factor, on `UserProfile.totp_secret`/`totp_enabled` (migration `0056`) + a `TOTPBackupCode` model (hashed, single-use, like `KnownDevice`'s token). **Independent of `EMAIL_ENABLED`** — the whole point is it works on instances with no SMTP — and unlike the emailed code, it is **not device-trust-based**: once enabled it's required on *every* login, not just new devices, and takes priority over the emailed-code check in `login_view` (checked after the signup-verify-email branch, before the new-device branch). Setup is web-only (Settings → **Two-Factor Authentication**): `POST /api/profile/totp/setup/` mints a secret (`pyotp.random_base32()`, unconfirmed — `totp_enabled` stays False) and returns a QR code (`_totp_qr_data_uri`, server-rendered via `qrcode`+base64 PNG, no client-side QR library); `POST /api/profile/totp/confirm/` requires a valid code against that secret before flipping `totp_enabled` True, and mints 8 single-use **10-digit numeric** backup codes (`_generate_totp_backup_codes` — numeric rather than alphanumeric so the same digit-only code field works for a TOTP code or a backup code, on web and mobile alike), shown once and only hashed (`_hash_token`, reusing `KnownDevice`'s helper) thereafter. `POST /api/profile/totp/disable/` requires the **account password**, not a TOTP code — so losing the authenticator app doesn't also lock the user out of turning 2FA off; `POST /api/profile/totp/backup-codes/regenerate/` requires a **TOTP code** instead, being routine maintenance rather than recovery. `GET /api/profile/totp/` reports enabled + remaining backup-code count. Login flow: `login_view` stashes `session['pending_totp']` and redirects to `totp_verify_view` (`/totp/`, `totp_verify.html`, cloned from `verify_code.html`); `_verify_totp_or_backup` checks the 6-digit TOTP code first (`pyotp.TOTP(...).verify(code, valid_window=1)`), then falls back to an unused backup code (consumed on match). A successful TOTP check also calls `_trust_device` when `email_enabled()` — a TOTP-enabled user who passes 2FA skips the emailed-code flow going forward too, avoiding double friction.

**The two factors are offered together, not exclusively.** TOTP is *first* whenever it's enabled, but the challenge page offers an **email a code instead** button when the instance has SMTP and the account has an address (`totp_verify_view` passes `email_fallback`) — an authenticator app can be out of reach while the mailbox isn't, and the backup codes alone are a poor answer to that. `POST /totp/email/` (`totp_email_fallback`) moves the pending state from `session['pending_totp']` to `session['pending_verify']` via the existing `_start_verification(user, 'login')`, marked **`from_totp`**; the emailed-code page reads that flag to reword its subtitle and to offer the way back, `POST /verify/totp/` (`verify_use_totp`), which restores `pending_totp`. `verify_use_totp` acts **only** when `from_totp` is set, so it can never re-route a plain new-device challenge. The fallback shares the `verify_resend` flood budget (4/15min) since it too sends mail. With no SMTP or no address, nothing changes — TOTP stays the only route, exactly as before; with no TOTP, the emailed code is unchanged.

**Mobile:** `login_view` returns `{"status":"totp_required"}` JSON for app clients (alongside the existing `{"status":"verify"}` for the emailed code), now carrying `email_available` + the masked `email` so the app can show the same fallback link; `AuthRepository.login()` gained `LoginResult.NeedsTotp` + `verifyTotp()` (POSTs to `/totp/`, mirrors `verifyCode()`/`/verify/`), plus `switchToEmailCode()`/`switchToTotp()` (a shared `switchChallenge()` POSTing the pending session to `/totp/email/` and `/verify/totp/`, mapping the JSON back onto a `LoginResult` — neither endpoint can complete a login, so `Success` is never a valid answer); `LoginScreen` shows a code-entry card identical in shape to the email-verify one, with the cross-links between the two. TOTP *setup* is deliberately **not** exposed on mobile (mirrors `mapbox_token`'s read-only-on-mobile precedent) — only the login-time challenge is mobile-aware. **New model + field ⇒ build + migrate; mobile change ⇒ rebuild APK + tag.**

**Login by username *or* email.** `login_view` first tries `authenticate(username=…)` as-is; if that fails and the identifier contains `@`, it resolves the email to a username via `User.objects.filter(email__iexact=…, is_active=True)` and retries — **only when exactly one active account matches** (legacy duplicate emails stay username-only, never ambiguously logged in). All downstream flow (email-verify, device trust, app JSON) keys off the returned user, so mobile gets email login for free. `SignUpForm.clean_email` enforces **case-insensitive email uniqueness** at signup so future email logins are unambiguous (existing duplicates are untouched — no data migration). Login page field is labelled "username or email".

**AI summary emails (opt-in, per-user).** When an instance has SMTP (`EMAIL_ENABLED`) *and* the user's AI Ask provider is configured (`UserProfile.ai_configured`), the user can opt into **daily / weekly / monthly / yearly** recap emails (independent cadence flags `summary_daily/weekly/monthly/yearly` on `UserProfile`, migration `0046`). `tracker/summary_email_tasks.py` mirrors `stats_tasks.py`: a daemon thread from `apps.ready()` sweeps hourly, `close_old_connections()` each pass, and for each opted-in user sends any cadence whose `summary_last_<period>` cursor predates the current period boundary (`_period_bounds` computes previous day/week/month/year windows in **server localtime**; restart-safe, no external cron, no duplicate sends). Single-flight per user via a PG **advisory lock with its own namespace** `0x52414d53` ('RAMS', distinct from stats' 'RAML'). Stats reuse the queryset helpers `_compute_overview_from_qs`/`_compute_distance_from_qs` (date-filtered qs, converted to the profile's `distance_unit`). Empty periods skip the email but still advance the cursor.

**Narrative + top cities/places.** Each email carries a short **AI-written narrative** — two dedicated prompts, deliberately *not* the Ask tab's Q&A prompt: `SUMMARY_SYSTEM_PROMPT_DAILY` is handed an actual chronological stay timeline (`_stay_timeline`, built from the period's `Visit` rows — labelled by matched POI, else `place_name`, else city — across all the user's devices, `_period_visits`) and told to narrate the day's real sequence ("you went to X in the morning, then spent the afternoon near Y"); `SUMMARY_SYSTEM_PROMPT_PERIOD` (weekly/monthly/yearly) is grounded in a **top cities / top places** ranked breakdown instead of a day-by-day rundown, which would be unreadable over a month. Both demand one short, concrete paragraph — no markdown, no invented facts. `_top_cities` re-sorts `_compute_visits_from_qs`'s per-city `time_spent` descending; `_top_places` groups the same `Visit` rows by POI id (else a ~111m lat/lon grid, matching the fog-of-war cell precision) and sums dwell time, so repeat stays at one spot collapse into one ranked entry. Both lists are also rendered in the email itself via `email_utils._ranked_list()` (numbered rows, alongside the existing `_stat_grid()` tiles), and fed as JSON to whichever prompt applies (`ai_tasks._provider_chat(profile, messages)`, no tools; `AIProviderError` → stats-only fallback). The email also links to `{SITE_URL}/map/?start=&end=` (boxed primary button) and `{SITE_URL}/stats/?start=&end=` (`email_utils._link()`, lighter secondary link) scoped to the period's date range — background threads have no `request` to call `build_absolute_uri` on, hence `settings.SITE_URL`.

Email built by `email_utils.send_summary_email()`. Config/endpoint: `GET/POST /api/profile/summary-email/` (`profile_summary_email_api`, `@login_required`) — GET returns flags + `available` (email+AI both set); POST saves the four toggles, or with `{"test":"daily"}` fires an immediate test send (`summary_email_tasks.send_summary_now`, bypasses due-check, doesn't advance the cursor). Settings → **Summary Emails** card (only shows cadence toggles when `summary_available`, else a "needs SMTP + AI" note). Summary prefs are config ⇒ **excluded from backups** (like AI config), no `meta.version` bump. **New model fields ⇒ build + migrate.**

**Distance unit in emails.** `roamly_speed_unit` (`kmh`/`mph`) is otherwise a pure client-side localStorage preference (see User-facing preferences below) — the summary-email scheduler runs in a background thread with no browser to read it from. `UserProfile.distance_unit` (migration `0058`, same `'kmh'`/`'mph'` values) is a server-side mirror written by `saveSpeedUnit()` in `settings.html` via `GET/POST /api/profile/distance-unit/` (`profile_distance_unit_api`) alongside the existing localStorage write — the map/stats pages are untouched, still localStorage-only. `summary_email_tasks._format_distance(km, unit)` converts the stat-tile figure and the JSON handed to the AI narrative.

**Unsubscribe (no login required).** Every recap email carries a "Manage email preferences" link built from `UserProfile.email_unsub_token` (migration `0057`, lazily minted by `email_utils._ensure_unsub_token` on first send — `null=True` so untouched profiles don't collide on the unique constraint, same trick as `Adventure.invite_token`). `email_unsubscribe_view` (`/email/unsubscribe/<token>/`, `email_unsubscribe.html`) looks the profile up by token — the token *is* the credential, same trust model as the password-reset link. A GET carrying `?period=<cadence>` (what the email link points to) one-click-flips just that cadence off before rendering the full 4-checkbox form for further changes; a plain POST saves all four at once. **Mobile design system (Field Journal).** The app used a stock Material 3 look (dynamic Material You color, default typography, tonal-elevation cards) that didn't match the web app and wasn't well liked; it's now a port of the web's own Field Journal system (see **Design system (Field Journal, dark-first)** above) — same dark/light hex palette read directly from `base.html`'s `:root`/`[data-theme="light"]`, so the two stay in sync by construction rather than by convention. `ui/theme/Theme.kt` defines `DarkColors`/`LightColors` (`darkColorScheme`/`lightColorScheme`) from that palette; **dynamic color is deliberately removed** — Field Journal is a fixed brand palette, not a per-device Material You scheme. `tracking/LocationTrackingService.kt` is a foreground service. **Capture uses two layers** (`applyCapture`):

- **Primary: continuous `requestLocationUpdates` stream + `PARTIAL_WAKE_LOCK`** — delivers smooth per-interval cadence when not in deep Doze (screen on, charging, or moving). Doze suspends the stream and ignores the wake lock, so it only runs when the device is already awake.
- **Backup: exact-alarm cadence** (`runFixCycle` → `scheduleNextFix`) via `setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP)` + `ACTION_TAKE_FIX` (FGS-start exemption). `runFixCycle` skips cheaply while the stream is fresh, takes over in Doze. Alarm cadence clamped to `MIN_ALARM_FLOOR_MS` (15s); next-fix delay measured from cycle start so acquiring time counts toward the interval.
- **`acquireBestFix`** — streams fixes for `min(interval, 10s)` budget, keeps most accurate, stops early on `maxAccuracyM` met or `ACQUIRE_STALL_MS` (3.5s) plateau. Logs best fix rather than gapping.
- **Dwell points (`dwellPointFrom`)** — when no fresh fix arrives (fused provider returns cached location, dedup rejects it), re-logs last known position stamped now (zero speed). Only while last real fix is within `DWELL_MAX_AGE_MS` (10 min).
- **Catch-up backstop** — `scheduleNextFix` arms a second alarm at `CATCHUP_MULTIPLIER` (3) × interval so a dropped alarm recovers within 3×. `runFixCycle` force-resets a `fixInProgress` flag stuck longer than acquisition budget.

**`LocationFilter.accept()` is a pure check; `commit()` is what advances its state**, called from `savePoint` once the row exists. When `accept()` did the advancing itself, a fix later discarded by the accuracy gate in `saveOrDwell` still moved `lastAcceptedTimeMs` to ~now — so the dwell point substituted in its place was rejected by the de-dup window (80% of the interval, 24s at the default 30s), and so was every fast retry, since 4s and 10s both fall inside it. Anywhere accuracy degraded, capture went **completely silent** rather than dwelling. The window now measures from the last point actually *saved*. Both methods are `@Synchronized` — the stream callback thread and the fix-cycle coroutine both reach them.

`savePoint(loc, isDwell)` distinguishes a real fix from a dwell re-stamp: only a real fix advances **`lastRealFixAtMs`**, which is what `DWELL_MAX_AGE_MS` is measured against (checking `lastAcceptedAtMs`, which a dwell save refreshed, meant the ceiling never expired and an outage fabricated an endless parked track). Dwell points also **skip the drift anchor** — their synthetic `speed = 0f` would otherwise let an outage *while moving* plant a false stationary anchor.

**`streaming` tracks the screen** (`streaming = screenOn` in `applyCapture`), not a hardcoded `true`. `screenOn` was maintained and then read nowhere, so: `runFixCycle`'s "recent point ⇒ interval already covered" skip applied in Doze where it must not (halving the cadence — the one thing its comment says must never happen), the untimed wake lock was never released, and the watchdog re-armed a stream the OS had suspended.

Callbacks run on `HandlerThread` ("RoamlyLocCb"). No-fix retries: quick (4s × 3) → medium (10s × 3) → `MIN_ALARM_FLOOR_MS`. Priority "auto" degrades `HIGH_ACCURACY`→`BALANCED` after 2 misses; explicit priorities honoured exactly; HIGH stays first so airplane mode (GPS-only) still works. Falls back to `fusedClient.lastLocation` when budget exhausted. Coarse 15-min heartbeat (`TrackingAlarmReceiver`) remains as the ultimate liveness check.

**Battery exemption is gated, not optional.** Without it, `setExactAndAllowWhileIdle` throttles to ~9 min in Doze. Starting tracking is blocked behind the exemption gate in `SettingsScreen` (with a "Track anyway (gaps)" escape hatch). While not exempt, a coral warning banner and notification line appear. `LocationFilter` is the **single accept() authority** — never movement-gated or accuracy-gated; rejects stale (> 2× interval), duplicate/older timestamp, or teleport (> 357 m/s). **Stationary-drift suppression (`tracking/DriftAnchor.kt`, default ON, toggle in Settings → GPS "Suppress stationary drift" → `UserPreferences.suppressStationaryDrift`).** The teleport guard only catches the *physically impossible*; a parked phone whose GPS wanders off at ~30 mph is plausible and consistent, so it slips through. `DriftAnchor` uses the tell that the chip's **Doppler speed (`Location.speed`) stays ≈ 0 while stationary even as the position estimate drifts**: after a short streak of low-Doppler fixes clustered within `ENTER_RADIUS_M`, it drops an anchor at their centroid and thereafter returns drift fixes **snapped** to the anchor (speed 0), so a parked device logs one stable point per interval instead of a drift spider. It releases the anchor three ways, and each threshold is load-bearing: Doppler showing real movement (**`MOVE_SPEED_MPS` = 0.8 m/s**, `EXIT_MOVE_STREAK`) — deliberately *below* walking pace of 1.2–1.4, since at the original 1.5 a walk away from a parked anchor never cleared the bar and was snapped back until the hard break 300m later; **sustained displacement** (`DEPART_RADIUS_M` 60m × `EXIT_DISPLACE_STREAK` 3), the only escape available to the speed-less fixes `PRIORITY_BALANCED` returns, which is exactly what the auto-degrade after two misses produces; and a **corroborated** large relocation (`HARD_BREAK_M`). The corroboration matters: releasing on the *first* fix past `HARD_BREAK_M` let a lone glitch through unmodified, before any speed check, and it then became the baseline for everything after — that is the isolated far-away, high-speed point that appears beside a stationary cluster. A break now needs a second fix also beyond `HARD_BREAK_M` and within `BREAK_CLUSTER_M` (150m) of the first; a real departure still releases one interval later, a spike is snapped and never recorded off-position. Wired at the single write chokepoint — `resolve()` runs at the top of `savePoint`, so the stream, fix-cycle, and dwell paths all flow through it; `driftAnchor.reset()` on pause. No new permission (reuses `Location.speed`). Points cached in Room, uploaded by `UploadWorker` (offline-first; `replace=true` for user-initiated syncs). **Batch upload:** tries `POST /api/push/batch/` (up to 100 points, `bulk_create(ignore_conflicts=True)`), falls back to single `POST /api/push/`. **Wedged-backlog recovery:** `savePoint` escalates to `replace=true` when backlog is non-empty and no successful delivery for `UPLOAD_STUCK_AGE_MS` (120s). Count backstop `UPLOAD_STUCK_THRESHOLD` (~40) kept as ceiling. `MainActivity.onResume` force-pushes (`replace=true`) any unsynced backlog on foreground.

**Tracking survivability stack:**
1. *Triple-defensive `startForeground`* — `goForeground()` called three times in `onStartCommand` and on boot.
2. *START_STICKY + persisted resume* — null-intent recreation reads `prefs.trackingEnabled` and resumes or stops.
3. *Self-resurrection* — `receiver/RestarterReceiver` (action `com.roamly.RESTART_TRACKING`) restarts service; service broadcasts to it from `onDestroy`/`onTaskRemoved` when torn down while enabled.
4. *Doze-piercing alarms* — two independent `setExactAndAllowWhileIdle` + `ELAPSED_REALTIME_WAKEUP` alarms (fall back to inexact when exact-alarm permission denied): (a) per-point fix alarm (`scheduleNextFix`, `ACTION_TAKE_FIX`), (b) 15-min liveness heartbeat (`TrackingAlarmReceiver`).
5. *Boot + app-update* — `receiver/BootReceiver` handles `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`/`MY_PACKAGE_REPLACED`/QUICKBOOT.
6. *Battery-optimization exemption* — `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` dialog from Settings → Reliability.
7. *OEM-killer onboarding* — Settings → Reliability links to `dontkillmyapp.com/<manufacturer>`.
8. *Multi-provider re-arm* — `PROVIDERS_CHANGED` receiver re-arms capture when providers toggle. `start()/stop()` wrapped in `runCatching` so a blocked FGS-start degrades to heartbeat retry.

**Stopping cleanly.** `trackingEnabled` = tracking should be running (gates START_STICKY resume, heartbeat, restarter, app-launch `resumeTrackingIfNeeded`). `autoStartTracking` = user-facing "Start on boot" option (the only thing `BootReceiver`/`MY_PACKAGE_REPLACED` keys on). `TrackingCoordinator.stopCompletely()` clears both + `trackingActive`, cancels heartbeat and periodic `UploadWorker`, kicks a final flush, stops service. Stop button requires confirmation dialog in both in-app Settings and notification Stop action (`EXTRA_CONFIRM_STOP` via `singleTop` `onNewIntent`). Starting sets `autoStartTracking=true` by default.

**Story body id-remapping on restore.** An adventure's `body` (the Story block document) embeds live database ids — inline `[^pin:ID]` footnotes, `location_card.place_id`, `photo_grid.photo_ids` — pointing at specific `AdventureBlurb`/`AdventureBlurbPhoto` rows. Restoring into a fresh database (the actual disaster-recovery case) recreates every blurb and photo with new auto-increment ids, so a `body` copied over verbatim would silently orphan every pin footnote, location card and photo grid — the same class of problem `AdventureDayNote.place_ref` already solves for day notes via a natural key (title+lat+lon), but `body` embeds ids, not natural keys, so the fix is different: v9 backups carry each blurb/photo's original `id`, and `restore_backup` builds `blurb_id_map`/`photo_id_map` (old id → newly-created row) while creating them, then `_remap_story_body_ids` walks `adv.body` after all blurbs/day-notes are created and rewrites those three reference points through the maps before saving. Only runs for freshly-created adventures (`adv_created`) — an adventure that already exists doesn't get its blurbs recreated, so there's nothing to remap. Backups without blurb/photo `id`s (pre-v9) restore exactly as before — unresolvable refs are left untouched, same as today.

**Manual backup is one zip (data + media), restorable in one step.** `export_backup_start` writes `_write_backup_json`'s output to a plain temp `.json`, then zips it into `backup.json` plus a `media/<relative-path>` entry per file from `_get_user_media_files` (adventure covers, blurb/day-note photos & videos, journal photos, profile picture) — the same file list S3 image backup uses, so the two stay in sync by construction. `ZIP_DEFLATED` for the JSON (text compresses well), `ZIP_STORED` per-file for media (already-compressed JPEG/MP4 — deflating again buys nothing). Exists because before this, photos/videos were only ever recoverable through the optional S3 image backup; an instance with none configured had no way to get them out at all. `restore_backup` sniffs the upload's magic bytes: `PK\x03\x04`/`PK\x05\x06` (zip) opens it, restores from `backup.json` as before, then extracts every `media/` entry to `MEDIA_ROOT` at its stored relative path (same path the just-restored `ImageField`/`FileField` values already point at, so nothing needs re-linking) — guarded against zip-slip by rejecting any entry whose normalized path would land outside `MEDIA_ROOT`. Anything else falls back to the legacy path (plain or gzip-magic-prefixed JSON, no media) for backups downloaded before this change. Settings' "Restore Backup" accepts `.zip`/`.json`/`.gz` for exactly that reason. **S3 auto-backup (`BackupConfig`) is untouched by any of this** — still JSON-only via `_build_backup_json`, with image backup as its own separate optional S3 upload.

**Backup download progress + sized transfer.** `export_backup_start` stores a *dict* job record in the cache (`backup_job:{user}:{job}`, TTL 3600 refreshed on every update) — `{status, stage, pct, done, total, started}`, and on completion `size` (final zip bytes) + `file_count` (media files zipped). One progress bar covers both phases: `_BACKUP_PREP_PCT`–`_DATA_PHASE_PCT` (8–55) for `_write_backup_json`'s callback (per section and every 5000 locations, `done`/`total` = locations), `_DATA_PHASE_PCT`–100 for the media-zipping loop (`done`/`total` = files, updated every 20). `export_backup_status` derives `eta` server-side from elapsed ÷ pct; Settings renders a `.bk-progress` bar with stage label, ETA, and a `done/total <unit>` line where the unit follows the current stage. **Because the download is a real `.zip` file on disk, `FileResponse` gets a correct `Content-Length` for free** — none of the gzip-streaming `Content-Encoding` trickery the old JSON-only download needed (Django's `GZipMiddleware` deletes `Content-Length` on streaming responses since it can't know the compressed size ahead of time; a zip's `FileResponse` already knows its size, so the response just sets `Content-Encoding: identity` to keep the middleware from re-compressing an archive that won't shrink further).

## Models

**Core tracking:**
- `Device` — a tracked phone/device, belongs to a User
- `Location` — raw GPS point (lat, lon, altitude, accuracy, speed, battery, timestamp) + reverse-geocoded city/state/country
- `APIKey` — 64-char hex token for mobile push auth

**Adventures** (named journeys, formerly "Trips"; Pals was a separate, simpler multi-member feature — **removed** in migration `0059`, its one distinct capability, per-member tracks, subsumed here). An Adventure is a **shared** journey: the editor (`adventure_edit.html`) and public page (`adventure_public.html`) present it as **Day Log · Story · Map**. In the editor the left pane toggles **Story** (the freeform `body` block document) and **Day Log** (per-member per-day notes); the **Map** stays persistent on the right rather than being a hidden tab. The public page renders the same content read-only as article sections.
- `Adventure` — time-bounded journey (device, creator, start_time, end_time, public_slug, subtitle, cover_image, cover_image_thumbnail, body). `body` is the **Story** — a JSONField of typed blocks (heading, paragraph, map_embed, photo_grid, divider, callout, location_card, timeline). The `timeline` block holds `{title, events:[{date, title, note}]}` and renders as a vertical dated timeline in editor + public (no backend model — lives in body JSON; `map_embed` blocks render a live MapLibre mini-map in the editor too). `.locations` filters Location by device + time range. `trip_detail`/`trip_public_detail_api` also assemble **`member_locations`** — each member's own device track for the window — so a shared adventure paints every traveller's route (per-member colour on the public map embeds).

Plan page surfaces the link + copy/reset/email-invite UI.
- `AdventureBlurb` — **the unified POI**: `title` + `text` (notes) + optional lat/lon + author + photos + comments + **`rating`** (1–5, null = unrated) + **`category`** (migration `0060`; slugs in `ADVENTURE_PLACE_CATEGORIES` — restaurant/cafe/bar/hotel/store/attraction/nature/transport/town/other). Located blurbs are the adventure's points of interest; a **categorised** place renders an emoji-glyph marker (else the star), and stars + a category badge show on the place card, map popup, and public page. Referenced inline in paragraph/heading/callout text via `[^pin:ID]` and by `location_card` blocks (both use the blurb id). **`AdventurePlace` was removed in migration `0037`** which copies each place into a blurb and rewrites all `[^pin:ID]`/`location_card.place_id` refs in body JSON to the new blurb ids. The `/api/trips/<id>/places/{create,<id>/update,<id>/delete}/` endpoints operate on blurbs (accept `rating`/`category`, cleaned by `_clean_rating`/`_clean_category`); `_poi_payload` carries them everywhere; `trip_detail`/public detail expose located blurbs as `places` so refs resolve.
- `AdventureBlurbPhoto` — photo **or video** on a blurb (max 5; `media_type` `image`|`video`, migration `0062` — image rows keep `image`+`thumbnail`, video rows use the `video` FileField). Also the store for story `photo_grid` blocks.
- `AdventureMilestone` — titled event with emoji and date
- `AdventureComment` — comment on a blurb
- `AdventureDayNote` / `AdventureDayPhoto` (migration `0060`; `0061` made it multi-entry) — **the Day Log**: `title` + `body` + up to 10 photos **or videos** (`AdventureDayPhoto`, `media_type` `image`|`video`, migration `0062`) + optional `place` FK to a located `AdventureBlurb`. A member may hold **several entries per day** (migration `0061` dropped the old `(adventure, author, date)` uniqueness), each editable only by its author, all grouped under the date and attributed. The day's map track is derived on the fly (the "show on map" button fits the editor map to that date's points; not stored). Deliberately **not** the personal `JournalEntry` model — journals are private/single-author, day notes are adventure-scoped and public-visible. Endpoints are **id-keyed** (all `@login_required` + `_get_trip_for_user`, writes **author-scoped** via `_own_day_note`): `GET /api/trips/<id>/days/`, `POST /api/trips/<id>/days/<YYYY-MM-DD>/create/` (new empty entry), `POST /api/trips/<id>/days/note/<note_id>/` (save title/body/`place_id`, validated by `_resolve_day_place`), `POST /api/trips/<id>/days/note/<note_id>/photos/` (multipart), `POST /api/trips/<id>/days/note/<note_id>/delete/`, `POST /api/trips/<id>/days/photos/<photo_id>/delete/`. `_adventure_day_notes`/`_day_note_payload` serialize (payload carries the linked `place`); `trip_detail`/`trip_public_detail_api` expose `day_notes`. Editor `adventure_edit.html` renders the Day Log as **list or calendar** (month grid, Monday-first, note titles shown in cells); the left pane is a draggable split with the map. **New model ⇒ build + migrate.**
- `PlannedStop` (migration `0043`) — **the forward-looking itinerary**: an ordered planned stop on an Adventure (`name`, optional lat/lon + `location_name`, `arrival_date`, `nights`, `transport` leg, `accommodation`, `notes`, `order`). Deliberately a *sibling* of `AdventureBlurb`, not merged: blurbs are past located notes, PlannedStops are future intent, so one Adventure holds both the plan and the recorded track (plan-vs-actual). Editor: the **"itinerary" panel** in `adventure_edit.html` (reorderable stop cards + "add stop" drops a numbered pin on the map; a dashed connector line joins located stops in order). Endpoints (all `@login_required` + `_get_trip_for_user`): `GET /api/trips/<id>/plan/`, `POST /api/trips/<id>/plan/create/`, `POST /api/trips/<id>/plan/<stop_id>/update/` (also reorders via `order`), `POST /api/trips/<id>/plan/<stop_id>/delete/`. `trip_detail` + `trip_public_detail_api` expose `planned_stops`; the public page (`adventure_public.html`) renders the dashed itinerary line + numbered markers on every map embed **and** an "Itinerary" list section. **New model ⇒ build + migrate.**

**Journals:**
- `JournalEntry` — one per user per calendar day (`unique_together = user, date`). Fields: title, body, mood (emoji), weather, is_favorite, optional pin (pin_latitude/pin_longitude/location_name). Day map is derived on the fly from `Location` points via `_journal_day_track` in `views.py`.
- `JournalPhoto` — photo on an entry (image + thumbnail, caption, order; max 20).

Streaks (`_journal_compute_streaks`) and lifetime totals computed from entry dates. Page (`journals.html`): Monday-first calendar, recent-entries list, two-pane editor modal (left: editor + photo grid; right: MapLibre day track). Journal endpoints under `/api/journals/`; `<str:date_str>` route registered after `stats/` and `photos/<id>/delete/` to avoid shadowing. `journal_photos_api` is `@csrf_exempt` for mobile multipart upload.

**Background jobs:**
- `GeocodingJob` — geocoding progress per user
- `POIDownloadJob` — OSM POI download progress
- `TransportJob` — transport-mode detection progress
- `BackupConfig` — S3 backup config + status

**Admin logging** (migration `0048`; see Logging & monitoring above; excluded from backups):
- `AccessLog` — one row per HTTP request (admin traffic/IP-access log)
- `ActionLog` — significant events (logins/signups/errors/admin actions)
- `DailyLogRollup` — per-day aggregate counts, kept forever

**Roads & gap filling** (migration `0049`; see Road snapping + gap filling above; all excluded from backups):
- `RoadSegment` — an OSM way: `way_id` (unique), `name`, `highway`, `oneway`, PostGIS `LineString` `geom` (GiST), plus a vestigial empty `node_ids` (`bigint[]`). Instance-wide, no user FK. PostGIS-only.
- `RoadDownloadJob` — progress row for the road download
- `RailSegment` — an OSM subway way: `way_id` (unique), `name`, `railway`, PostGIS `LineString` `geom` (GiST). Instance-wide, no user FK. PostGIS-only. (migration `0064`)
- `RailStation` — an OSM subway station node: `node_id` (unique), `name`, PostGIS `Point` `geom` (GiST). Used for transfer stitching + gap-proximity. Instance-wide. PostGIS-only.
- `RailDownloadJob` — progress row for the subway download (clones `RoadDownloadJob` + a `stations` counter)
- `DownloadedRegion` — coverage tracking so a re-run only asks about growth since last time: `kind` = `road`/`subway`/`poi`, `key` = a `"gy,gx"` grid-cell coordinate or a `"city|state"`. See "Auto-download new regions" above.
- `DismissedSubwayGap` — a detected subway gap the user rejected (user + start/end anchor coords), so it stops resurfacing. User intent ⇒ excluded from backups.
- `EditBatch` — one map-editor action, so it can be undone as a unit; `location_ids` records real rows a paste-as-real created
- `InferredLocation` — a point the editor generated. **Never** a recorded fix, and read only by the map and the editor
- `TrashedLocation` — full snapshot of a deleted real point, restorable for 30 days

**User:**
- `UserProfile` — profile picture, `is_admin`, AI Ask config (`ai_ask_enabled`/`ai_base_url`/`ai_api_key`/`ai_model`/`ai_system_prompt`/`ai_allow_journals` + `ai_configured` property), `mapbox_token` (server-side Mapbox basemap token, synced to all devices), road config (`road_provider`/`osrm_url`/`snap_to_roads` (default **True**) + `road_provider_resolved` property; see Road snapping), `email_verified` (default True; see Email verification), summary-email opt-in (`summary_daily/weekly/monthly/yearly` + `summary_last_*` cursors + `summary_any` property; see AI summary emails), `email_unsub_token` (lazily-generated unsubscribe-link credential), `distance_unit` (server-side mirror of `roamly_speed_unit`, for the summary-email job), TOTP 2FA (`totp_secret`/`totp_enabled`; see TOTP two-factor authentication), `intro_seen` (default True; see `RoamlyIntro` — first-run welcome tour); `get_or_create`'d in `settings_view`

- `TOTPBackupCode` — a hashed, single-use TOTP recovery code (migration `0056`; see TOTP two-factor authentication above)

- `CustomPlace` — user-defined geofence (`name`, `latitude`, `longitude`, `radius_m`, auto-assigned `color`)
- `DismissedSuggestion` — a place suggestion the user rejected, so it stops resurfacing (suggestions themselves aren't stored)

**Geocoding reference data:**
- `Boundary` — US Census TIGER admin polygon (`name`, `state`, `kind` = `place`|`cousub`, PostGIS `geom` MultiPolygon, GiST-indexed). PostGIS-only.

## URL / API conventions

Adventure API URLs use `/api/trips/` paths (backward compat). View functions are still named `trips_api`, `trip_detail`, etc. — only UI and model classes use "adventure" naming.

Public adventure pages: `/adventure/<slug>/` (`adventure_public.html`); public API: `/api/trip/<slug>/`.

Adventure CMS editor: `/adventures/<id>/edit/` (login + membership required). Endpoints:
- `PATCH /api/trips/<id>/body/` — save body JSON (also accepts `name`, `subtitle`)
- `POST /api/trips/<id>/cover/` — upload cover image
- `POST /api/trips/<id>/cover/delete/` — remove cover image
- `POST /api/trips/<id>/blurbs/<id>/update/` — edit blurb (text, lat/lng, location_name)

Inline pin refs: `[^pin:42]` references a located `AdventureBlurb` (POI) by id. Number computed from document order, not stored. POIs render as coral star markers on editor + public maps; clicking opens a themed popup (author + title + notes + photos). Create/edit via the map "add POI" flow (uses the repurposed `/places/` endpoints).

## Custom Places

User-defined named geofences — **Places** tab (`/places/`, `places_view` → `places.html`). `CustomPlace`: `name` + center + `radius_m` + auto-assigned clay-palette `color` + `notes` (migration `0030`). Membership computed on the fly via `_find_nearby_locations(qs, lat, lng, radius_m)` (PostGIS `ST_DWithin` / SQLite bbox) — **no FK on `Location`, no migration, no background job**.

Places page: **suggested-places list** + card grid (point count + last-seen) + two MapLibre modals (create/edit; detail with stats, cities covered, autosaving notes). Endpoints (all `@login_required`, ownership-scoped):
- `GET/POST /api/places/` — list / create
- `GET /api/places/suggestions/` — recurring stays not yet named (registered **before** the `<int:place_id>` routes)
- `POST /api/places/suggestions/dismiss/` — reject a suggestion
- `GET /api/places/<id>/` — aggregate stats (`_compute_place_detail`). Kept **lightweight** so the detail modal opens fast on a huge place: cities via a DB `GROUP BY`, per-day counts + dwell time from a **timestamps-only** ordered scan (one narrow column). It **no longer returns a map point sample** — those stream separately (below).
- `GET /api/places/<id>/points/` — `place_points_api`, a `StreamingHttpResponse` of newline-delimited JSON coordinate chunks (`[[lng,lat],…]` per line). One ordered scan decimated to ~3000 points (stride from the total count); yields 400-point chunks as read so the detail map fills in progressively. `X-Accel-Buffering: no` so nginx doesn't buffer the stream.
- `POST /api/places/<id>/update/`, `POST /api/places/<id>/delete/`

**Detail modal load order (`openDetail` in `places.html`).** Circle + map zoom + name + autosaving notes paint **instantly from the cached place geometry** (`placesCache` already carries lat/lng/radius_m/color/notes) — no server wait. The aggregate `GET /api/places/<id>/` fills the stats/days/cities a moment later. Map points stream in via `streamDetailPoints` reading `/points/` progressively (`detailPtsToken` cancels a prior place's still-running stream so it can't paint into the current one).

**Place suggestions.** Surfaces recurring stays the user hasn't named, so Places stops being purely manual. `place_suggestions_api` clusters **`Visit` rows** (the existing dwell detection in `visit_tasks.py`) — not raw points — via `_cluster_visits`, a grid-indexed greedy merge at `_SUGGEST_RADIUS_M` (150m, matching the radius the Visit worker already used, so repeat stays at one spot collapse into one candidate). A cluster is offered only at `_SUGGEST_MIN_VISITS` (3) **and** `_SUGGEST_MIN_HOURS` (1.0), which filters out one-off stops and traffic jams.

**Suggestions are computed on the fly and never stored, and there is deliberately no `confirmed` state.** Confirming opens the existing create modal prefilled (centre + matched POI name + radius); *saving the CustomPlace* is what retires the suggestion, because clusters falling inside an existing place's radius are filtered out — the place itself is the confirmation. So the only state worth persisting is rejection: `DismissedSuggestion` (migration `0041`, user + lat/lon). **Rejecting means "don't offer this as a place", not "this stay didn't happen"** — the `Visit` rows are untouched, so Stats/Search/AI are unaffected.

Cached under a plain `suggestions:{user_id}` key (30m TTL, **not** gen-keyed — visits accrue slowly and the clustering is a whole-history pass). All three `CustomPlace` mutations `cache.delete` that key, since creating/moving/deleting a place changes which clusters it covers. Unlike the other Places endpoints, `place_suggestion_dismiss_api` is **not** `@csrf_exempt` — the template sends `X-CSRFToken` instead.

Clicking a suggestion row expands an **inline mini-map** (accordion — one row at a time). A **single** MapLibre instance (`miniHost`, created detached) is *moved into* whichever `.sg-mini` slot is open rather than one map per row, since a long queue would otherwise hold a dozen live GL contexts; `paintMini()` re-centres it and is called both on expand and on the map's `load` (whichever lands second). `renderSuggestions()` detaches `miniHost` before replacing rows, so a re-render can't destroy the shared map with the DOM it was sitting in.

Every mutation calls `_bust_user_cache`. Custom places also appear in:
- **Data table** — `locations_api` resolves via `_place_membership` (bbox+haversine), sets `custom_place`; template prefers it over `poi_name`, renders in coral.
- **Search** — `search_api` matches `CustomPlace.name__icontains`, prepends results above OSM POIs.
- **Map layer** — optional "my places" toggle, persisted in `roamly_show_places`. Draws two things: the radius **circles** as GL layers (`myplaces-fill`/`myplaces-line`), and the **name tags** as DOM `maplibregl.Marker`s (`.place-tag` — a bordered plate in the place's colour with a wedge tail whose tip sits on the exact centre). Tags are markers rather than a `symbol` layer because the design fonts have no SDF glyph PBFs, so a symbol layer could only ever render the stock demotiles font — and being outside the style, markers also survive basemap swaps untouched. Only the circles need re-adding after a style swap: `addPlacesLayers` is idempotent and guards internally, called from both `style.load` **and `styledata`** — `isStyleLoaded()` can still be false at the instant `style.load` fires and `style.load` never fires again, which is why the layer used to go missing at random.

## Map rendering

Two modes selected by `roamly_map_renderer`:
- **Vector tile mode** (PostGIS only): `/api/tiles/<z>/<x>/<y>.pbf`
- **Classic mode** (SQLite/fallback): GeoJSON from `/api/track/`, decimated to configurable point limit

Detail points load progressively via `/api/locations/` as user pans/zooms (viewport bbox). Accumulate in client-side `accMap` (deduped by `"deviceId:timestamp"`).

Adventure map loads from `/api/trips/<id>/` (capped 30k). Under 20k: all dots immediately; over 20k: heatmap-first, dots on zoom.

**Basemaps (`map.html`).** Selected by the sidebar "basemap" buttons, persisted in `roamly_map_tile_style` (per-device UI choice, localStorage). Built-in free basemaps (always available): `Streets` (CARTO light), `Dark` (CARTO dark), `Satellite` (Esri). **Optional Mapbox basemaps** appear only when the user has a public Mapbox token (`pk.…`) set in Settings → Main Map Settings: `Mapbox Streets`/`Mapbox Outdoors`/`Mapbox Satellite`, built via `_mapboxRasterStyle` from Mapbox raster-tile URLs (style-8 raster source, same pattern as the built-ins), with matching buttons injected into the basemap group at load. If a saved Mapbox style becomes unavailable (token removed), the map falls back to `Streets`. Purely additive — no built-in basemap was removed.

The basemap buttons live in a **3-column grid** (`.sidebar-btn-group`) so the extra Mapbox buttons wrap onto their own rows instead of squishing. A `map.on('error')` handler surfaces Mapbox tile auth failures (a correct token returns tiles; a 401/403 means an invalid token or URL restrictions) to `map-info` + the console, so a blank Mapbox basemap is never a silent mystery.

**Mapbox token is stored server-side** on `UserProfile.mapbox_token` (migration `0039`) so it syncs across every device the user logs in from — web *and* the mobile app. It's a public/client-side token by design, so it is **not masked**. Get/set via `GET/POST /api/profile/mapbox-token/` (`profile_mapbox_token_api`, login-required). The `custom_js_snippet` context processor exposes it to templates as `MAPBOX_TOKEN`; `map.html` reads it inline (`const _mapboxToken = '{{ MAPBOX_TOKEN|escapejs }}'`) and `settings.html` renders the field from it + POSTs changes. **New `UserProfile` field ⇒ build + migrate.**

**Mobile basemap selector.** Lives in the map-options sheet (below), listing `Streets` (OSM MAPNIK), `Satellite` (Esri), `Dark` (CARTO) plus `Mapbox Streets`/`Outdoors`/`Satellite` **when a token is present**. `basemapTileSource(name, token)` maps each label to an osmdroid `OnlineTileSourceBase` (Mapbox/Esri use custom `getTileURLString`; Esri is z/y/x order; CARTO is plain XYZ). Selection persists in `UserPreferences.mapBasemap` (per device) and is applied by a `LaunchedEffect` keyed on `basemap` + `mapboxToken`. The token is read-only on mobile (`RoamlyApi.getMapboxToken` → cached in `UserPreferences.mapboxToken`, refreshed on `MapViewModel` init) — it's only ever set on the web. osmdroid's built-in zoom buttons are hidden (`zoomController` visibility `NEVER`) in favour of the custom side FABs. **Mobile change ⇒ rebuild APK.**

**Map tools (`map.html` only):**
- **Globe** — `map.setProjection({type:'globe'|'mercator'})`. Requires **MapLibre GL v5** (globally in `base.html`, v5.24.0). Persists in `roamly_globe`; re-applied on `style.load`.
- **Scratch** — highlights visited countries, with the US broken out to state-level detail. `/api/countries/` returns visited `country_code`s (uppercase ISO-2) plus a `states` list (full names, matching TIGER `STATE_NAME`/GeoNames formatting, e.g. "California"). Client fills `tracker/static/tracker/data/world-countries.json` (Natural Earth 110m, ~170KB) for every visited country **except** `US` — that one's whole-country polygon is deliberately excluded from the fill so it doesn't paint a flat blob underneath the per-state layer — and separately fills `tracker/static/tracker/data/us-states.json` (PublicaMundi US states, 50 + DC + Puerto Rico, ~90KB, joined on `properties.name`) for whichever states are in the visited list. Same styling (`#d0694a`, two layers each: fill + line) for both. **New static files need `collectstatic` — `--build` runs it on container start.** `tracker/static/tracker/map-core.js` is the app's only `{% static %}`-loaded application script (`sw.js` is served by a view instead), and it is what both `/map/` and `/editor/` render from — a deploy that skips `collectstatic` breaks both pages, not just a font.
- **Fog of War** — dims everywhere the user has never been. **Always all-time, never date-filtered** (explored territory stays explored), so it can't be fed by the map's own points — those are viewport- and date-scoped. `GET /api/fog/` (`fog_api`) returns the DISTINCT ~110m grid cells (`_FOG_CELLS_PER_DEG` = 1000, i.e. lat/lon rounded to 3dp) over the user's whole history, as a flat `[gy, gx, …]` int array. **Deliberately not keyed on `cache_gen`** — every push bumps the gen and a full-history DISTINCT is far too expensive to redo per push, so it uses a plain `fog:{user_id}` key with a 1h TTL (same reasoning as `StatsSnapshot`). Client renders a 2D `#fog-canvas` over the map (**not** a MapLibre layer — a world polygon with tens of thousands of holes can't be tessellated) and punches holes with `destination-out` at `FOG_REVEAL_M` (200m) per cell, `FOG_ALPHA` 0.75. Redrawn on `map.on('render')` to stay glued during pan/zoom. Cells are bucketed by whole degree (`fogBucketsInView`) and the frame scans whichever is smaller — viewport buckets or the whole index — since at world zoom the viewport spans ~65k buckets. **Fog and Globe are mutually exclusive** (a flat mask can't wrap a sphere); each toggle turns the other off. Persists in `roamly_fog`.
- **Snapped view** — the sidebar's `snapped view` toggle (`roamly_snap_roads`, default on, rendered only when `ROAD_SNAP_ENABLED`). **Display-only and browser-only**: it decides whether the detail layer paints points at their snapped road positions, nothing more. It was called `snap to roads` — the same words as the account-wide master switch in Settings (`UserProfile.snap_to_roads`) — and two controls sharing one name is precisely why people flipped the sidebar button, saw nothing change, and concluded snapping was broken while the real switch sat off. The button carries a `title` saying which is which, and `loadTripLines`'s map-info note now names the control that fixes each case (`roads: off (Settings → Road Snapping)` / `roads: no data (ask an admin to download road data)`) rather than a bare `roads: off`.
- **Hide outliers** — a `hide outliers` sidebar toggle (`roamly_hide_suspect`, **default on**) drops `flag='suspect'` points from both dot layers, from `buildLinesFC` (skipped entirely, so the line runs from the point before straight to the point after rather than spiking out and back), and from `renderTrack`'s auto-fit bbox — one stray fix could otherwise rescale the whole map. `setHideSuspect()`/`suspectCount()` live in `map-core.js`; the button + badge are wired in `map.html`. **Both** dot layers must carry the filter for the same reason snapping does: the decimated track and the detail accumulation draw the same fix above `DETAIL_MIN_ZOOM`. `track_api` had to start **returning** `flag` for any of this to work — it was selected and carried, then dropped from the final projection, which quietly made the pre-existing red-suspect styling dead code. Purely a display filter: the rows are untouched, and `_gated_distance_segments` already gave them no credit, so **no number anywhere changes**.
- **Replay** — animates one day's track. Fetches from `/api/locations/` (`all=1`), builds per-device sorted arrays, draws growing trail + head dot via `requestAnimationFrame` (60s at 1×). Base layers hidden while replaying.

**Trip Lines mode (`map.html` only, gated by `ROAMLY_MAP_CFG.tripLinesEnabled` — absent on `/editor/`, which keeps the old accumulated-layer `buildLinesFC` behaviour untouched).** A Google-Timeline-style alternative to the point cloud, toggled by the same `roamly_connect_lines` preference (Settings → Main Map Settings → **Trip Lines Mode**; reload required, like the other load-time map prefs) — when on, `loadCurrentMode()` calls `loadTripLines()` instead of `loadTrack()` and **replaces** the decimated track + viewport-driven detail layers entirely rather than overlaying on top of them; `maybeLoadViewport()` no-ops in this mode since the server already returns the whole filtered range in one shot. Two ideas, both reusing existing machinery instead of new detection:

- **Dwell blobs** are stops, detected **on the fly by `_detect_dwells` from the same point stream the lines use** — deliberately **not** read from the `Visit` table. That was the original design and it was wrong: `Visit` is only populated by `visit_tasks._visit_worker`, a background job triggered off the geocoding tail, so on an instance where it has never run the table is simply empty and the layer silently drew nothing (the bug as first shipped — a real database with 368k locations had *zero* `Visit` rows, every one still `processed_for_visits=False`). **A map layer must not depend on an unrelated background job having been run.** A blob's **radius** is how far its own points actually scattered from the centroid (90th percentile of haversine distance — resistant to one stray fix ballooning a tight stay — floored at `_DWELL_MIN_RADIUS_M` 12m). Labels come from the point's `poi__name` → `place_name` → `city`. Togglable independently via **Dwell Blobs** in Settings (`roamly_dwell_blobs`, default on) — off draws transit lines straight through the dwell windows instead of circles.

**Dwell sensitivity is user-configurable** (Settings → Main Map Settings, three dropdowns), because the original hardcoded parameters (mirrored exactly from `visit_tasks`: 150m running-centroid radius, 5-minute minimum, matching a Visits-page row) threw a blob at nearly every red light and parking lot on an active day — accurate to what `visit_tasks` calls a "visit," but far too trigger-happy for a map layer meant to highlight *meaningful* stops. `_detect_dwells(points, cluster_radius_m, min_duration_s, min_points)` takes all three as parameters (module constants remain the defaults for direct/internal callers); `trip_lines_api` parses `dwell_min_minutes`/`dwell_min_points`/`dwell_radius_m` off the querystring, clamped server-side (1–180 min, 0–5000 points, 20–1000m) since they ride in from the client. `roamly_dwell_min_minutes` (default **30 min**, options 5/15/30/60) and `roamly_dwell_radius_m` (default 150m, options 150/250/400) raise the bars a stock install ships with; `roamly_dwell_min_points` (default **0 = off**) is a second, *independent* gate — a stay can clear the duration bar on a sparse track (a device that only pings every few minutes) yet still not be worth a blob, which point count catches and duration alone can't. Both the duration and point-count bars must clear for a cluster to become a dwell.
- **Transit lines** are every point *not* covered by a detected dwell. `_build_line_segments` walks each device's points in order, breaking into a new run whenever it crosses a dwell window (the track stopped there, even briefly) or a gap exceeds the **Line Gap Threshold** setting (`gap_minutes` query param). Each run is optionally run through the *existing* `roads.snap_points()` — the same function `/api/roads/snap/` uses for point-mode's "snap to roads" toggle, gated the same way on `UserProfile.snap_to_roads`. The run (snapped where eligible, raw where not) is then decimated by `_line_gate_points`: keep a point only once it clears a distance gate from the last *kept* vertex (accuracy-scaled for raw fixes, a small fixed floor for already-snapped ones) and reject any hop faster than a GPS teleport — the same two ideas `_gated_distance_segments` (below) uses for distance accumulation, just keeping coordinates instead of summing metres. Suspect-flagged and >100m-accuracy fixes are dropped outright, same bar as distance. `_line_gate_points` returns `{lng,lat,id,snapped}` vertices rather than bare coordinates, because the next step needs both.

**Snapping alone does not make a line follow a road**, and this was the feature's first real bug: `snap_points` moves each *fix* onto the nearest road but inserts nothing *between* consecutive fixes, so a car sampled every 30s (~400m apart at speed) drew a straight chord across every bend — on the road, not following it. **`_densify_along_roads`** is what produces the curvature: for each consecutive pair of vertices where **both** ends snapped, it asks `roads.route_between()` (the same A*/Directions/OSRM call the editor's "connect via roads" uses, dispatched by `road_provider_resolved`) for the real path and splices in its intermediate shape points. Requiring both ends snapped is the load-bearing guard — it proves both anchors sit on the network, so the result is a real road path rather than one invented from a fix that was never near a road. Three more guards: legs shorter than `_LINE_DENSIFY_MIN_M` (40m) keep the chord (visually identical, and routing every 8m gate-step would be thousands of calls), legs longer than `_LINE_DENSIFY_MAX_M` (3km) are recording holes a route would fabricate a path across, and a returned route longer than `_LINE_DENSIFY_MAX_DETOUR` (2.5×) the direct line is a bad match (wrong carriageway, a loop around a block) and loses to the chord — a confidently wrong road reads far worse than a slightly flat bend. `_LINE_MAX_ROUTE_CALLS` (200) is a **shared per-request** budget (a one-element list threaded through `_build_line_segments`) so one huge range can't fire thousands of A* searches; legs cache 30 days on `lineroute:{version}:{provider}:{id_a}:{id_b}` (both fixes and the road between them are immutable), storing `[]` as a "no usable route" sentinel so a failed pair isn't retried on every pan. Segments carry `routed: true` when any leg was densified.

The response also reports **`snap_enabled`** + **`snap_provider`**, which `loadTripLines` renders into the map-info line (`roads: off` / `roads: no provider` / `roads: local · N routed`). Without it, the master toggle being off, no road data being downloaded, and snapping being genuinely broken are all indistinguishable from "the lines look straight".

**`UserProfile.snap_to_roads` defaults to `True`** (migration `0071`, which also flips every pre-existing profile). It used to default to `False`, which meant the single master switch for the entire snap pipeline — point-mode snapping *and* Trip Lines' `_densify_along_roads` curvature — was silently off for every account ever created, with the only way to find it being a checkbox under a provider dropdown in Settings. Defaulting it on is safe precisely because **`road_provider_resolved` is the real gate**: an account with no downloaded roads, no Mapbox token and no OSRM URL resolves to `''`, every consumer no-ops, and nothing changes — and the moment a provider *does* become available (an admin runs the road download, a token gets added) snapping starts by itself with no second opt-in. That is the "auto-enable once a provider resolves" behaviour, achieved without a polling job or a tri-state field: the flag is on, the provider is what varies.

**Settings → Road Snapping card layout.** The card leads with the master switch (`.road-master`, a bordered `--primary` plate) rather than burying it under the provider dropdown, and that checkbox **autosaves** (`onSnapMasterChange()`) instead of needing a separate Save press — a checkbox that looks set once ticked but isn't saved is most of why the feature went unnoticed. Provider/OSRM config moved into a collapsed `<details class="road-advanced">` block with its own "Save provider" button, since `Auto` is right for essentially everyone. `_roadsResolvedNote()` now reports the **switch and the provider together** ("On, using your downloaded OSM roads — 261,043 roads stored" / "On, but no road data is available yet…" / "Off — …"), because snapping being *on* is not the same as snapping *working* and a ticked box alone would imply curves should be appearing.

**Trip Lines prerequisite popup (`settings.html` only).** The map-info line above is diagnostic, read only by someone already looking at `/map/` — turning **Trip Lines Mode** on in Settings is the point where a user should be told road-following has its own setup, not left to notice its absence later. `onTripLinesModeChange()` (replacing the plain `savePref` the `#connect-lines` select used to call directly) fetches the same `GET /api/profile/roads-config/` the Road Snapping card itself reads, and shows `#trip-lines-prereq-modal` only when there is something to fix (`!resolved || !snap_to_roads` — nothing pops up for a user who already has this configured). The modal is a checklist, not a single message, because the two prerequisites are independent and each needs its own fix: **"Snap points to roads"** (`tripLinesFixEnableSnap()` — flips the checkbox and POSTs the existing roads-config payload directly, no navigation needed) and **"Road data source"**, whose fix depends on what's actually missing — `has_postgis` and no local roads offers **"Download now"** (`tripLinesFixDownloadRoads()`, which closes the modal, scrolls to the Background Jobs card, and calls the *existing* `startRoads()` so the real progress bar takes over rather than a second one living in the modal); no PostGIS (so `local` can never resolve) offers **"Add Mapbox token"** instead, scrolling to and focusing that field for the user to fill in — that step can't be automated. Each fix action re-fetches and re-renders the checklist in place (`_refreshTripLinesPrereqList`) rather than closing the modal, so fixing one item while the other is still pending is visible immediately. Pure template change — no rebuild/migration.

Endpoints: `GET /api/track/lines/` (`trip_lines_api`) takes the same filter params as `/api/track/` plus `gap_minutes`, Redis-cached like `track_api` (`tripline:{user}:{cache_gen}:{querystring}`); returns `{devices:[{id,name,segments:[{coords,snapped,routed}],dwells:[…]}], snap_enabled, snap_provider}`. `GET /api/dwell/points/` (`dwell_points_api`) returns one blob's raw points (capped 3000, strided if denser) — deliberately **un-gated**, since expanding a blob is supposed to show the real jittery point cloud it summarizes, not a cleaned-up version. It's keyed by **`device_id` + `start`/`end` epoch seconds, not a row id**, because dwells are computed per request and never stored; ownership is enforced via the device lookup and the window is clamped to `_DWELL_WINDOW_MAX_S` (7d) so it can't be turned into an unbounded point dump.

Client rendering (`map-core.js`): `renderTripLines()` builds one `LineString`-per-segment source (`trip-lines-src`) and, if dwell blobs are on, one `Point`-per-visit source (`trip-dwells-src`) — replacing both on every call via `clearTripLineLayers()`, called from both `loadTripLines()`'s response handler and the basemap-swap `styledata` handler (re-rendering from the cached `tripLineData`, mirroring how `renderTrack(lastTrackData, false)` does it for points mode).

**Dwell blob sizing** is the one place on the map where a circle scales to a real-world metre radius *with* a pixel floor, and getting it wrong is what made blobs never appear at all in the first cut. MapLibre requires `["zoom"]` to be the input of a **top-level** `step`/`interpolate`; the original expression wrapped that interpolate in `["max", DWELL_MIN_PX, …]` to apply the floor, which makes `addLayer` **throw** — so the whole dwell layer was silently never created while the (zoom-expression-free) line layer rendered fine. The floor is therefore baked into **per-feature stop values** instead: `dwellFeature()` precomputes `px_z0…px_z20` at every other zoom (`DWELL_ZOOM_STOPS`, from the same `156543.03392 * cos(lat)` Web Mercator constant `map.html`'s fog-of-war canvas overlay uses), each already `Math.max(DWELL_MIN_PX, …)`-ed, and `dwellRadiusExpr()` emits a top-level `['interpolate', ['exponential', 2], ['zoom'], …]` over them. Below the crossover both ends of an interval are the floor so it interpolates flat; above it they're exact powers of two so base-2 exponential interpolation reproduces the true curve **exactly**. Only the single interval straddling the crossover is approximate, by under 1.6px for realistic stay sizes. (Both claims are checked against `@maplibre/maplibre-gl-style-spec`'s `createPropertyExpression`, which is also the fastest way to validate any future paint-expression change without a browser — note its signature is `(expr, rootKey, propertySpec)`.)

**Click a dwell blob to expand it** into its raw point cloud (`onDwellClick`) — toggles `expandedDwellId`, fetches `/api/dwell/<id>/points/`, and draws the un-gated points + a thin connecting line (`trip-dwell-expand-src`, device-coloured) so a "squiggly blob" is visible on demand rather than always drawn. The click/hover listeners on `trip-dwells-layer` are registered **once, unconditionally** (guarded only by `TRIP_LINES_ENABLED`, not by the current mode) rather than inside `renderTripLines` — MapLibre's delegated layer listeners don't dedupe, so re-registering on every render would stack a firing per past render (an existing latent pattern in `renderTrack`'s own per-device click handlers, not replicated here). A response is discarded if `expandedDwellId` no longer matches the visit it was fetched for, so clicking a second blob — or the same one twice — while a fetch is in flight can't paint a stale result.

## Migration notes

`Adventure` renamed from `Trip` in migration `0002_rename_trip_to_adventure`. FK fields renamed in `0010_rename_trip_fk_to_adventure`. Both depend on `0009_trip_creator_trip_public_slug_tripblurb_and_more`.

When adding models or fields, create and commit the migration file — `tracker/migrations/` is volume-mounted.

**Transport mode detection** (`tracker/transport_tasks.py`, `TransportJob`, migration `0040`, manually run from Settings → Background Jobs). Labels every point with how the user was moving, on `Location.transport_mode` (`''` = unclassified). Modes are **`still` / `walk` / `cycle` / `vehicle` / `plane`** — deliberately **no car/train split**, their speed profiles overlap too much to call reliably.

**Classifies journeys, not points.** A single fix's speed lies (a car at a red light reads 0 m/s), so `_split_journeys` cuts each device's track into runs of movement bounded by stops longer than `_STOP_GAP_S` (180s) — short stops stay *inside* the journey — and never bridges a track gap over `_MAX_BRIDGE_S` (900s). `_classify` scores each journey from its **85th-percentile** speed (not max — one bad fix shouldn't promote a walk to a flight) plus the median as a guard, against `_WALK_MAX_MPS`/`_CYCLE_MAX_MPS`/`_VEHICLE_MAX_MPS`. Every point in the journey gets the journey's mode; **points outside any journey are labelled `still`**, which keeps the whole history classified and makes re-runs idempotent rather than leaving stale modes behind.

Speed comes from `Location.speed` (Doppler — trustworthy even when the position estimate wanders, the same property `DriftAnchor` leans on), falling back to speed derived from consecutive fixes for imported history (CSV/GPX/Takeout), which has no Doppler. The worker paginates on **`(timestamp, id)`, never `id` alone** — imported points get ids in file order, which need not match time order, so an id cursor would silently skip points. The trailing journey of each chunk is carried into the next rather than classified half-scored. Endpoints: `/api/transport/detect/{,status/,stop/}` + `GET /api/transport/breakdown/` (`transport_breakdown_api` — distance/hours per mode, reusing `_gated_distance_segments` per same-mode run so totals agree with `distance_api` instead of being a second, rawer estimate). Surfaced as the **How You Travelled** card on Stats (`still` excluded from the bars — it's most of the points and isn't travelling). Does **not** auto-run. **New model + field ⇒ build + migrate.**

**Road snapping** (migration `0049`). GPS scatter puts recorded points beside the road, or alternating across it. Snapping draws them where they belong — **display-only**: `Location.latitude/longitude` are **never** rewritten, the recorded fix is the record.

`POST /api/roads/snap/` takes **only point ids** (the server reads coordinates back from the DB: enforces ownership, stops a caller seeding the cache with invented coordinates, and guarantees the timestamp ordering the smoother needs) and returns `{id: [lng,lat]}`.

**Only road journeys are snapped** (`roads.snappable`): `transport_mode` in `vehicle`/`cycle` snaps, `walk`/`still`/`plane` never, and an unlabelled point (the common case — the detection job is manual, so everything recorded since the last run is `''`) falls back to the **median speed of its ±3 time neighbours** against `_SNAP_MIN_SPEED_MPS` (5 m/s). A *raw* per-point threshold is unusable: a stationary phone reports Doppler spikes over 30 m/s, so isolated readings say nothing — and journey-level `transport_mode` additionally keeps a car snapped while it waits at a red light. This matters because `HIGHWAY_RE` stores **no pedestrian geometry**, so the nearest candidate for a fix on a trail or in a garden is always a *road*; without the gate, walking a property got dragged onto it. Tolerances are correspondingly tight (`_SNAP_MIN_MAX_M` 20m, `_SNAP_ACC_MULT` 1.5, `_SNAP_HARD_MAX_M` 60m).

**`plane` is excluded outright, but `transport_tasks` deliberately never splits car from train or ferry** ("their speed profiles overlap too much to call reliably") — both land on `vehicle`, and without a further check would be exactly as snappable as an actual car. Since `RoadSegment` (and every external provider's driving profile) only knows about roads, a train running near one gets dragged onto it — the trace reads as "you drove 250 km/h down this street." `_SNAP_MAX_PLAUSIBLE_ROAD_MPS` (45 m/s / ~162 km/h) is the fix: above virtually every real-world road speed limit (including realistic unrestricted-autobahn cruising), while ordinary and high-speed trains cruise well past it, so a **sustained** speed above it is a reliable rail signal even for an explicitly `vehicle`-labelled stretch — checked against the same median-neighbour window as the unlabelled fallback, so one Doppler spike can't trip it. This deliberately does **not** attempt to catch a slower train or a ferry (both stay within ordinary road speeds and are genuinely indistinguishable from a car by speed alone) — it only stops the single most visually wrong case. The unlabelled fallback also gained this as an upper bound, where previously it had none.

Results are cached per point id (`snap:v2:{provider}:{id}`, 30d — a fix and the road beside it are both immutable; the version segment invalidates decisions made under older rules), with a falsy sentinel for unsnappable points. **Gate rejections are deliberately not cached** — the gate reads neighbours, so a point at the edge of one viewport batch sees fewer than it will in another, and caching a rejection could pin a driving point unsnapped for the whole TTL. Snapped coordinates live only in the cache, never in the database, so they are never in a backup.

Snapping is resolved **before either layer paints** (`loadTrack` and `loadViewport` both await `fetchSnapsForIds`) and memoised in a page-lived `snapCache`: painting at recorded coordinates and correcting a moment later made every dot visibly jump on load and again on each pan. **Both** point layers snap from one cache — the decimated `/api/track/` dots and the detail `accMap` dots share `minzoom: DETAIL_MIN_ZOOM`, so above that zoom they draw the same fix twice, and snapping only one turned each point into two side by side. Snapped points carry a mauve halo ring (`acc-pts-snap-ring`, a separate layer because MapLibre can't dash a circle stroke) and the popup says the recorded position is unchanged.

**Three interchangeable providers** in `tracker/roads.py` — `snap_points(profile, pts)` and `route_between(profile, a, b, mode)`, dispatching on `UserProfile.road_provider` (`''`=auto → **local → mapbox → osrm**, via `road_provider_resolved`):
- **`local`** (default when road data exists) — roads in the `RoadSegment` table, no external calls at query time. PostGIS-only. Snapping is a **LATERAL KNN `<->` probe** followed by a **Viterbi pass**: nearest-road-per-point alone ping-pongs between a motorway and its frontage road, so emission cost = distance and transition cost = `_SNAP_SWITCH_PENALTY_M` (40m) for changing way. Points with no road inside `max(20m, 1.5×accuracy)` are **left where they were recorded**. Routing is **A\*** over a graph whose vertices are keyed on the **coordinate itself** (`_vkey`): connected OSM ways share a node and therefore an identical position, so a coordinate touched by two ways *is* an intersection. `RoadSegment.node_ids` is vestigial and left empty — keying on node ids is what originally broke routing outright, since Overpass returns incomplete geometry for ways clipped at a query-box edge and every such way was silently dropped. Routes are **road-only end to end**: each anchor is spliced into the *nearest edge* at its projection point (`_splice_anchor`) and the raw GPS anchors are excluded, because otherwise the route could only begin at a junction and opened with a straight off-road leg. `_nearest_edge` consults an **edge spatial index** (`_index_edge`/`_ecell`, ~1.1km buckets, ~45× faster than scanning every edge), and `_load_graph` memoises one graph keyed on bbox containment. **`_splice_anchor` mutates the graph it is handed**, so every touched vertex is recorded and `_unsplice` restores it in a `finally` — a leftover anchor in a cached graph would let one route wander through a previous one's anchors.
- **`mapbox`** — Map Matching + Directions using the existing `UserProfile.mapbox_token` (100 coords/request cap).
- **`osrm`** — `/match/v1` + `/route/v1` against `UserProfile.osrm_url`. A non-`driving` profile that 400s retries as `driving`.

**Valhalla was removed** (migration `0072`), having been added only two commits earlier in `0070`. It was a whole second service to run — the official `ghcr.io/valhalla/valhalla-scripted` image, a `docker-compose.yml` entry, a Geofabrik `.osm.pbf` tile build per region, a `data/valhalla` volume, a `VALHALLA_TILE_URLS` env var, a manual `docker compose restart valhalla` to apply a new region, plus `valhalla_tiles_tasks.py`, an `auto_download_tasks` hook, `SiteConfig.auto_download_valhalla_tiles`, a `DownloadedRegion` kind, and an Admin Panel → Downloads card — in exchange for map matching the app already had two answers for. The **local** provider (`RoadSegment` + A\*, 260k+ ways downloaded on this instance) produces the same road-following curvature with no extra service, and **OSRM** covers the one thing Valhalla's Meili was actually claimed to be better at (a proper HMM matcher for dense parallel-road grids) with a public demo server and a far simpler self-host story. Removing it also fixed a live bug it introduced: `valhalla_url` defaulted to `http://valhalla:8002` (and `0070` backfilled that onto every existing profile), so `road_provider_resolved`'s auto chain ended `if self.valhalla_url: return 'valhalla'` and **never returned `''`** — every account with no local roads and no Mapbox token silently "resolved" to a service that mostly wasn't running. That empty-string return is the gate every snap consumer checks, and it is what makes `snap_to_roads` safe to default on, so it has to be honest. Migration `0072` drops `UserProfile.valhalla_url` + `SiteConfig.auto_download_valhalla_tiles`, deletes `DownloadedRegion(kind='valhalla')` rows, and resets any profile that had explicitly picked `valhalla` back to auto (leaving the dead string would resolve to `''` and silently disable snapping for that account).

**`RoadSegment` is the largest table in the app**, so `tracker/road_download_tasks.py` keeps it small: the download area is derived from the ~2km cells the user actually travelled through — the cells containing fixes *and* the cells between consecutive fixes, rasterised with an integer DDA (`_line_cells`), skipping pairs that fail the same speed/distance rules routing applies so a flight can't rasterise a transcontinental line. Only drivable classes (**no `service`**, no footway/path/cycleway), `way_id` unique so overlapping areas dedupe. Merged runs are capped at `MAX_RUN_CELLS` (12, ~26km): corridor bridging makes long stretches of adjacent cells, and merging them wholesale produced single bboxes hundreds of kilometres wide, which is what timed Overpass out. Failures are **retried with backoff then bisected** and the unrecoverable count lands in `RoadDownloadJob.failed`, surfaced in red — a silently-empty corridor is indistinguishable from snapping being broken.

**Bisecting only helps when Overpass was reached and said no** (an `HTTPError` — rate-limited, 504 under load): a smaller query is genuinely less likely to hit the same limit, so `_download_boxes` retries then splits the batch in half, recursively. It does **not** help when the request never got out the door at all — DNS failure, connection refused, a TLS error, the whole thing timing out with no response — because every leaf of that same bisection tree hits the identical failure. A real instance hit exactly this: a 20-box batch under total connectivity loss triggered the full bisection tree (~78 requests, each up to `OVERPASS_TIMEOUT + 20` = 80s), so **one** unreachable batch could occupy a worker for close to two hours while `RoadDownloadJob.processed` sat at 0 looking frozen — and a "stop, then restart" did not help, because the still-running (bisecting) thread from before the stop kept burning through the same requests in the background, and the *new* thread hit the identical outage and got stuck the same way. Non-`HTTPError` exceptions are now caught separately: one retry for a possible blip, then the **whole batch** fails at once (no bisection) — collapsing that scenario from ~78 requests to 2. `_road_download_worker` also carries a `consecutive_unreachable` counter across batches; `CONNECTIVITY_FAIL_LIMIT` (2) consecutive whole-batch connectivity failures ends the run early with every remaining batch counted as failed, rather than rediscovering the same outage 82 times over. `_download_boxes` returns a third value, `unreachable`, threading this distinction through the bisection recursion (`lu and ru`) so a genuinely mixed outcome — some leaves reachable, some not — isn't misreported either way. Settings surfaces a whole-run failure specifically ("could not reach Overpass for any area") when `failed >= total`, rather than a bare count indistinguishable from one bad corridor.

**`OVERPASS_URL` is env-configurable** (`roamly/settings.py`, read once into the module-level constant in `road_download_tasks.py`; `rail_download_tasks.py` imports the same name, so one setting covers both roads and subway). The official instance enforces a fair-use policy and **will actively refuse connections** (TCP-level "connection refused" on every one of its IPs, not a timeout) from an IP it judges abusive — confirmed on a real instance whose IP had been hammered for hours by the pre-fix bisection storm above; `unreachable` correctly classifies a ban as a fast-fail case, so the symptom is now a clear "could not reach Overpass for any area" within a couple of batches rather than a hang, but the download still can't proceed until either the ban lifts or `OVERPASS_URL` points somewhere reachable. A public mirror (`overpass.kumi.systems`, `overpass.private.coffee`, etc.) is a same-day workaround; those aren't blocked but are shared community infrastructure and can be genuinely overloaded — their own dispatcher timing out is a real `HTTPError` 504, which correctly gets the retry-then-bisect treatment rather than the fast-fail path, since a smaller query against a busy-but-reachable server is worth another attempt.

The road/subway/POI/transport/stats progress bars in Settings previously prefixed their status text with `.spinner` (a `border-top-color` circle), which reads misaligned next to text — `inline-block` defaults to baseline vertical-align, so the spinner's centre sits below the text's. The road-download bar (`#roads-bar`) instead gets a `.bar-flow` class while active: a diagonally repeating gradient (`--primary`/`--primary-hover`) animated via `background-position`, applied to the bar's own fill rather than a separate icon next to the text, so there's no alignment to get wrong. Removed via `classList.remove('bar-flow')` (and the bar's inline `background` explicitly cleared first, since an inline style always wins over a class's `background-image` regardless of shorthand/longhand) once the run finishes, replaced by a flat `--success`/`--text-muted` fill. Respects `prefers-reduced-motion`. Pure template change — no rebuild/migration.

The run is owned by a **`RoadDownloadJob.worker_token`** (migration `0053`). `_running_threads` is per-process, so with several gunicorn workers the liveness check cannot see a thread running elsewhere: a status poll in another process concluded the run had died and started a second worker, each keeping its own progress counter and overwriting the other — the reported percentage climbed, then jumped backwards, then stalled. Every progress write is now conditional on the token, `_claim()` mints a fresh one on start (retiring any straggler), `stop` clears it, and the worker `return`s as soon as the row stops naming it. A `_beat()` callback touches `updated_at` between Overpass attempts **and during the history scan** so a slow-but-healthy phase is never mistaken for a dead one, and `STALE_AFTER_S` (240) is comfortably above the worst case for a single batch.

`_visited_boxes` scans **one device at a time** ordered by timestamp. A single global `order_by('device_id', 'timestamp')` cannot use `tracker_loc_device__idx` (which is `('device', '-timestamp')`), so Postgres full-sorted every row before yielding the first — the slowest thing the job does, running before any progress exists to report. The scan finishes before `total` is known, so the status endpoint reports `phase='scanning'` while `total` is still 0 and the UI says so explicitly rather than showing a frozen `0/0`. Geometry is stored **unsimplified**: a junction is recognised by its coordinate, and a simplifier can't know which vertices are shared. **Storage is roughly 5-9 KB/km²**. Road data is wiped from Settings → Background Jobs → **Delete Road Data** (`TRUNCATE`, instance-wide reference data with no user FK, like `POI`/`Boundary`).

**Map editor** (`/editor/`, `editor_view` → `editor.html`, migration `0052`). Replaces automatic gap filling, which was removed: a background job deciding on its own which holes to fill, and how, produced output that could not be trusted, and four rounds of tuning did not fix the premise. Everything is now deliberate, synchronous and undoable — no job row, no thread, no nightly sweep.

The page is `standalone: True` (no nav chrome) and gets its rendering from **`tracker/static/tracker/map-core.js`**, shared with `/map/`, so the two look identical by construction rather than imitation. Tools: **select** (click; Ctrl-click toggles; Shift-drag box-selects via `queryRenderedFeatures` with a bbox), **delete**, **connect via roads** (exactly 2 points → `roads.route_alternatives` offers up to 3 distinct routes to pick from → `editor_tasks.points_along` lays the chosen one down), **move/retime** one point, **add** a point at a typed time or a **run** from an anchor at a fixed interval, and **copy a stretch** onto another date.

**Connecting is a preview, not a commit.** For many gaps there is more than one plausible way round and only the person who drove it knows which, so `/api/editor/route/` returns up to three candidates (drawn in distinct colours, clickable on the map or in the sidebar) and `/api/editor/route/commit/` lays down the one chosen by index. Candidates are held in the cache for 15 minutes and committed by index rather than by geometry, so a client can never inject a path that was never offered. Local alternatives come from the **penalty method** (`_local_alternatives`): A\* returns the single cheapest path, so asking again yields the same answer — inflating the cost of the edges each route used by `_ALT_PENALTY` (4×) pushes the next search onto a genuinely different road, and near-duplicates are rejected at `_ALT_SIMILARITY` (0.75 shared vertices). OSRM and Mapbox just ask for `alternatives=true`.

**Editor routing uses a much wider anchor tolerance** than `_ROUTE_MAX_ANCHOR_M` (80m): `_EDITOR_ANCHOR_M` is 500m. That gate exists to stop a *background job* inventing a leg from a point nowhere near a road, but here a person picked both ends deliberately. With the tight gate, connecting only worked for points close enough to a road to have been snappable in the first place — which is why it appeared to depend on snapping. `_nearest_edge` takes a matching `reach` so the ~1.1km index cells are searched widely enough to find the road.

**Point spacing follows a speed gradient.** One point per `FILL_INTERVAL_S` (10s) of travel, positioned by assuming speed varies linearly between the two anchors' recorded Doppler values: `v(t) = v0 + (v1-v0)·t/T`, so `s(t) = v0·t + (v1-v0)·t²/(2T)` scaled to the route length. Points therefore bunch where the track was slow and stretch where it was fast, instead of sitting at even distances. With no usable speed at either end it degrades to even spacing. The old 60s spacing with a flat 500-point cap put 500 points on a two-minute hop; 10s spacing means a short connection gets a handful.

A time interval alone cannot bound density, though, so `MIN_POINT_SPACING_M` (25m) is a hard floor applied *while* laying points down: a long gap over a short distance means 10 seconds of travel is only a few metres, and 40 minutes over 2km produced 239 points 8m apart — a solid band, denser than any real tracking. Thinning happens as points are placed rather than afterwards, because under a speed ramp the spacing varies along the route and only a running check catches the slow end; dropping one never moves the others, since each kept point stays where its own timestamp puts it. That case now yields 80 points at 25m. `MAX_POINTS_PER_ROUTE` (500) remains as the outer ceiling.

**Editor-generated points render on `/map/` too**, behind a `filled gaps` sidebar toggle (`roamly_show_inferred`). They are drawn to read as *part of the track*: the same per-device colour and dot size as a recorded fix, plus a detached ring in a colour used nowhere else (`#4fc3d9` cyan — not in the device palette, and distinct from the mauve snapped-point ring), with a dashed connecting line that respects `roamly_connect_lines`. `addInferredLayers` is idempotent and wired to both `style.load` and `styledata`, and the layers join `baseLayerIds()` so replay hides them. `/api/inferred/` returns `device_id` per batch for exactly this colouring.

`tracker/editor_tasks.py` holds the operations. Output goes to **`InferredLocation`** by default — no aggregate reads that table, so distance, visits, stats, fog and backups are untouched by anything drawn. **"Count as real data"** (offered when pasting or adding) instead writes plain `Location` rows, which are already covered by the backup format, so **`meta.version` is unaffected**. Every action records an **`EditBatch`** so it can be undone as a unit; for a paste-as-real the created ids are stored in `EditBatch.location_ids`, which is how the undo works without adding a column to `Location`.

**The copy guard matters:** `Location.unique_together` is `(device, latitude, longitude, timestamp)`, so pasting onto a *different date* collides with nothing and inserts cleanly — silently producing two interleaved tracks that every aggregate double-counts. `editor_copy_preview_api` therefore reports conflicts up front and `editor_copy_api` refuses a non-empty destination unless `replace` is set (which trashes the originals first).

**The `bulk_create` trap:** `bulk_create`/`update`/`bulk_update` all bypass `Location.save()`, leaving the PostGIS `location` column NULL and the point invisible to every spatial query — already a production bug once. Every editor path that creates or moves a real point goes through `editor_tasks._make_location`, which sets `Point(lng, lat, srid=4326)` explicitly; `editor_move_api` uses `.save()` rather than `.update()` for the same reason.

**Trash** (`TrashedLocation`). Deleted **real** points are snapshotted in full before deletion and restorable from Diagnostics → **Trash**; generated points are hard-deleted, being regenerable. A full snapshot rather than a tombstone is necessary because a `Location` is the primary record and cannot be recomputed — unlike `DismissedSuggestion`, whose "restore" merely clears a marker. Restoring mints a **new** id (`original_id` is informational) and is idempotent, since the recreated row carries the original unique tuple. Purged after `log_cleanup_tasks.TRASH_RETENTION_DAYS` (30) by the **existing hourly log-cleanup sweep** — deliberately not a new daemon, having just removed one. `EditBatch`, `InferredLocation` and `TrashedLocation` are all operational/user-intent ⇒ **excluded from backups**.

**Subway gap filling** (migration `0064`, PostGIS-only, web-only). Subways have no GPS, so an underground ride leaves a hole in the track. This detects those gaps and fills them along the real subway line — including across transfers — as **real** `Location` rows, so the ride's distance counts. Built on the road-download + routing + editor machinery, three pieces:

- **Subway data** — `tracker/rail_download_tasks.py` (a sibling of `road_download_tasks.py`, reusing its `_visited_boxes` corridor-cell selection verbatim) downloads `railway=subway` running tracks (service tracks excluded) **and** subway station nodes from Overpass into **`RailSegment`** (way + LineString geom, GiST) and **`RailStation`** (station node + Point geom, GiST). Same worker-token/`_claim`/`_beat`/bisecting-retry mechanics as roads, tracked in **`RailDownloadJob`** (clones `RoadDownloadJob` + a `stations` counter). Instance-wide reference data, no user FK. `_subway_data_available()` + `SUBWAY_AVAILABLE_CACHE_KEY` mirror the roads gate. Settings → **Download Subway Data** card; endpoints `POST /api/subway/{download,download/stop,delete}/` + `GET /api/subway/download/status/`.

- **Transfer-aware routing** — `tracker/rails.py` reuses `roads.py`'s A\* (`_route_on`), anchor-splicing, edge index and geometry helpers wholesale. Rail-specific graph build (`_load_rail_graph`): a **dense** graph (every shape point a vertex — no junction-splitting, since interchanging lines are in separate tunnels sharing no node), uniform bidirectional edges (no highway weight / no oneway), and **transfer stitching** (`_stitch_transfers`) — each `RailStation` is joined to every track vertex within `_RAIL_STATION_LINK_M` (150m) through a synthetic hub node at a small transfer cost, so A\* can cross between lines at a shared station. Wide anchor tolerance (`_RAIL_ANCHOR_M` 500m, anchors are surface fixes). Public: `route_subway(a,b)`, `route_alternatives_subway(a,b,k=3)` (penalty method → the candidate lines). No Mapbox/OSRM rail profile exists — always local.

- **Detection + fill** — `tracker/subway_gap_tasks.detect_gaps(user)` scans each device's track (ordered `(timestamp, id)`) for consecutive fixes with a real time gap (`_GAP_MIN_S`..`_GAP_MAX_S`), a plausible jump (`_JUMP_MIN_M`..`_JUMP_MAX_M`), and above-walking implied speed, then surfaces the pair **only if `route_alternatives_subway` returns a route** whose length is within a sanity factor of the straight line — that routing test *is* the "only where a subway route is nearby between the two" guard, and it rejects ordinary above-ground travel that merely passes a station. Computed on the fly, cached `subway_gaps:{user_id}` (30 min, `?refresh=1` recomputes). `GET /api/subway/gaps/` returns each gap + its candidate routes; `POST /api/subway/gaps/fill/` commits the chosen route **by index** (client never sends geometry — same anti-injection guard as `editor_route_commit_api`) via `editor_tasks.points_along` + `create_batch(kind='subway', target='location')` (real rows, even-spaced by time — no speed ramp, the surface anchors are at walking speed); `POST /api/subway/gaps/dismiss/` records a **`DismissedSubwayGap`** (user + anchor coords, like `DismissedSuggestion`) so it stops resurfacing. Every fill is an undoable `EditBatch`; `GET /api/subway/fills/` lists them and `POST /api/subway/fills/<id>/delete/` reverses one via `editor_tasks.undo_batch` (points → Trash, gap resurfaces). UI: Diagnostics → **Subway Gaps** tab (MapLibre mini-map, gap list with per-gap line picker + Fill/Dismiss, plus a filled-routes history with Delete). All new tables (`RailSegment`/`RailStation` reference data, `DismissedSubwayGap` user intent) are **excluded from backups** — no `meta.version` bump. **New models ⇒ build + migrate.**

**POI matching** (`tracker/poi_match_tasks.py`, `POIMatchJob`, manually run from Settings → Background Jobs). Labels every GPS point with nearest named POI within 150m, stored on `Location.poi` FK (migration `0025`). In-memory degree-grid, one `UPDATE` per POI per 5k chunk. Requires POI table populated first. Endpoints: `/api/poi/match/{,status/,stop/}`. Does **not** auto-run.

`_journal_day_track` accepts `tz_offset` (browser `getTimezoneOffset()` minutes) to bind to user's local calendar midnight, not UTC.

**Quality review scan** (`_flag_suspicious_locations`, `flag_scan_api` `POST /api/diagnostics/flag-scan/`). Flags points with bad accuracy / impossible speed / altitude spikes / **isolated spikes** as `Location.flag='suspect'` (`flag_reason` is a comma-joined subset of `accuracy,speed,altitude,spike,jitter`).

The **`spike`** reason (`_is_spike`, thresholds `_FLAG_SPIKE_*`) is what catches the outlier that actually happens: a stationary phone emitting one fix a couple of km away. The absolute `_FLAG_MAX_SPEED_MPS` bar is ~720 km/h, which that sails under at ~66 m/s, and **lowering it is not an option** — 35 m/s would flag every motorway drive and every flight. What separates a glitch from fast travel is that the track *comes back*: `_is_spike` requires high implied speed **both into and out of** the point (15 m/s), over real displacement (200m each way), **with the two neighbours within 200m of each other**. A plane or a motorway never satisfies the return clause. This is why the scan keeps a **three-point sliding window** (`p0`/`p1`/`loc`) rather than just `prev_loc` — a point is only final once its successor has been read — while still streaming, since a whole history doesn't fit in memory.

The **`jitter`** reason (`_is_jitter`, thresholds `_FLAG_JITTER_*`) catches the *other* real outlier: a **stationary phone reporting a garbage high Doppler speed** (34–48 mph logged from a device that never left the house), with the position drifting only tens of metres. This defeats everything else — the mobile `DriftAnchor` assumes a parked phone reports ~0 Doppler (this chip reports the opposite, so the anchor never engages), the mobile speed-corrector doesn't always knock it down, and `_is_spike` can't see it because the point is *clustered* with its neighbours, not far from them. `_is_jitter` flags a point whose **own reported `Location.speed` ≥ 8 m/s** yet which sits **within 100m of both neighbours** *and* covered **under 40% of what `speed×dt` implies** on each side — physically impossible for real travel, which is always hundreds of metres from its neighbours at that speed. The absolute-distance gate keeps a lone mid-journey Doppler glitch (track still visibly moving through) from being flagged; only a genuinely clustered point qualifies. (Needs `Location.speed`, so it's added to the scan's `.only()`.) Non-destructive like every flag: the rows stay, `_gated_distance_segments` already gave them no distance credit, and the **hide-outliers** map toggle hides them — so raw points survive any future change of heart.

The scan **runs nightly**, piggybacked on `stats_tasks.compute_snapshot` (already per-user, already single-flighted by its advisory lock, trivial next to the stats work), bounded to the trailing `FLAG_SCAN_DAYS` (7); it's wrapped in its own `try` so a scan failure can't mark a good snapshot errored. The manual all-time run from Diagnostics is unchanged. Accepts an optional time window (`?start_date`+`?end_date`, `?hours=N`, or `?all=1`) parsed like `location_diagnostics_api`; when scoped, only points in the window are reset+rescanned so flags outside it survive. The Diagnostics → **Quality Review** tab has a range selector driving it (defaults to All time). `flagged_locations_api` still navigates flagged points by day/week.

**Settings jump-nav.** `settings.html` wraps its `.settings-grid` in a `.settings-layout` flex with a sticky left `.settings-nav` (desktop ≥960px). The nav is **built in JS** from each `.settings-grid > .card`'s `.card-header` text (first text node, so badges/icons don't leak in) — it auto-assigns card ids, smooth-scrolls on click, and highlights the in-view section via `IntersectionObserver`. Add a card and it appears in the nav automatically; no manual list to maintain.
