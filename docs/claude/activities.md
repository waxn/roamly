# Activity recording

_Read when: Recorded rides/walks/runs, ActivityTrack, smoothing pipeline._

**Activity recording (rides / walks / runs / rows).** A deliberately recorded activity is meant to come out the way a Strava track does: smooth, following curves, no outliers, and cheap enough to run for ten hours. The first design got none of that because it was a *mode of* the all-day capture loop — a 2s stream bolted onto machinery built for Doze survival (exact alarms, best-fix bursts, dwell points, a de-dup window, a 100 m accuracy gate, a pinned wake lock, an upload every minute), every piece of which either degrades a 1 Hz track or burns power a ride doesn't need. It was rebuilt (migration `0095`, Room v5) around three ideas: **record privately, upload once, smooth on the server.**

**Phone: a dedicated recorder (`tracking/ActivityRecorder.kt`).** While a session is live, `LocationTrackingService.applyCapture` **suspends the whole all-day loop** — stream, fix-cycle and catch-up alarms, dwell points, DriftAnchor, wake lock — and hands capture to the recorder; clearing the session hands it back through the normal path. All-day fixes would only interleave with the recording anyway. The recorder requests **1 Hz, HIGH, GNSS-only** (`FixRequest.gnssOnly`; the platform source otherwise arms GPS and NETWORK side by side, and a Wi-Fi fix every few seconds is exactly the zig-zag a ride must not have — fused ignores the flag). Battery comes from what Strava does: **the GNSS chip runs continuously (cheap) while the CPU sleeps** — screen-off the request carries a 20s `maxDelayMs` so the chip batches fixes and the CPU wakes once per batch; screen-on it delivers every second for the live screen. **No wake lock** (a foreground service with a batched request needs none), **batched Room writes** (in memory, flushed every 2s screen-on / 15s screen-off), **no network until Stop**, and the notification is refreshed at most every 10s. The 12-hour auto-stop and a screen-on stall re-arm live in the watchdog.

**`ActivityFilter` decides fix by fix, and never substitutes.** Accuracy worse than 30 m is dropped (relaxing to 50 m after a sustained poor-signal run, so a forest is recorded coarsely rather than not at all); duplicate/out-of-order times are dropped (batched delivery can repeat one); and a fix implying a speed the **sport** can't reach from the last accepted one is dropped, with accuracy slack, re-anchoring after 5 rejections in a row (the anchor was probably the bad fix). Per-sport ceilings / Kalman process noise / pause thresholds live in `ActivitySport` and mirror `SPORTS` in `tracker/activity_track.py`. **No dwell points, ever** — a missing fix is a gap. Rejections are tallied in memory and written to `CaptureStats` at flush, not per fix.

**Storage and upload.** Accepted fixes go to `activity_points` (`ActivityPoint`, `TrackingDatabase` **v4 → v5**, additive `MIGRATION_4_5` — the regression test is still: capture offline on the old APK, upgrade in place, confirm the backlog uploads). At Stop, `ActivitySaveWorker` waits for the recorder's final flush (count stable across checks — Stop and the service's flush race by design), posts the envelope with **`has_track`**, then sends the raw rows in **2000-row chunks** to `POST /api/activities/track/upload/`. Chunks are **idempotent by index**: a chunk the server holds comes back `duplicate` with `next_chunk` (the worker jumps there), one from the future gets a 409 (the worker retries from 0, which resumes). Local rows are deleted **only** when a response says `complete`; a 4xx keeps them. **Discard deletes the recorded rows** — all-day tracking was paused, so that stretch is genuinely gone, and the dialog says so.

**Live screen.** `RecordViewModel` reads `activity_points` by id cursor (`countFlow` trigger + `after(afterId)`, `conflate()` + `collect`, never `collectLatest` — the fold advances its cursor) through a forward **`KalmanFilter2D`**, accruing distance and moving time only while Doppler speed clears the sport's pause threshold. `RecordScreen` appends to **one persistent `Polyline`** (rebuilding it per fix was O(n²) over a ride), thins drawn vertices to 3 m, follows the newest point until the user drags, and shows a GPS quality line. Live figures are provisional; the server's are kept. `RecordScreen` is a route with no tab, reached from a button above the map's zoom controls, with its own `MapView`.

**Server: `ActivityTrack` holds the raw recording; `tracker/activity_track.py` turns it into a ride.** `ActivityTrack` (OneToOne, migration `0095`) stores the raw rows `[t_ms, lat, lon, alt, acc, spd]` as **one gzipped-JSON blob** (a 10-hour ride is ~36k fixes only ever read together — one row, not a table growing by tens of thousands per ride), plus `chunks_received`, `complete`, `mirrored` and a `smoothed` cache keyed by `algo_version`. The pipeline is pure Python (no numpy):

- **`clean`** — accuracy cut, then the per-sport speed check run **forwards and backwards**, keeping only fixes both passes accept, so a bad *first* fix (which a forward-only pass trusts as its anchor) is caught.
- **`smooth`** — per gap-split segment (`SEGMENT_GAP_S` 60s), a constant-velocity Kalman filter in local metres with measurement noise from each fix's accuracy and a **Mahalanobis innovation gate**, then a **Rauch-Tung-Striebel backward pass**. Forward-only filtering lags and rounds corners late and wide; the backward pass is what makes curves follow the road. Axes are independent 2-state filters, so every matrix is 2×2.
- **`stats`** — distance summed over the smoothed track at full resolution (not 30s centroids, which cut corners), **auto-pause from displacement across a 10s window** (hop-by-hop speed made 10 standing minutes credit ~200 m of wander), max speed off a rolling median of moving samples, elevation gain/loss from median → 20s mean → 3 m hysteresis.
- **`simplify`** — iterative Douglas-Peucker (replaced the old every-n-th stride, which could keep a spike and drop the bend around it). **The detail map no longer uses it:** `display_payload` returns **every smoothed point** (every fix that passed `clean` and the smoother's Mahalanobis gate) — it used to DP at 2 m (widening to fit 6000 vertices), which drew an 800-fix walk as a couple of hundred vertices with straights collapsed to chords. `display_payload(sm, tolerance_m=…, max_points=…)` still simplifies on request. Track cache tag is **`c3`** for this. DP now only feeds the list's map tiles (`thumb_polylines`, below).

On synthetic data this lands a 200 m-radius loop within ~1.2 m (raw: 4.2 m) and distance within 0.1%. **`ALGO_VERSION`** is the recompute key: `Activity.stats_algo_version` and `ActivityTrack.algo_version` carry it, and a mismatch re-scores on the next read — improving the smoother re-scores every ride with no migration or job. Changing an activity's kind also re-scores (the sport sets the ceilings).

**Old activities fall back to history.** With no complete `ActivityTrack`, the points come from `Activity.locations` (excluding `flag='suspect'`, accuracy ≤ 50 m) and go through the **same** pipeline, with the original `stats_point_count`-vs-live-`COUNT` staleness rule and `_ACTIVITY_SETTLE_S` (24h) cut-off. **The count query and `Activity.locations` must use byte-identical filters.** A dedicated track's staleness key is `raw_count` instead.

**History mirror.** On the final chunk, `_mirror_activity_to_history` writes the smoothed track **thinned to one point per 5s** into `Location` via `editor_tasks._make_location` (PostGIS column set; `bulk_create` bypasses `save()`), `ignore_conflicts`, then busts `cache_gen` and kicks geocoding — so the ride still shows on `/map/` and counts in history although all-day tracking was paused. Deleting an activity deletes the track, **not** the mirrored fixes. `Location` still gains no grouping column (queried from ~75 places; would be stale on backlog replay). **`HealthWorkout` deliberately does not host this** — it is contractually GPS-free with phone-computed totals.

**Activity reads have their own cache generation** (`activity_gen:{user}`, `_bust_activity_cache`) for the same reason health does. Detail and track responses are **content-addressed** on `stats_computed_at` / `stats_point_count`. Nothing is added to `StatsSnapshot`.

Endpoints (writes `@csrf_exempt` + `_require_api_intent` + `_require_json`; `ApiKeyAuthMiddleware` resolves the Bearer key, so save-on-stop needs no session): `GET/POST /api/activities/`, `POST /api/activities/track/upload/` (chunk; accepts `Content-Encoding: gzip`; `_ACT_TRACK_CHUNK_MAX` 5000 rows, `_ACT_TRACK_MAX_POINTS` 60000), `GET /api/activities/<id>/`, `GET /api/activities/<id>/track/` (`segments`/`speeds`/`times`/`elevations`/`source`), `GET /api/activities/<id>/gpx/` (smoothed, `?raw=1` for raw, one `<trkseg>` per segment), `POST /api/activities/<id>/{update,delete,recompute}/`. Pages: `/activities/` + `/activities/<id>/`.

**Activities list = a grid of map tiles.** `/activities/` is a responsive card grid (`.act-grid`, `auto-fill minmax(17rem)`, one column on a phone); each `.act-card` heads with a **static mini-map composed client-side** — no MapLibre on the page. The list API adds **`thumb`** per activity: a list of Google-encoded polylines (precision 5, one per gap-split segment so a hole is not a chord) from `activity_track.thumb_polylines` — Douglas-Peucker with a tolerance scaled to the ride's bbox diagonal, widened (each pass over the last pass's survivors) until ≤ `_ACT_THUMB_POINTS` (96) vertices. `_activity_thumbs` caches each one content-addressed (`act:thumb:v1:{user}:{id}:{stats stamp}:{stats_point_count}`, 30 days, `get_many`/`set_many`); a cold page builds for at most `_ACT_THUMB_BUDGET_S` (2.5s) and then sends `thumb: null` for the rest **and skips caching the list response**, so the next request carries on. `thumb` is `null` while pending / not yet built, `[]` when there is no line. The page decodes it, picks a fractional web-mercator zoom that fits the bbox in a nominal 360×180 frame (capped at z16, one zoom deeper on ≥1.5 DPR unless the source is `@2x`/512px), and emits the covering raster tiles as `<img loading="lazy" decoding="async">` positioned in **percentages** plus an SVG `<path>` (`vector-effect: non-scaling-stroke`, `var(--primary)` over a `var(--bg)` casing) in the matching viewBox — so a tile scales with its card and is never measured. Tile background: `activities_view` renders the same `_user_basemaps` catalog as `/map/` (`#roamly-basemaps`), and the page takes the first `raster` source of the entry named by `roamly_map_tile_style`; a vector-only entry (OpenFreeMap) falls back to CARTO `dark_all` if its id says dark, else CARTO Voyager (with `CARTO_TILE_QS`). Tile URLs are deterministic (fixed subdomain per x/y) so the browser HTTP cache serves repeats; failed tiles are removed and the dotted `--bg-elevated` tint + line remain. One plain-text attribution line (parsed with `DOMParser`, never `innerHTML` into the page) sits under the grid.

**Instant back navigation.** The list response text is kept in **sessionStorage** (`roamly_act_list:v1:{user}:{kind}`; the active filter in `roamly_act_kind`), rendered synchronously on load (so no skeleton and the browser restores scroll), then revalidated: re-rendered only when the fetched text differs. bfcache restores (`pageshow.persisted`) revalidate too. All storage access is try/catch; quota errors drop the other filters' copies. `activity_detail.html` clears every `roamly_act_list:` key after a rename or delete. The detail page's **back control is a `.btn.btn-outline.btn-sm` with an arrow icon**; when the referrer is `/activities/` it calls `history.back()` (scroll restore), otherwise it follows its href. The detail map colours the line by speed **relative to the activity's own 5th–95th percentile** (the map's blue→green→amber→red functional ramp; an absolute 1–30 m/s scale would paint a whole walk one colour; honours `roamly_speed_gradient`), and the speed and elevation charts plot against **time** with gaps as breaks, the speed axis from the 99th percentile, and hover marking the spot on the map. **The charts do not use the map's simplified vertices** (Douglas-Peucker keeps bends and drops straights, so a long straight road charted as one ramp): the track response carries a separate **`chart`** series from `activity_track.chart_series` — full-resolution smoothed track, speed zeroed while auto-paused and capped at the sport ceiling, a centred time-window mean (speed ±max(5s, 1.5 buckets), elevation ±max(15s, 1.5 buckets)), then bucketed evenly in time to ≤1500 samples — drawn as quadratic curves through the samples. The track cache key carries a `c2` tag for it; the page falls back to the vertex arrays if `chart` is missing. **Activities is baked into Health**: `_health_tabs.html` switches between `health.html` and `activities.html`. Backup: envelopes via `_build_activities_data`, raw tracks as the streamed **`activity_tracks`** section (`meta.version` **17**; restored by `client_id` after the activities, `mirrored=True` since the mirror travels in `locations`). **Deploy the server before the APK** — an old server 404s the track upload (the worker keeps retrying and keeps the rows) and ignores `has_track`. **New model ⇒ build + migrate; mobile change ⇒ rebuild APK + tag.**
