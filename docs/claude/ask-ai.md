# AI Ask, proposals and journal recap

_Read when: Ask chat, tools, proposals, AI recap on Journals._

**AI "Ask" (per-user, BYO OpenAI-compatible LLM).** Optional **Ask** tab (`/ask/`, `ask_view` → `ask.html`) for natural-language questions over the user's location history. Config on `UserProfile` (`ai_ask_enabled`, `ai_base_url`, `ai_api_key`, `ai_model`, `ai_system_prompt`; migration `0031`), edited from **AI Ask** card in Settings (`POST /api/profile/ai-config/`). API key is masked as `••••••••` on GET, only overwritten on POST when value ≠ mask. `UserProfile.ai_configured` = enabled + base_url + key + model all set. The Ask tab only renders when `AI_ASK_ENABLED` is true (set in `context_processors.custom_js_snippet`); `ask_view`/`ask_api` re-check it (403 guard).

`tracker/ai_tasks.py` runs an OpenAI-compatible tool-call loop (`run_ask`): system prompt + client turns → `POST {base_url}/chat/completions` with `tools`/`tool_choice:auto` → execute tool calls scoped to `request.user`, append `role:"tool"` results, repeat ≤5×. All tools are strictly **read-only** ORM reads. **Latency is the tool layer, not the model:** the three all-time tools (`get_history_overview`, undated `get_distance`, `list_visited_places`) read the user's finished `StatsSnapshot` (`_snapshot_json`; never kicks a compute, falls back to the live scan when none exists) instead of rescanning the whole history per call, and one model turn's tool calls run concurrently (`_run_tool_calls`, ≤4 threads; each re-enters the caller's timezone and closes its DB connections). `_provider_chat` reuses a module-level `requests.Session`, the default prompt tells the model to batch independent lookups into one turn, and `run_ask` logs per-provider-call and per-tool ms. `TOOL_DISPATCH` maps: `search_history`→`_run_history_search`, `get_day_detail`→`_compute_day_detail`, `list_visited_places`→`_compute_visits_from_qs`, `list_custom_places`→`_compute_places_payload`, `get_custom_place_detail`→`_compute_place_detail`, `get_distance`→`_compute_distance_from_qs`, `get_history_overview`→`_compute_overview_from_qs`. Journal tools (`search_journals`, `read_journal_entry`) are **opt-in**: only offered when `UserProfile.ai_allow_journals` is set (migration `0032`). `ask.html`'s `format()` renders only internal `/`-prefixed markdown links and `**bold**` after HTML-escaping — dates link to `/map/?date=YYYY-MM-DD` without XSS risk. Chat is ephemeral (browser-only). AI config excluded from backups. **New model field ⇒ build + migrate.**

**Ask chat page (`/ask/`, migration `0112`).** The web Ask tab is a full chat app: a chat list (search over titles and message text, pin, rename, delete, grouped Pinned / Today / Previous 7 days…), a streamed conversation, and a map panel beside it (a bottom sheet on phones). Chats are saved server-side as **`AskChat`** (title, `titled` once the model or user named it, `pinned`, `mode`) + **`AskMessage`** (`role`, `content`, `cards` = the map cards shown, `meta` = `sources` + `followups`). Private conversation text, so **excluded from backups** like the AI config. The Android app keeps the one-shot `/api/ask/` and is unchanged apart from gaining the new data tools.

**It can only read; changes are proposed and the user approves them** (see Ask proposals below). That is enforced by there being no tool that writes, not by the prompt (which also says so). A turn only ever writes its own chat rows, `AskProposal` included. `test_every_tool_is_read_only` runs every tool through the real loop and checks that `Location`/`Flight`/`CustomPlace`/`Adventure`/`JournalEntry` are unchanged, and the flight tools never return `booking_ref`, `ticket_number`, `passenger_name`, `frequent_flyer` or `bcbp_raw`.

**Ask proposals (approval-based edits, migration `0114`, `tracker/ask_edits.py`).** For four things the chat may *propose* a change: **add a flight** (`propose_add_flight`, after `lookup_flight` when the user gives a number and date), **edit a logged flight** (`propose_update_flight`, only the fields named), **fill in an empty journal title/mood/weather or append text to an entry** (`propose_journal_entry`, offered only behind `ai_allow_journals`; existing text is never replaced), and **add a custom place** (`propose_add_place`). A propose tool only reads and validates (`_apply_flight` on an unsaved copy, the duplicate check, the place-name check) and returns a draft under `_proposal`; `ask_events` yields it as a `proposal` event and `send_api` stores it as an **`AskProposal`** (kind, target, `payload` = exactly what approving applies, `before` = the touched fields' values when proposed, `rows` = the card's before/after lines). The page shows a card with **Approve / Deny**; **only `POST /api/ask/proposals/<id>/approve/`** (web-only, CSRF-checked, owner-scoped) changes a record. Approve claims the row first (`status` pending → approved by conditional `UPDATE`, so a double click applies once), refuses a proposal older than `PROPOSAL_TTL` (7 days) or whose turn was never saved (`message` NULL), and refuses as stale when a touched field no longer matches `before` (journal body by SHA-256). **A flight edit cannot move anything it didn't list:** `_apply_flight_changes` re-validates the whole flight, then restores every field the changes don't name (re-validation would otherwise fill a bare `BOS` with its airport name), errors if any field outside `FLIGHT_FIELDS` would change, and approval requires the resulting diff to equal the stored `after` exactly. Booking reference, ticket number, passenger name and `source` are never offered to the model and dropped if sent. Creation reuses the pages' own paths (`_create_custom_place`, shared with `places_api`; flight save + `_match_flight_track` + `_kick_opensky`). The model learns the outcome because `send_api` appends `ask_edits.history_note` (`[Proposed change: … — APPROVED/DENIED/NOT applied]`) to the assistant turn it came from when replaying history. At most `MAX_PER_TURN` (5) per answer. A failed turn deletes its proposals; a regenerate deletes the old reply's (FK cascade). The app's one-shot `/api/ask/` is not offered the tools and `_run_one_tool` refuses them there (`edits=False`). Proposals are chat rows ⇒ **excluded from backups**. **New model ⇒ build + migrate.**

- **Streaming.** `POST /api/ask/send/` (`ask_views.send_api`, web-only, CSRF-checked) streams one JSON object per line: `chat`, `status` ("Checking your flight log…"), `delta`, `map`, `done` (with `sources`), `saved`, then `followups`. It is labelled `text/event-stream` with `no-transform` so a Cloudflare tunnel passes it unbuffered, and sends `Content-Encoding: identity` because `GZipMiddleware`'s streaming compressor doesn't flush per chunk. **The provider's stream is read as bytes and decoded as UTF-8 per line.** `requests`' `decode_unicode` uses the response charset, an event stream usually names none, and it fell back to Latin-1, which stored every emoji and dash garbled ("ð", "â"). Migration `0113` reverses that on saved replies (Latin-1 → UTF-8 round trip, only where it succeeds and changes the text). `ai_tasks.ask_events` is the loop (up to `_CHAT_MAX_ROUNDS` 8 tool rounds), over `_provider_stream`, which assembles streamed `tool_calls` fragments and also accepts a provider that ignores `stream` and answers plain JSON. The user's question is saved first and the reply when it ends. A stop or disconnect saves what arrived (`GeneratorExit`). **A provider round is bounded**: `_STREAM_MAX_BYTES` (512 KB) and `_STREAM_DEADLINE_S` (240 s), because `_REQUEST_TIMEOUT` only bounds the wait between bytes and the base URL is user-chosen; a cut-off round keeps its text plus `_CUT_OFF_NOTE` and drops half-streamed tool calls. Sends are limited to `_SEND_LIMIT_PER_HOUR` (120) per account (429). Rendered links must start with a single `/` — `//host` and `/\host` are refused as outside links. A provider error undoes the turn: a new question and a just-created chat are removed; a regenerate keeps the old reply and restores an edited question.
- **Model and effort picker** (migration `0118`, `UserProfile.ai_extra_models`). **Ask-only; the global model in Settings is never changed.** The composer has a model button that opens a popup: *Your models* (the Settings default first, then ones added here; ✕ removes an added one), *Available from your provider* (`GET /api/ask/models/` → `ai_tasks.list_provider_models`, the provider's `GET {base}/models`, best effort, `[]` when unsupported; clicking one adds and selects it) and an input + **Add** for any id by name (≤30 added). `POST /api/ask/models/ {action: add|remove, model}` edits only `ai_extra_models`. Next to it an **Effort** dropdown (default/low/medium/high). Both choices are remembered in the browser (`roamly_ask_model`, `roamly_ask_effort`) and sent with each `send` as `model`/`effort`. `send_api` accepts a model **only if it is in `ai_model_choices()`** (default + added; anything else falls back to the default) and an effort only from `ai_tasks.EFFORTS`, then runs the turn on a `copy.copy` of the profile with `ai_model`/`ai_effort` overridden — never saved. Effort goes out as `reasoning_effort`; a 400/422 retries without it and remembers the (base URL, model) in `_NO_EFFORT` for the process. The model used is stored in `meta.model` and shown in the stats line when more than one model is configured. Title/follow-up calls use the default model. The app's one-shot `/api/ask/` is unchanged.
- **Icons and map chrome.** Every icon on the page is an inline stroke SVG (`stroke: currentColor`, width 2, round caps, `fill: none`), never a Unicode glyph: the chat rows' star / rename / delete (`ROW_ICONS`, 16px glyphs in 28px targets, shown on hover, focus-within and the open chat; a pinned chat keeps its star visible, filled in `--primary`, `aria-pressed`), the top bar's chats / download / new chat, and the map panel's open-in-map / close. The map panel's head shares `.ask-topbar`'s height, padding, rule and type, so the two bars line up across the split. On the map, the legend (top-left, wraps, clear of the zoom buttons) and the ranking (bottom-left, a sticky mono "Top N" / "Most driven" caption over a numbered list) are small `--bg-card` plates with hairline borders, mono micro-labels and role radii. Popups inherit the popup's ink (the old forced dark text was unreadable on the components facets' dark popups); Field Journal (no `data-style`) gets its popup and zoom group drawn here, the compact attribution under every facet, as on `/map/`. In-message map cards wrap title + subtitle in a `min-width: 0` column so long titles ellipsize instead of overflowing.
- **Regenerate / edit.** `{"chat_id", "regenerate": true, "message"?}` re-answers the last question, optionally edited. The superseded replies are deleted only when the new one is saved.
- **Time and tokens.** Each request sends `stream_options: {include_usage: true}`. A base URL that answers 400/422 is retried once without it and remembered in `_NO_STREAM_OPTIONS` (per process). `_turn_stats` adds up the rounds: `out_tokens` is all completion tokens, tool arguments included; `in_tokens` is the last round's prompt; `tok_s` uses streaming time only (first token to last); `seconds` is the whole turn. With no reported usage, output is estimated at about 4 characters per token and marked `estimated` (shown with `~`). It rides on `done` as `stats`, is stored in `meta`, and shows as a small mono line under the answer, with details on hover.
- **Tables.** The page's Markdown subset renders pipe tables: a header row plus a `|---|` separator, `:` alignment, cells escaped like the rest. base.html's version line is hidden on this page, because it sat on the composer under the pinned app; the version is shown in the chat list's footer instead.
- **After the answer:** `ai_tasks.followups` makes one small no-tool call for a chat title (only until `titled`) and three follow-up chips, stored in `meta`. It is best effort and runs after `saved`, so the reader never waits on it.
- **Modes** (`ASK_MODES`: plan / brainstorm / flights / recap, stored on the chat) add one line to the system prompt. In the chat, `_CHAT_DIRECTIVE` makes the assistant a travel companion. Facts about the user must come from tools. General travel knowledge (destinations, tips, flight times) is allowed but labelled as a suggestion.
- **Map cards** (`tracker/ask_map.py`, `ask_tools.py`) are small parameter dicts, never geometry. `history` (a date, a range and/or city/state/country) draws as lines up to `_LINE_MAX_DAYS` (7), else dots, thinned in the database to about `_MAX_POINTS` (3000) on `id % k`. `flights` (optional year) draws great-circle arcs with longitudes unwrapped, weighted by count. `pins` are places the model suggests (≤25, coordinates validated, `connect` for a route) and touch no user data. `GET /api/ask/map/` re-reads the signed-in user's own points whenever a card opens, so a stored chat never holds a copy of the history. `/map/?date=` links in an answer open in the side panel; modifier-click still goes to the full map.
- **Data maps** (`tracker/ask_datamap.py`, `show_data_map`, card `kind: "data"`). Statistics drawn on the map panel. **Read-only by construction: the model never writes a query**, it picks a `metric` from a fixed list plus validated parameters and the server runs its own scoped queries. Metrics: `place_visits` (distinct places whose `Visit` place/POI name contains `name_contains`, per US state or country, with visit counts), `days` (distinct days per state/country, optional date range), `town_coverage` (towns visited ÷ `Boundary` place/cousub towns per US state; a state with no boundaries loaded shows its visited count and no percentage), `top_roads` (up to ~2500 sampled driving fixes snapped to the nearest `RoadSegment` within 40 m, ranked by road name, share is relative, top 15 drawn with line weight by share). The card holds only parameters; `GET /api/ask/map/` recomputes (`geometry`, cached 10 min per user+card) so a stored chat holds no history. The page joins regions to `static/tracker/data/us-states.json` (by name) or `world-countries.json` (by `cc`), colours by sqrt-scaled value, prints the number at each region's centroid and lists the top 10 in a corner panel. An empty result is a 404 with a hint. Offered with `maps=True` only, like the other map tools. No model or migration.
- **Tools.** `ask_tools.DATA_TOOL_SCHEMAS` are added to `TOOL_SCHEMAS`, so the app's `/api/ask/` gets them too: `list_flights`, `get_flight_stats`, `lookup_flight` (AeroDataBox, its own 15/day per account under `ask_flight_lookup:`), `list_adventures`, `get_adventure`, `get_period_summary` (`yearly_json`), `get_travel_modes` (`transport_json`), `get_stays` (`Visit` rows, ≤2 months), `get_achievements` (`AchievementSnapshot`), `list_unvisited` (countries or US states), and `search_near` (a coordinate the model knows → have they been there). The map tools (`show_map`, `show_flights_map`, `show_places`) are offered only with `maps=True`, and `_run_one_tool` refuses them otherwise.

Endpoints: `GET /api/ask/chats/?q=`, `GET /api/ask/chats/<id>/`, `POST …/rename/`, `…/pin/`, `…/delete/` (the conversation only), `POST /api/ask/send/` and `GET /api/ask/map/`. All require `ai_ask_enabled` + `ai_configured` and are owner-scoped. The page loads MapLibre, Markdown export is client-side, and Ctrl+Shift+O starts a new chat. **New models ⇒ build + migrate.**


**AI recap on Journals (on demand, never stored).** The **recap my past few days** button on `/journals/` (in the sidebar, between the search box and the today box) opens a side panel over the page, and opening it is the opt-in: **that is the only thing that calls the provider**, once per opening. Closing it aborts any request and empties the panel, and there is no preference, cursor, cache or model behind it, so a reload starts closed. `POST /api/journals/recap/` (`journal_recap_api`, `tracker/journal_recap.py`) is a POST because each call spends the user's provider credits, so a prefetch must never trigger one; web-only, so CSRF-checked (no `@csrf_exempt`), limited to `_JOURNAL_RECAP_LIMIT` (12) an hour per account, answered `no-store`. It uses the summary emails' AI and helpers (`ai_tasks._provider_chat` with no tools, gated on `ai_configured`; `_period_visits`, `_stay_timeline`, `_top_cities`, `_top_places`, `_compute_overview_from_qs`, `_compute_distance_from_qs`) under its own `JOURNAL_RECAP_SYSTEM_PROMPT` (friend-like 3-5 sentence prose naming real places; `_stay_timeline` drops pass-through stays, so towns only driven through are never mentioned). With AI not set up the panel links to Settings and makes no request.

The stretch is `RECAP_DAYS` (5): today so far plus the four days before, in the user's zone. **Earlier stretches are the same weekdays `EARLIER_WEEKS` (1–4) weeks back and 52 weeks back, each stopping at the same clock time as now**, since today is only part done and a full earlier day would always look busier. A stretch counts only when the tracker ran on at least half its days: an empty week is missing data, not a quiet week, and averaging it in would make every ordinary week look busy. With none left, `earlier` is left out of the payload entirely and the prompt tells the model not to compare; the panel says so itself. The figures are computed server-side and returned as `facts`, so the numbers shown never depend on the model having copied them. Nothing recorded and no journal entries means **no provider call at all** (`status: 'empty'`). Journal text goes to the provider only behind `ai_allow_journals`, only for the days in the stretch, capped per entry; the panel's footer says what was used. New model + migration ⇒ `up -d --build`. Not in backups.

**"A year ago today" header chip (written at 2am, saved per day).** `base.html` shows a small chip in the navbar between the Data menu and the notification bell (desktop only, hidden ≤1280px and when `roamly_year_ago` is `off`). `POST /api/year-ago/` (`year_ago_api`, `tracker/year_ago.py`) is a POST because a miss spends provider credits; CSRF-checked, `no-store`, limited to `_YEAR_AGO_LIMIT` (20) provider-bound requests an hour per account (saved lines aren't counted). The target day is the same calendar date one year back in the user's zone (Feb 29 → Feb 28). It reuses the recap's AI and helpers (`_provider_chat` with no tools, `_period_visits`, `_stay_timeline`, `_top_places`, `_top_cities`, `_journal_rows`) under its own prompt (a 3–7 word headline, blank line, 2–3 sentences). **Every line is saved as a `YearAgoRecap` row** (one per account and day, migration `0120`) and served from it afterwards, so a day costs at most one provider call; a row written under the other `ai_allow_journals` setting is rewritten in place instead of served, so journal-derived text is never shown after consent is withdrawn. A day with nothing recorded is only remembered in the cache (`year_ago:none:<user>:<date>:<consent>`, 2 days). Saved and known-empty days skip the rate limit; only a provider-bound request counts. **Lines are written ahead at night** by `year_ago_tasks` (a daemon from `apps.ready()`, every 15 min): from 2am until 6am in the user's own zone it writes today's and tomorrow's line (a year-ago day is long over, so tomorrow's is ready before midnight and the first load of the day only reads a row). It covers only accounts with AI configured whose chip was shown in the last 14 days (`viewed_at`; the on/off switch lives in the browser, so this is how the server knows), takes a per-account advisory lock (`'RAMY'`) so the three workers don't write the same line, and stops after 3 provider failures a day, leaving the on-demand path. All saved lines are listed in Raw data → **Year ago recaps**. Journal text goes to the provider only behind `ai_allow_journals`. No points and no consented journal text that day ⇒ `status: 'none'` with **no provider call**; AI not set up ⇒ `status: 'unavailable'` (200, no error); provider failure ⇒ 502, not cached. The browser also keeps the result in `sessionStorage` (`roamly_year_ago_cache`, keyed by local date; failures retry after 30 min) so navigating never re-asks. The chip links to `/map/?date=YYYY-MM-DD`; hover/focus opens a popover with the full summary, distance and top places. **‹ › buttons (and ←/→) in the popover step to the previous/next day**: `POST offset=<n>` (form field, clamped to ±`MAX_OFFSET_DAYS` = 30, non-integer ⇒ 400) moves the target day `n` days from the year-ago date. Each day is its own saved row (keyed by date, so the response carries no offset; a stepped day is saved but doesn't count as viewing the chip), the same rate limit applies to misses, and stepped days are cached client-side in `sessionStorage` `roamly_year_ago_days` (per local date). A stepped day with nothing recorded shows "Nothing recorded on this day." rather than hiding; the chip itself always stays on a year ago today. New model + migration ⇒ `up -d --build`. Not in backups.
