# Backups and restore

_Read when: Backup format, S3, zip, restore, progress._

**Backups (data + media).** **Data backup** is one JSON document (`meta.version` = **26**) covering: devices, locations (plus overlap-hidden points, tagged — see Device overlaps), **device_overlaps**, cell_samples, activities + **activity_tracks**, adventures (subtitle/access_pin/cover/body blocks + nested members/blurbs(POIs, with `id`/`title`/**`rating`**/**`category`**)/milestones/comments/**planned_stops**/**day_notes**), journals (JournalEntry incl. `quick_note` + photo metadata), custom_places (name/center/radius_m/color/notes), api_keys, **family_circles** (circles the user created, with their members/places/alerts — see Family Circle below), **flights** (the flight log), **edit_batches** (map-editor generated points, grouped by edit), **trip_blogs** (see Trip blog). Excluded: derived data (Visit/VisitJob, POI, SiteStat, StatsSnapshot, Boundary, `Location.transport_mode`) and AI config. **`SummaryEmailLog` (sent recap emails) is excluded** too, with no `meta.version` bump: it is a log of mail already delivered to the user's inbox (each row carries a full HTML body, so it would bloat every backup), and losing it on restore loses no data the person created. **`DismissedSuggestion` is also excluded** — it's user intent rather than derived, so it's a deliberate call, not an oversight: after a restore, rejected place suggestions simply reappear and get re-rejected, which was judged not worth widening the backup contract for. **One builder, not two:** `views._write_backup_json` streams the whole document to a temp file, which `backup_tasks.build_backup_zip` wraps into the archive both the manual download and the S3 backup ship (below); locations, health samples, cell samples and activity tracks stream row-by-row to avoid OOM, everything else goes through shared list-building helpers in `backup_tasks.py` (`_build_adventures_data`/`_build_journals_data`/`_build_custom_places_data`/`_build_health_workouts_data`/`_build_activities_data`/`_build_family_data`/`_build_flights_data`/`_build_edit_batches_data`/`_build_trip_blogs_data`). **When adding a user-content model/field:** add or extend a shared helper, bump `meta.version`, teach `views.restore_backup` to read it — there is only the one function to teach. `restore_backup` accepts all versions (v26 adds journal `quick_note`; v25 adds `trip_blogs`; v24 adds flight `icao24` + OpenSky tracks; v23 adds the flight track link; v22 adds flight boarding-pass fields + photo; v21 adds `edit_batches`; v20 adds `flights`; v19 adds overlap `kind`; v18 adds `device_overlaps` + overlap-hidden points inside `locations`; v17 adds the streamed `activity_tracks`; v16 adds `cell_samples`; v9 adds `id` to each blurb + blurb photo, purely so restore can remap references — see below; v8 adds adventure `day_notes` + blurb `rating`/`category`; the removed **Pals** feature's legacy top-level `"pals"` key is silently ignored; v7 adds adventure `planned_stops`; v6 blurbs carry `title`; v4/v5 adventure `places` and v2/v3 legacy `trip_places` are restored **as blurbs**; v5+ `custom_places`). Restores are idempotent (`get_or_create` on natural keys). Media travels **inside the same zip** as the data, for both the manual download and S3 — there is no separate media path any more (see the next two paragraphs).

**Story body id-remapping on restore.** An adventure's `body` (the Story block document) embeds live database ids — inline `[^pin:ID]` footnotes, `location_card.place_id`, `photo_grid.photo_ids` — pointing at specific `AdventureBlurb`/`AdventureBlurbPhoto` rows. Restoring into a fresh database (the actual disaster-recovery case) recreates every blurb and photo with new auto-increment ids, so a `body` copied over verbatim would silently orphan every pin footnote, location card and photo grid — the same class of problem `AdventureDayNote.place_ref` already solves for day notes via a natural key (title+lat+lon), but `body` embeds ids, not natural keys, so the fix is different: v9 backups carry each blurb/photo's original `id`, and `restore_backup` builds `blurb_id_map`/`photo_id_map` (old id → newly-created row) while creating them, then `_remap_story_body_ids` walks `adv.body` after all blurbs/day-notes are created and rewrites those three reference points through the maps before saving. Only runs for freshly-created adventures (`adv_created`) — an adventure that already exists doesn't get its blurbs recreated, so there's nothing to remap. Backups without blurb/photo `id`s (pre-v9) restore exactly as before — unresolvable refs are left untouched, same as today.

**A backup is one zip (data + media), restorable in one step.** `backup_tasks.build_backup_zip(user, out_path, include_media=…, progress=…)` writes `_write_backup_json`'s output to a private temp `.json`, then zips it into `backup.json` plus a `media/<relative-path>` entry per file from `_get_user_media_files` (adventure covers, blurb/day-note photos & videos, journal photos, profile picture). It is the **only** archive builder: `export_backup_start` (manual download, always with media) and `_run_backup` (S3) both call it, so the file a user downloads and the file in their bucket are identical by construction. `ZIP_DEFLATED` for the JSON (text compresses well), `ZIP_STORED` per-file for media (already-compressed JPEG/MP4 — deflating again buys nothing). Exists because photos/videos used to be recoverable only through a separate, optional S3 image backup (loose files; removed in migration `0092`), so an instance without one had no way to get them out at all. `restore_backup` sniffs the upload's magic bytes: `PK\x03\x04`/`PK\x05\x06` (zip) opens it, restores from `backup.json` as before, then extracts every `media/` entry to `MEDIA_ROOT` at its stored relative path (same path the just-restored `ImageField`/`FileField` values already point at, so nothing needs re-linking) — guarded against zip-slip by rejecting any entry whose normalized path would land outside `MEDIA_ROOT`. Anything else falls back to the legacy path (plain or gzip-magic-prefixed JSON, no media) for backups downloaded before this change. Settings' "Restore Backup" accepts `.zip`/`.json`/`.gz` for exactly that reason. **S3 auto-backup (`BackupConfig`) uploads that same zip** as `{prefix}{username}/backup_<ts>.zip` (`application/zip`). It used to upload a raw, uncompressed `backup.json` — ~12× larger than the deflated zip on a real instance — with media going up separately via an opt-in "image backup". **`BackupConfig.include_media`** (migration `0091`, default **True**, which backfilled existing configs) picks full zip vs data-only zip; it is S3-only — the manual download always includes media. The Settings switch ("Include photos & videos", same bordered `--primary` plate as the tracking-alert switch) **autosaves alone**: `backup_config_api` treats a POST whose only key is `include_media` as a narrow update, so flipping it never saves half-edited credentials in the fields above; a full-form POST missing the key reads it as True, so an old page can't switch media off by omission. `_prune_old_backups` counts `.zip` **and** legacy `.json` objects so pre-zip backups still rotate out. `last_backup_file_count` feeds the status line ("N media files" / "data only"). **Restore-size warning:** `restore_backup` caps a zip at 2 GiB of `backup.json` and 4 GiB of media (zip-bomb guard); `restore_limit_warning` flags an archive past either, stored in `BackupConfig.last_backup_warning` (migration `0093`) and returned as `warning` on the download's ready state — a backup Settings can't restore should say so when it's made. **Staleness uses a heartbeat:** a run stamps `last_backup_heartbeat_at` (migration `0090`, throttled to `HEARTBEAT_EVERY_S`, plus every 2 MB uploaded), and `get_backup_status` fails a run only after `STALE_AFTER_S` (600) without one — the run's thread usually lives in another gunicorn worker, and judging on the start time failed long, healthy media backups mid-run.

**Restoring a zip streams `locations`, `cell_samples` and `activity_tracks`, and builds nothing else twice.** `_open_backup_json(zf)` returns `(small keys, locations iterator, cell-samples iterator, activity-tracks iterator)` — the streamed set is the module-level `_STREAMED_BACKUP_KEYS`, because a 400k-point archive that the streaming *export* produced could not be `json.loads`ed back on the same machine — a backup you cannot restore at the size where it matters is not a backup. It deliberately does **not** use `ijson.kvitems(jf, '')`: that builds each value in full before yielding it, so `locations` would be materialised in RAM and only then discarded by the filter, with peak memory identical to the `json.loads` it replaces. Instead `ijson.parse` is scanned for top-level `map_key` events (raw events, nothing built, constant memory) and each small key is then pulled with its own `ijson.items` pass — re-reading the member once per key, which is cheap because every key except `locations` is tiny and a restore is rare. Falls back to plain `json.loads` when `ijson` is unavailable, so an instance that has not rebuilt behaves as before. **`_open_backup_json` is a private helper and must not carry view decorators** — a stray `@login_required` on it made every zip restore 500 (`login_required` treats its first argument as the request, so it read `.user` off the `ZipFile`), while `restore_backup`, the actual view, was left with no auth decorator at all. Only the zip path called the helper, so plain-JSON restores kept working and hid it.

**Backup download progress + sized transfer.** `export_backup_start` stores a *dict* job record in the cache (`backup_job:{user}:{job}`, TTL 3600 refreshed on every update) — `{status, stage, pct, done, total, started}`, and on completion `size` (final zip bytes) + `file_count` (media files zipped). One progress bar covers both phases: `_BACKUP_PREP_PCT`–`_DATA_PHASE_PCT` (8–55) for `_write_backup_json`'s callback (per section and every 5000 locations, `done`/`total` = locations), `_DATA_PHASE_PCT`–100 for the media-zipping loop (`done`/`total` = files, updated every 20). `export_backup_status` derives `eta` server-side from elapsed ÷ pct; Settings renders a `.bk-progress` bar with stage label, ETA, and a `done/total <unit>` line where the unit follows the current stage. **Because the download is a real `.zip` file on disk, `FileResponse` gets a correct `Content-Length` for free** — none of the gzip-streaming `Content-Encoding` trickery the old JSON-only download needed (Django's `GZipMiddleware` deletes `Content-Length` on streaming responses since it can't know the compressed size ahead of time; a zip's `FileResponse` already knows its size, so the response just sets `Content-Encoding: identity` to keep the middleware from re-compressing an archive that won't shrink further).

**Restore progress.** The restore stays one synchronous `POST /api/import/backup/` — its response is still what carries the result or the error — but the browser mints a `job_id`, sends it with the upload, and polls `GET /api/import/backup/status/<job_id>/` (`restore_backup_status`) while the request runs; with gunicorn's `gthread` workers the poll is served concurrently. `_RestoreProgress` writes `{status, stage, pct, done, total, unit}` to `restore_job:{user}:{job}` (1h TTL, writes throttled to 2/s, best-effort — a cache failure never fails a restore); cache writes sit outside the DB transaction, so they are visible mid-restore. Each stage owns a slice of the bar sized by rough cost: one unit per streamed location/cell-sample row (totals from the backup's own `counts`, else the list length for legacy JSON), the small sections together as a tenth of that, media a fixed 25% when present. Settings uploads through `XMLHttpRequest` rather than `fetch` because only XHR reports upload progress, which is the first 20% of the bar (`RESTORE_UPLOAD_PCT`); a status poll before the view has started answers `pending`.
