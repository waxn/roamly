# Downloads, Overpass and auto-download

_Read when: Road/subway/POI downloads, DownloadedRegion, Overpass pool/failover._

**Downloads (Admin Panel → Downloads).** Road, subway and POI data (`RoadSegment`, `RailSegment`/`RailStation`, `POI`) are instance-wide reference tables with no user FK, but the three background jobs that populate them (`RoadDownloadJob`, `RailDownloadJob`, `POIDownloadJob`) used to be per-user (`OneToOneField(User)`), triggered from each person's own Settings → Background Jobs, with the download AREA scoped to *that user's own* device history. That was architecturally backwards once the data itself is shared — two users on the same instance could each run their own download, racing to populate one table neither of them owns alone. All three are now **admin-only, instance-wide singletons** (`pk=1`, `SiteConfig`-style — migration `0067`, which also deletes any pre-existing per-user rows since job *status* has no value worth carrying across the shape change), and the download area for each now covers **every user's combined travel history**, not just one person's:

- `road_download_tasks._visited_boxes()` (shared verbatim by `rail_download_tasks.py`, per its own docs) scans `Device.objects.all()` instead of `Device.objects.filter(user_id=user_id)`.
- `poi_tasks.py`'s city list comes from `Location.objects.exclude(city='')` across every device, not one user's.
- Each module's `_running_thread` is a single module-level variable (was a `{user_id: Thread}` dict) — there is now only ever one run to track per job type, instance-wide.
- Every API endpoint (`road_download_api`/`_status_api`/`_stop_api`, `road_data_delete_api`, the `subway_*` and `poi_*` equivalents) gained `err = _require_admin(request); if err: return err` as its first check. URL paths are unchanged (`/api/roads/download/` etc., not moved under `/api/admin/...`) — only the view-level gating changed, to keep the URL churn to zero.
- **New:** `POST /api/poi/delete/` (`poi_delete_api`) — POI never had a delete endpoint before this; added for parity with road/subway's existing `TRUNCATE`-based delete. `POIDownloadJob` also gained `worker_token` and `failed` fields it didn't have before (migration `0067`), bringing it up to the same cross-process-ownership and failure-reporting standard road/subway already had — it previously only had a bare 60-second staleness check with no token-based ownership at all, and no way to surface a partial-failure count.
- `rail_download_tasks._download_boxes` gained the same `HTTPError`-vs-everything-else split and `unreachable` return value `road_download_tasks._download_boxes` has (see Road snapping below) — it forked its own retry loop originally rather than reusing the road version's, so it had not received that fix.
- Settings → Background Jobs keeps **Reverse Geocoding**, **Re-geocode All Points**, **Match POIs to Points**, **Detect Transport Modes** and **Recalculate Stats** (all genuinely per-user, operating on that user's own points) — only the three download cards moved out, replaced with a note pointing non-admins at "ask your instance admin" and admins at a link to `/admin-panel/#downloads`.

**Auto-download new regions** (migration `0068`). All three downloads are now also **incremental and automatic**, not just admin-triggered. `DownloadedRegion` (`kind` = `road`/`subway`/`poi`, `key` = a `"gy,gx"` grid-cell coordinate for road/subway or `"city|state"` for POI) records what's already been fetched from Overpass, so any run — manual button or automatic — only asks about growth since last time:

- `road_download_tasks._visited_cells()` (the raw cell-set scan, unchanged) feeds `_visited_boxes(kind, beat=None)`, which now diffs against `DownloadedRegion.objects.filter(kind=kind)` before merging into query boxes, and returns `(boxes, box_cells)` — the cell keys behind each box, so the caller can mark them covered once that box's batch actually succeeds. `rail_download_tasks` calls the same function with `kind='subway'` (road and subway are tracked independently despite sharing the cell grid, since a cell can have one without the other). A batch's cells are marked covered via `_mark_covered(kind, keys)` **only when that batch's `failed_boxes == 0`** — a partial failure leaves its cells uncovered so the next run retries them, rather than silently skipping a corridor forever because it happened to share a batch with a cell that failed. `_visited_cells()` itself is cached 10 minutes (`road_download:visited_cells`) since road and subway both call it with an identical result — without this, an auto-download sweep (which checks both kinds) or an admin clicking both buttons paid for the full per-device location scan twice in a row for the same answer.
- `poi_tasks.py` filters its per-city list against `DownloadedRegion(kind='poi')` before downloading, and `get_or_create`s a `(city, state)` row **only for a city Overpass genuinely answered for** (even with zero results). Any other outcome leaves it uncovered for the next run and counts it in `failed`. This used to key off `unreachable` alone, so a city rate-limited with a 429, timed out, or truncated by a `remark` returned the same empty list as a city with no POIs and was marked covered **forever** — never retried, and never counted as failed either. `_download_city_pois` returns an explicit `answered` flag for exactly this.
- All three delete endpoints (`road_data_delete_api`/`subway_data_delete_api`/`poi_delete_api`) now also clear the matching `DownloadedRegion` rows, so deleting the data really does mean starting over rather than leaving every cell/city marked "already covered" against an empty table.
- This makes the **manual** button itself incremental too (re-clicking "Download Roads" after nothing has changed now costs one DB scan and zero Overpass requests, not a full re-query) — there's no separate code path for "auto" vs "manual", both call the same `start_road_download()`/`start_subway_download()`/`start_poi_download()`.

`tracker/auto_download_tasks.py` is the scheduler that actually triggers unattended runs: a daemon thread from `apps.ready()` (mirroring `log_cleanup_tasks.py`'s pattern exactly — PG advisory lock namespace `0x52414d44` 'RAMD', `close_old_connections()` each pass, every exception swallowed) sweeps every 6 hours and, for whichever of `SiteConfig.auto_download_roads`/`auto_download_subway`/`auto_download_pois` are enabled (**all three default on**), calls the same `start_*_download()` entry point the manual button uses — skipping a kind only if its job row already looks genuinely mid-run (`status='running'` and updated within `STALE_AFTER_S`, the same staleness grace each job's own status endpoint uses to decide whether to resurrect a run). Because the downloads are incremental, a sweep against a fully-covered instance is nearly free — the cost is a full-history DB scan (no Overpass calls), not a re-download. `SiteConfig.overpass_urls` (migration `0076`) lives on the same tab and sets which Overpass endpoints all three downloads use — see "Endpoints are a pool" below. The three toggles are editable from **Admin Panel → Downloads** (one checkbox per card, auto-saving via `POST /api/site/auto-download/`, admin-only) for an instance that would rather trigger downloads by hand — e.g. one whose Overpass mirror is flaky enough that unattended retries aren't welcome. **New model + `SiteConfig` fields ⇒ build + migrate.**


**`RoadSegment` is the largest table in the app**, so `tracker/road_download_tasks.py` keeps it small: the download area is derived from the ~2km cells the user actually travelled through — the cells containing fixes *and* the cells between consecutive fixes, rasterised with an integer DDA (`_line_cells`), skipping pairs that fail the same speed/distance rules routing applies so a flight can't rasterise a transcontinental line. Only drivable classes (**no `service`**, no footway/path/cycleway), `way_id` unique so overlapping areas dedupe. Merged runs are capped at `MAX_RUN_CELLS` (12, ~26km): corridor bridging makes long stretches of adjacent cells, and merging them wholesale produced single bboxes hundreds of kilometres wide, which is what timed Overpass out. Failures are **retried with backoff then bisected** and the unrecoverable count lands in `RoadDownloadJob.failed`, surfaced in red — a silently-empty corridor is indistinguishable from snapping being broken.

**All Overpass traffic goes through `tracker/overpass.py`.** It is the only place that makes the request, and it splits a failure **three** ways rather than two — the two-way split it replaced is what made a merely slow mirror indistinguishable from an offline server:

- **`http`** — reached, and it answered with an error status (429 rate limit, 504 under load). A smaller query is genuinely less likely to hit the same limit, so the caller retries and then **bisects**, unbounded.
- **`timeout`** — reached, but no usable answer in time. Also worth retrying and shrinking, so it takes the **same** retry-then-bisect path. Deliberately broader than literal timeouts: a connection dropped mid-response (`ConnectionReset`, `RemoteDisconnected`, `IncompleteRead`) is the same situation for the caller.
- **`unreachable`** — the request never got out the door (DNS failure, connection refused, no route, TLS failure). Every leaf of a bisection tree would fail identically, so the **whole batch** fails at once. Without this, one unreachable batch of `BOXES_PER_REQUEST` boxes became ~78 doomed requests at up to `SOCKET_TIMEOUT` apiece — a multi-hour hang with `processed` stuck at 0.

`classify()` is an explicit ordered `isinstance` chain rather than a stack of `except` clauses, because two ordering traps decide the whole thing: **`HTTPError` is a subclass of `URLError`** (test it first or every HTTP status reads as a connection failure), and **`socket.timeout` *is* `TimeoutError` on Python 3.10+, which subclasses `OSError`** (test it before any generic errno handling). A `URLError`'s `.reason` is recursed into through the same table, so the wrapped and directly-raised forms of one failure can never disagree.

**Getting that second trap wrong is the bug this all exists to fix.** The old code was `except HTTPError: retry+bisect` / `except Exception: fail the batch as unreachable`, so a read timeout from a slow-but-reachable mirror was reported as unreachable. `CONNECTIVITY_FAIL_LIMIT` (2) consecutive unreachable batches then trips each worker's circuit breaker, which counts **every remaining batch as failed** and sets `processed = total` — making `failed >= total`, the exact condition the admin panel used to print "could not reach Overpass for any area". Two slow queries reddened an entire run on a server that could reach Overpass perfectly well. POI had it worst: it had forked its own tighter `[out:json][timeout:30]` + 35s socket budget while roads used 60/80, and its 15km all-tags query is the heaviest the app makes, so it timed out on essentially every city (1,102 of them on a real instance).

Because `timeout` now reaches the bisect path, **`MAX_TIMEOUT_BISECT_DEPTH` (2) caps timeout-driven bisection** — each leaf can cost a full failover walk across the pool, so an unbounded tree would recreate exactly the stall described above. `http` keeps bisecting unbounded. `_download_boxes` returns `unreachable` and the failing `OverpassResult` alongside its counts, and bisection propagates the deepest non-empty error (`le or re_`).

**Endpoints are a pool, not a single URL.** `overpass_query` walks the configured endpoints in order, advancing to the next on `timeout`/`unreachable` — but **not** on an `http` answer *about the query*, because there the server did answer and asking three more mirrors the same oversized question only earns three more rate limits. The exception is `_FAILOVER_STATUSES` (500/502/503): a **mirror-down** status from a reverse proxy says nothing about the query, and stopping there is how a pool whose *first* endpoint is having a bad day fails every batch while a healthy mirror sits untried two lines below it. Those continue the walk, recorded as `timeout` — reached-but-no-usable-answer is what that bucket means, it keeps a pool-wide outage out of the connectivity circuit breaker (the endpoints *were* reached) and it caps the bisect depth, while the message keeps the real HTTP status so the admin panel still names what happened and where. The endpoint that last worked is remembered (`overpass:last_good`, 1h) and tried first, so a run doesn't re-pay a dead endpoint's cost on every request. Crucially, **a query is only reported `unreachable` when *every* endpoint was** — if even one was reached-but-slow the aggregate is `timeout`, so a single slow mirror can never trip a worker's connectivity circuit breaker. `beat()` fires before **every endpoint attempt**, not once per batch: a walk across a four-endpoint pool can cost `4 x SOCKET_TIMEOUT`, well past `STALE_AFTER_S` (240), and a status poll in another gunicorn worker would otherwise declare the run dead and start a second.

Resolution order: **`SiteConfig.overpass_urls`** (migration `0076`, newline-separated, edited from **Admin Panel → Downloads**) wins **outright** when non-blank — an admin who typed a list made an explicit choice, and quietly appending public mirrors underneath it is the surprise the field exists to remove for an instance running a private Overpass. Blank falls back to `settings.OVERPASS_URLS` (env `OVERPASS_URLS`, else a built-in pool), with the legacy singular env `OVERPASS_URL` **prepended** if set, so an existing `.env` keeps its chosen mirror as primary and gains the rest as free fallbacks. Resolution is cached (`overpass_endpoints`, 1h, busted on save, mirroring `get_contact_email()`). The Admin Panel editor renders the **effective** list (`resolved`), not the stored text, so the built-in defaults are reorderable and removable like anything else rather than being invisible until someone retypes them by hand — and because blank means "use the pool", any edit necessarily saves the full explicit list, or a deleted default would simply come back. `MAX_ENDPOINTS` (12) caps it, since each endpoint is a potential attempt on every request. `overpass_test_api` accepts an optional `endpoints` list so an admin can probe a reordered list before saving it. It lives in `SiteConfig` rather than env-only because **`docker-compose.yml` is gitignored and enumerates its env vars explicitly**, so adding one to `.env` alone never reaches the container — which is what made "just point it at a working mirror" a much bigger job than it sounds.

The built-in `DEFAULT_POOL` **deliberately omits the official `overpass-api.de`**: it enforces a fair-use policy and **refuses connections outright** (TCP-level, on every one of its IPs) from an IP it judges abusive, so on such a network it is a guaranteed failed attempt on every request. Add it back at the top of the list from the Admin Panel if the server can reach it.

**Every endpoint in the pool must be a *world* instance, and a regional extract is worse there than a dead one.** It doesn't fail — it answers **HTTP 200 with an empty `elements` list** for anything outside its own region, which a download cannot tell apart from "this cell genuinely has no subway". The run therefore stores nothing, counts **zero failed boxes**, and — since a batch with no failures is a batch that succeeded — `_mark_covered` writes every one of its cells into `DownloadedRegion`, so the area is **never asked about again** and every retry is a no-op too. `overpass.osm.ch` was in `DEFAULT_POOL` and is Switzerland-only; that is exactly how a Montreal metro download came back with 0 segments and 0 stations and then stayed that way. Removing it from the constant is not enough on its own — the Admin Panel renders the *effective* pool, so any save writes the full explicit list into `SiteConfig.overpass_urls`, which then wins outright — hence migration `0078` strips it from a saved list too (same shape as `0072` resetting profiles that had explicitly picked Valhalla). **Recovering an instance already poisoned this way means deleting the data**, since the coverage rows are what suppress the retry: the three delete endpoints clear the matching `DownloadedRegion` rows, so Admin Panel → Downloads → **Delete Subway Data** then re-download is the fix.

All three status endpoints report **`covered`** (the `DownloadedRegion` row count for that kind) for exactly this, because a run that builds **zero batches** has three completely different causes that used to render as one message ("no location points to cover yet"): no history at all (`covered == 0`), an incremental run that legitimately found nothing new (`covered > 0`, data stored), and the poisoned state — `covered > 0` with **nothing stored**, which is a silent dead end that suppresses every future retry. `dlUpdateUI` now names each one, and the third in red with the specific Delete button to press.

The endpoint test also reports when two entries **resolve to the same machine** (`_mark_shared_hosts`, matched on resolved IPv4/IPv6): two names on one box are one endpoint's worth of redundancy, not two, and they go down together. `overpass.kumi.systems` and `overpass.private.coffee` share an identical A *and* AAAA record, so a four-entry pool watching both return 502 at the same moment is watching one server have a bad day. Resolution failures are silently ignored — it's an advisory note, not an accusation.

`overpass_test_api` catches this class of mirror, because nothing else can: after the reachability probe it runs a second **`COVERAGE_QUERY`** for `place=city` nodes in Paris, New York and Tokyo (`COVERAGE_ANCHORS`), reporting `world` (all three), `partial` (a regional extract — flagged in red as "remove it") or `unknown`. It is deliberately a *separate* request from `PROBE_QUERY` rather than a replacement: it walks a bbox index instead of fetching one object by id, so a loaded mirror can time out on it while being perfectly usable for real downloads — and so its own failure reports `unknown` and says nothing, never failing the endpoint.

**Diagnostics.** Each job row carries `last_error`/`last_error_kind`/`last_error_endpoint` (migration `0077`, operational ⇒ **excluded from backups**), written on every progress update **and in the circuit-breaker back-fill** — that is the write the "everything failed" screen actually reads — cleared at run start and exposed by all three status endpoints including their idle payloads (or the UI reads `undefined` on a fresh instance). `admin_panel.html`'s `dlUpdateUI` keys its message off the kind, so "no endpoint reachable", "every endpoint too slow" and "every request rejected" read differently and each names the host. **`POST /api/site/overpass-test/`** (`overpass_test_api`, admin-only) probes every endpoint **concurrently** — deliberately not the failover walk, since the point is a per-endpoint verdict including ones a real request would never have reached. Its `PROBE_TIMEOUT` is a generous 30s on purpose: a mirror needing 20s for a trivial query is still usable at `SOCKET_TIMEOUT`, and failing it at a tight 15s would tell an admin to remove an endpoint that works — it is flagged `slow` (`PROBE_SLOW_MS`) instead. `GET/POST /api/site/overpass/` (`site_overpass_config_api`) reads/saves the list.

The road/subway/POI/transport/stats progress bars in Settings previously prefixed their status text with `.spinner` (a `border-top-color` circle), which reads misaligned next to text — `inline-block` defaults to baseline vertical-align, so the spinner's centre sits below the text's. The road-download bar (`#roads-bar`) instead gets a `.bar-flow` class while active: a diagonally repeating gradient (`--primary`/`--primary-hover`) animated via `background-position`, applied to the bar's own fill rather than a separate icon next to the text, so there's no alignment to get wrong. Removed via `classList.remove('bar-flow')` (and the bar's inline `background` explicitly cleared first, since an inline style always wins over a class's `background-image` regardless of shorthand/longhand) once the run finishes, replaced by a flat `--success`/`--text-muted` fill. Respects `prefers-reduced-motion`. Pure template change — no rebuild/migration.

The run is owned by a **`RoadDownloadJob.worker_token`** (migration `0053`). `_running_threads` is per-process, so with several gunicorn workers the liveness check cannot see a thread running elsewhere: a status poll in another process concluded the run had died and started a second worker, each keeping its own progress counter and overwriting the other — the reported percentage climbed, then jumped backwards, then stalled. Every progress write is now conditional on the token, `_claim()` mints a fresh one on start (retiring any straggler), `stop` clears it, and the worker `return`s as soon as the row stops naming it. A `_beat()` callback touches `updated_at` between Overpass attempts **and during the history scan** so a slow-but-healthy phase is never mistaken for a dead one, and `STALE_AFTER_S` (240) is comfortably above the worst case for a single batch.

`_visited_boxes` scans **one device at a time** ordered by timestamp. A single global `order_by('device_id', 'timestamp')` cannot use `tracker_loc_device__idx` (which is `('device', '-timestamp')`), so Postgres full-sorted every row before yielding the first — the slowest thing the job does, running before any progress exists to report. The scan finishes before `total` is known, so the status endpoint reports `phase='scanning'` while `total` is still 0 and the UI says so explicitly rather than showing a frozen `0/0`. Geometry is stored **unsimplified**: a junction is recognised by its coordinate, and a simplifier can't know which vertices are shared. **Storage is roughly 5-9 KB/km²**. Road data is wiped from Settings → Background Jobs → **Delete Road Data** (`TRUNCATE`, instance-wide reference data with no user FK, like `POI`/`Boundary`).
