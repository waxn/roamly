# Summary emails and tracking alerts

_Read when: AI summary emails, unsubscribe, no-data alerts._

**AI summary emails (opt-in, per-user).** When an instance has SMTP (`EMAIL_ENABLED`) *and* the user's AI Ask provider is configured (`UserProfile.ai_configured`), the user can opt into **daily / weekly / monthly / yearly** recap emails (independent cadence flags `summary_daily/weekly/monthly/yearly` on `UserProfile`, migration `0046`). `tracker/summary_email_tasks.py` mirrors `stats_tasks.py`: a daemon thread from `apps.ready()` sweeps hourly, `close_old_connections()` each pass, and for each opted-in user sends any cadence whose `summary_last_<period>` cursor predates the current period boundary (`_period_bounds` computes previous day/week/month/year windows in **server localtime**; restart-safe, no external cron, no duplicate sends). Single-flight per user via a PG **advisory lock with its own namespace** `0x52414d53` ('RAMS', distinct from stats' 'RAML'). Stats reuse the queryset helpers `_compute_overview_from_qs`/`_compute_distance_from_qs` (date-filtered qs, converted to the profile's `distance_unit`). Empty periods skip the email but still advance the cursor.

**The cursor stores the period's boundary, not the send time, and "already delivered" is a 12h tolerance (`_SAME_PERIOD_TOLERANCE`), not an exact `>=`.** The boundary is a local midnight in the zone of the user's newest fix, so it moves when they travel: after a flight from Virginia to Chicago, "today began" moved from 04:00Z to 05:00Z, the 00:22 EDT stamp (04:22Z) predated it, and yesterday's recap went out a second time at 13:21. Consecutive periods' boundaries are always ≥ 23h apart, so a stamp within 12h of the current boundary is the same period seen from another zone. Zone jumps over ~11h (a transpacific flight) can still skip one recap. The profile is also loaded **inside** the per-user advisory lock, so a worker can't act on a copy read before another worker stamped the cursor.

**Narrative + top cities/places.** Each email carries a short **AI-written narrative** — two dedicated prompts, deliberately *not* the Ask tab's Q&A prompt: `SUMMARY_SYSTEM_PROMPT_DAILY` is handed an actual chronological stay timeline (`_stay_timeline`, built from the period's `Visit` rows — pass-through stays are dropped (unmatched < 10 min, matched business < 4 min), consecutive same-place stays merged, and each line carries part of day + duration; the labels name the business first, "Hannaford in Bangor, ME"; **travel days** (`_journey`: first and last real stay >100 km apart) keep only 30 min+ stays plus the first/last, and hand the model a `journey` (started/ended/states crossed) with `_JOURNEY_RULES` telling it to narrate a trip and treat fuel/food/scale stops as colour (also used by the Journals recap and the header's year-ago line); both prompts share `_STYLE_RULES`: warm friend-like prose, 3-5 sentences, never mention towns merely passed through — labelled by matched POI, else `place_name`, else city — across all the user's devices, `_period_visits`) and told to narrate the day's real sequence ("you went to X in the morning, then spent the afternoon near Y"); `SUMMARY_SYSTEM_PROMPT_PERIOD` (weekly/monthly/yearly) is grounded in a **top cities / top places** ranked breakdown instead of a day-by-day rundown, which would be unreadable over a month. Both demand one short, concrete paragraph — no markdown, no invented facts. `_top_cities` re-sorts `_compute_visits_from_qs`'s per-city `time_spent` descending; `_top_places` groups the same `Visit` rows by POI id (else a ~111m lat/lon grid, matching the fog-of-war cell precision) and sums dwell time, so repeat stays at one spot collapse into one ranked entry. Both lists are also rendered in the email itself via `email_utils._ranked_list()` (numbered rows, alongside the existing `_stat_grid()` tiles), and fed as JSON to whichever prompt applies (`ai_tasks._provider_chat(profile, messages)`, no tools; `AIProviderError` → stats-only fallback). The email also links to `{SITE_URL}/map/?start=&end=` (boxed primary button) and `{SITE_URL}/stats/?start=&end=` (`email_utils._link()`, lighter secondary link) scoped to the period's date range — background threads have no `request` to call `build_absolute_uri` on, hence `settings.SITE_URL`.

Email built by `email_utils.send_summary_email()`. Config/endpoint: `GET/POST /api/profile/summary-email/` (`profile_summary_email_api`, `@login_required`) — GET returns flags + `available` (email+AI both set); POST saves the four toggles, or with `{"test":"daily"}` fires an immediate test send (`summary_email_tasks.send_summary_now`, bypasses due-check, doesn't advance the cursor). Settings → **Summary Emails** card (only shows cadence toggles when `summary_available`, else a "needs SMTP + AI" note). Summary prefs are config ⇒ **excluded from backups** (like AI config), no `meta.version` bump. **New model fields ⇒ build + migrate.**

**Distance unit in emails.** `roamly_speed_unit` (`kmh`/`mph`) is otherwise a pure client-side localStorage preference (see User-facing preferences below) — the summary-email scheduler runs in a background thread with no browser to read it from. `UserProfile.distance_unit` (migration `0058`, same `'kmh'`/`'mph'` values) is a server-side mirror written by `saveSpeedUnit()` in `settings.html` via `GET/POST /api/profile/distance-unit/` (`profile_distance_unit_api`) alongside the existing localStorage write — the map/stats pages are untouched, still localStorage-only. `summary_email_tasks._format_distance(km, unit)` converts the stat-tile figure and the JSON handed to the AI narrative.

**Unsubscribe (no login required).** Every recap email carries a "Manage email preferences" link built from `UserProfile.email_unsub_token` (migration `0057`, lazily minted by `email_utils._ensure_unsub_token` on first send — `null=True` so untouched profiles don't collide on the unique constraint, same trick as `Adventure.invite_token`). `email_unsubscribe_view` (`/email/unsubscribe/<token>/`, `email_unsubscribe.html`) looks the profile up by token — the token *is* the credential, same trust model as the password-reset link. A GET carrying `?period=<cadence>` (what the email link points to) one-click-flips just that cadence off before rendering the full 4-checkbox form for further changes; a plain POST saves all four at once. Links are built with `settings.SITE_URL` (`.env` `SITE_URL`, meant exactly for absolute links from request-less background threads — the summary scheduler has no `request` to call `build_absolute_uri` on).

**Tracking alerts ("no data received").** An opt-in email when Roamly stops receiving location data — the failure users actually hit, a phone that quietly stopped tracking after an OS update, an OEM battery manager, or a force-stop, which is otherwise invisible until you open the map days later and find a hole. Config on `UserProfile` (`alert_no_data_enabled` default **False**, `alert_no_data_hours` default **3**, plus the `alert_no_data_last_point`/`alert_no_data_sent_at` cursors; migration `0073`), edited from the **Tracking Alerts** card in Settings (`GET/POST /api/profile/alerts/`, `profile_alerts_api`).

Gated on `EMAIL_ENABLED` + the account having an address, but **deliberately not on `ai_configured`** the way the summary emails above are — this is a plain operational notice with nothing to narrate, so requiring a BYO LLM to receive it would be absurd. `tracker/alert_tasks.py` mirrors `summary_email_tasks.py`: a daemon thread from `apps.ready()`, `close_old_connections()` each pass, single-flight per user via a PG **advisory lock with its own namespace** `0x52414d41` ('RAMA', distinct from stats' 'RAML', summary's 'RAMS', log-cleanup's 'RAMG' and auto-download's 'RAMD'). The sweep runs every **15 minutes**, not hourly like the recap scheduler — the interval bounds how late an alert can be, and the minimum threshold a user can pick is 1 hour, which an hourly sweep could deliver nearly 2 hours late. `clamp_hours` bounds the threshold to 1–168h at both the API boundary and again in the worker, since the value rides in from the client.

**The alert is account-wide, not per-device**, and that is the load-bearing choice: `latest_fix(user)` takes the newest fix across *all* the user's devices, because a retired device that will never report again would otherwise alert forever. It queries **one device at a time** rather than a single user-wide `aggregate(Max)` — `tracker_loc_device__idx` is `(device, -timestamp)`, so a per-device ordered lookup is an index seek while a user-wide aggregate has no matching index and degrades into a scan on a large history, which this sweep would then pay every 15 minutes.

**One email per outage**, via `alert_no_data_last_point` — it records the newest fix at the moment the alert went out, so the sweep skips a user whose newest fix is still the one already alerted about, and **re-arms by itself** as soon as a newer point lands (tracking resumed, so the next silence is a genuinely new outage). No separate "recovered" flag to keep in sync, and nothing to reset by hand. An account that has **never** logged a point returns `no-data` and is never mailed — otherwise every freshly-created account that ticks the box would be alerted immediately, before it had pushed anything. Saving a changed toggle or threshold clears the cursor, so a threshold the user just lowered is re-evaluated against the current outage from scratch rather than being suppressed by a cursor left over from the old settings. A send that fails (SMTP outage) doesn't stamp, so the next sweep retries.

Both card controls **autosave on change** (no Save button — the whole point is a switch that's actually on when it looks on, the same reasoning as the Road Snapping master switch), and "Send test" (`send_alert_now`) previews the real mail against the user's current data, bypassing the enabled flag, threshold and dedupe without advancing the cursor. The email itself (`email_utils.send_no_data_alert_email`) carries no AI narrative and no stats — just how long it's been silent, when and from which device the last fix came, and links to the map and Settings. Alerts share the recap emails' unsubscribe page: `email_unsubscribe_view` now also saves `alert_no_data_enabled`, and `?period=alerts` (`_ALERTS_PERIOD`, kept out of `_SUMMARY_PERIODS` since alerts have no cadence and drive no `summary_*` field name) one-click-disables them. Alert prefs are config ⇒ **excluded from backups** (like AI/summary config), no `meta.version` bump. **New `UserProfile` fields ⇒ build + migrate.**
