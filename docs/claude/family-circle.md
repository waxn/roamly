# Family Circle

_Read when: Family circles, geofences, FCM push, Simple Mode._

## Family Circle

A self-hosted answer to Life360/Paralino — a mutual location-sharing group where every accepted, sharing member sees every other member's live location and shared places, and gets notified when someone arrives at or leaves one. Nothing like this existed before: `CustomPlace` is private/per-user with no enter/exit detection at all (membership is always computed lazily, never by watching a transition), and the only prior cross-user location-sharing precedent was `AdventureMember`'s time-boxed, owner-chosen-window sharing — Family Circle borrows that model's hard-won consent shape (below) but is otherwise a new, open-ended, peer-to-peer feature (migration `0086`).

**Models.** `FamilyCircle` (name, creator, lazily-minted `invite_token`, same shape as `Adventure.invite_token`). `FamilyMembership` — a direct structural copy of `AdventureMember`'s post-migration-`0082` consent fields: `accepted_at` (NULL = invited, not consented — nothing about this member is visible to the circle until they accept) and `share_location` (accepting an invite is not itself consent to broadcast a live position; also gates whether the geofence checker evaluates this member at all). **Invite-by-link only** — there is deliberately no add-by-username endpoint, since that unilateral-add shape is exactly what caused `AdventureMember`'s old unbounded-disclosure bug (migration `0082`), and this feature has no reason to reintroduce it. `FamilyPlace` — a circle-scoped geofence, deliberately **not** a retrofit of `CustomPlace` (private/per-user, and every existing consumer — `_place_membership`, the data table, search — assumes single-owner semantics); self-serve, so any accepted member may create one, not just the circle's creator. `FamilyPlaceAlert` — one member's own enter/exit subscription for one place, **opt-out not opt-in**: both flags default `True` on the model, and `family_tasks._notify` treats every accepted member as subscribed at those defaults unless they've explicitly saved a row turning a direction off — self-serve alerting is only useful to a non-technical family member if it works before they've found a settings screen. `FamilyMemberPlaceState` — the enter/exit transition-state cache (`is_inside` per member+place), a derived cache excluded from backups like `StatsSnapshot`. `FamilyPushToken` — one registered FCM token per app install, not an FK to `Device` (registration can race ahead of a device's first location push, and a family-only member may never enable GPS tracking at all); excluded from backups like `APIKey.key`.

**Geofence detection is event-driven, not swept.** `tracker/family_tasks.py`'s `ensure_family_geofence_check(user_id, fixes)` is kicked from `push_location`/`push_location_batch` right after the existing `ensure_auto_geocode(user.id)` call — a fire-and-forget daemon thread, same spawn shape as that geocode trigger, but **not debounced**: the whole check is a couple of small indexed queries plus in-memory haversine against a handful of places (the same "a user has only a handful of these" cost assumption `CustomPlace`'s own docstring makes), genuinely cheaper than the geocoding trigger it sits next to. `push_location_batch` evaluates **only the newest fix per device in the batch** — a reconnecting phone draining a day's offline backlog must not replay a day of enter/exit events — and both hooks skip fixes older than ~10 minutes vs. `now()`, since an alert about somewhere the phone was hours ago is actively misleading. A transition compares the fix against `FamilyMemberPlaceState`: **no existing row seeds silently, never notifies** (mirrors `alert_tasks`' "never tracked anything ⇒ never mailed" guard) — otherwise a brand-new member's first push, or a place created while a member already stands inside it, fires a fake "entered" event. The state upsert on a real transition is wrapped in `select_for_update()` to guard a genuinely concurrent single-push + batch-push race. A 15-minute reconciliation sweep (`start_family_scheduler`, wired into `apps.py` alongside the other seven schedulers, advisory-lock namespace `0x52414d46` — 'RAMF', the next untaken tag after stats 'RAML', summary 'RAMS', log-cleanup 'RAMG', auto-download 'RAMD', alerts 'RAMA') is the safety net for a dropped thread or a newly-created place, not the primary delivery path — "kid left school" can't wait up to 15 minutes.

**Push delivery: Firebase Cloud Messaging, admin-configured per instance.** `tracker/push_tasks.py` signs FCM HTTP v1 API requests from a service-account key via `google-auth` (`google.oauth2.service_account.Credentials` + `google.auth.transport.requests.Request`) — deliberately not `firebase-admin`, which pulls in Firestore/Storage/Auth client libraries this app never touches for what is really just "mint an OAuth2 token, POST it"; `requests` (already a dependency) does the POST. `SiteConfig.fcm_service_account_json` (migration `0087`) is **masked** like `turnstile_secret_key`, not unmasked like `carto_api_key` — this is a server-signing secret, not a client-embedded tile key, and is never added to a context processor. `fcm_project_id` is parsed out of the JSON at save time so sends don't re-parse it. Edited from **Admin Panel → Push Notifications** (`POST /api/site/fcm/`, admin-only), same masked-secret save pattern as `site_turnstile_api`. Sends are **data-only** (no top-level `notification` block) — the only way `onMessageReceived()` reliably fires app-side regardless of foreground/background/killed state, so notification-building and deep-linking stay consistent instead of the OS tray sometimes intercepting a mixed payload directly. Best-effort per token, no retry queue, matching `alert_tasks`' existing posture for outbound notifications ("a send that fails doesn't stamp, the next sweep retries") — a dead-registration response (404/`UNREGISTERED`/`INVALID_ARGUMENT`) deletes that `FamilyPushToken` row, anything else just logs to `last_error`. Config only ⇒ **excluded from backups**, no `meta.version` bump for the `SiteConfig` fields themselves.

**The officially-distributed mobile APK needs a matching `google-services.json` baked in at CI build time** — a new optional `GOOGLE_SERVICES_JSON_BASE64` GitHub Actions secret, decoded into `mobile/app/google-services.json` before `assembleRelease` and removed after, alongside the existing keystore-decode step (`.github/workflows/mobile-release.yml`). `com.google.gms.google-services` is applied **conditionally** in `app/build.gradle.kts` (`hasGoogleServices = file("google-services.json").exists()`) — mirrors the existing `hasUploadSigning` pattern for release signing exactly: a build with no Firebase credentials must still succeed, just push-disabled, never fail outright. For the official build the Firebase project is the maintainer's own (message routing only, no user data stored there); a self-hoster building their own APK must supply both their own `google-services.json` *and* the matching service-account JSON in their instance's Admin Panel together — they're two halves of the same credential pair.

**Web endpoints.** Invite/join mirrors `trip_join_view` exactly: `family_join_view` (`/family/join/<token>/`) is a **POST-gated confirm page** (`family_join.html`, standalone template, own token block + `CUSTOM_JS_SNIPPET` injection like `adventure_join.html`) that explains what accepting means *before* recording consent — never a state-changing GET, the same lesson `AdventureMember`'s old bug already taught. `/api/family/circles/` (list/create), `/api/family/circles/<id>/` (detail incl. places), `/{rename,delete}/` (creator-role only), `/invite/` (mint/rotate, any accepted member), `/leave/`, `/members/<user_id>/remove/` (creator-role only), `/api/family/share/` (the caller's own `share_location` toggle, autosave). Places: `GET/POST /api/family/circles/<id>/places/` (self-serve — any accepted member, not creator-gated), `POST /api/family/places/<id>/{update,delete}/`. Alerts: `GET/POST /api/family/places/<id>/alerts/` (caller's own subscription only). Live map: `GET /api/family/circles/<id>/locations/` — a new query path scoped to circle membership, not a parameter bolted onto `/api/track/`, which is scoped to `device__user=request.user`, a fundamentally different authorization axis. Push token: `POST /api/family/push-token/` (idempotent register, replaces any prior row for the same `(user, device_label)` pairing) and `/unregister/`.

**Backup**: `FamilyCircle`/`FamilyMembership`/`FamilyPlace`/`FamilyPlaceAlert` are user content and join the format (`meta.version` 14 → 15) — `backup_tasks._build_family_data(user)` exports circles the user **created**, with their full member/place/alert set, the same "you back up what you own" shape `_build_adventures_data` already has (a member's own backup does not carry their membership in a circle someone else created, exactly like a shared Adventure they didn't create). `restore_backup` applies `AdventureMember`'s exact consent rule: only the restoring account's own membership may restore as accepted, every other member restores pending regardless of what the backup file claims, since a backup is attacker-authored input from the restoring user's point of view. `FamilyMemberPlaceState`/`FamilyPushToken` stay excluded (operational).

**Mobile (`ui/family/*`).** `FamilyScreen` is the single entry point, reached from a **Settings card** ("Family Circle") in both Simple and Advanced Mode — no dedicated bottom-nav tab (the bar is full at six), the same reasoning `Record` uses, implemented the same swap-in-place way Health/Diagnostics/Location Data already are rather than as a NavHost route. Internally it hosts three segmented tabs — **Map** (`FamilyMapScreen`, osmdroid, one dot + short trail per sharing member, `MEMBER_TRACK_COLORS` — the same palette Adventure member tracks use), **Places** (`FamilyPlacesScreen` — `CustomPlace` has no mobile UI at all today, so this whole surface is new: a tap-to-drop-a-pin map for creating a place, since a non-technical family member should never have to type coordinates, plus per-place opt-out alert toggles), **Circle** (`FamilyCircleScreen` — member roster, share-location switch, invite mint/copy/share via Android's share sheet, leave/remove/rename/delete) — mirroring how `SearchTabScreen` already hosts Ask/Search internally rather than adding more top-level routes. `FamilyPushService` (`FirebaseMessagingService`) registers the FCM token on rotation, gated behind `AuthRepository.ensureApiKey()` — the same guarantee Health's setup flow already needed, since a family-only user who never started GPS tracking would otherwise have no API key.

**Simple Mode.** A reduced bottom nav — `[Map, Settings]` instead of the full six — for a non-technical family member, toggled from a Settings card and reversible from Settings in either mode. `UserPreferences.simpleModeEnabled` drives `RoamlyNavHost`'s item set reactively (`AuthViewModel.simpleModeEnabled`, reusing that already-`prefs`-holding ViewModel rather than adding a second one for one boolean) — no restart needed. Turning it on also force-enables **adaptive interval** in the same DataStore edit, so the target user never has to separately discover a second checkbox.

**Adaptive interval** (`UserPreferences.adaptiveIntervalEnabled`, a general Settings toggle anyone can opt into, not hardcoded to Simple Mode — matching this codebase's habit of generalizing behind a config flag rather than special-casing). Swaps `LocationTrackingService`'s alarm cadence between two fixed constants — `ADAPTIVE_MOVING_INTERVAL_MS` (60s) and `ADAPTIVE_STATIONARY_INTERVAL_MS` (300s) — by the last real fix's cleaned (jitter-dropped, spike-corrected) Doppler speed against `MOVE_SPEED_MPS` (widened from `private` to top-level-visible in `DriftAnchor.kt` so this reuses it rather than inventing a third "is this real movement" threshold). Structurally different from the existing `activitySession` override: that input (`prefs.activitySession`) is known at config-build time and fits cleanly inside `observeConfig()`'s `combine()`, but adaptive interval's input — a live speed reading — is only known *after* a fix lands, so `effectiveIntervalMs(cfg)` reads `lastFixSpeedMps` at the point the cadence is actually computed (both `alarmIntervalMs` and the stream-freshness check in `runFixCycle`) rather than baking a value into `TrackingConfig` up front. Recording always wins over adaptive mode — a live ride's fixed 2s cadence is a stronger, more deliberate override. Fixed bounds, not user-tunable, for v1 — avoids a second knob interacting with the ordinary `trackingIntervalSecs` setting.

**New models + `SiteConfig` fields ⇒ build + migrate; new mobile dependency (`google-auth` server-side has no mobile equivalent — the mobile side adds `firebase-messaging-ktx`) ⇒ rebuild; mobile change ⇒ rebuild APK + tag.**
