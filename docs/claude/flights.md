# Flights

_Read when: Flight log, boarding passes, track matching, OpenSky, AeroDataBox, detected flights._

**Flights** (`/flights/`, `flights_view` → `flights.html`, migrations `0102`–`0107`; also in the app, see **Mobile Data tab + boarding-pass scanning**). An AirTrail-style personal flight log: **List** (sortable table; each flight number links to `https://www.flightradar24.com/data/flights/<number>`, carried as `fr24_url` in the payload), **Map** (MapLibre, flights only: great-circle arcs interpolated in JS with longitudes **unwrapped** so a transpacific route is one continuous line rather than a stripe across the map, weighted by how often the route was flown; airport dots sized by visits; click either for details) and **Stats** (distance, time aloft, airports, airlines, countries, multiples of the Earth/Moon distance, flights per year, top airports/routes/airlines, class/reason, records, and an **Aircraft** section: types, families, manufacturers and individual tails flown, most flown types/families/manufacturers, tails flown more than once, and per-type distance/time records — the family is the model without its variant, `Boeing 737-800` → `Boeing 737`, the same rule in `acFamily` on web and app), all **computed client-side from the list**, which is small. Tabs deep-link by hash; a year filter applies to all three (the per-year chart always spans every year). Distance respects `roamly_speed_unit`.

`Flight` stores **both airports denormalised** (code, name, city, country, position, IANA zone), so a flight never depends on a lookup table changing underneath it and a backup restores it whole; `distance_km` is the great-circle airport distance recomputed in `save()`. It is **not** linked to `Location` and no GPS aggregate reads it. **Times are entered as each airport's wall clock** (what a boarding pass prints): the API accepts an aware ISO instant (`sched_dep`, what the lookup supplies) *or* a naive `sched_dep_local` read in that airport's zone, stores UTC, and returns both. `_apply_flight` is the single validator, used by create, update **and backup restore**. A typed code is filled from the bundled airport data (`tracker/airports.py`, a lazy singleton over `tracker/static/tracker/data/airports.json` — ~9.7k OurAirports rows `[iata, icao, name, city, cc, lat, lon, size]` (size 2 large / 1 medium / 0 smaller), every IATA code plus large/medium fields, built by `scripts/build_airports.py`, a plain no-Django script, and committed); the zone comes from `tz_utils.zone_name_for_point`. The browser loads the same JSON lazily for airport autocomplete. Endpoints (`@login_required`, owner-scoped, CSRF via `X-CSRFToken`): `GET/POST /api/flights/`, `POST /api/flights/<id>/update/`, `/delete/`.

**Boarding-pass details** (migration `0105`). A flight also keeps what a scanned boarding pass carries: `booking_ref`, `passenger_name`, `checkin_seq`, `ticket_number`, `frequent_flyer`, `bcbp_raw` (the barcode text verbatim, so nothing the parser skipped is lost) and `boarding_pass_image`; `source` gains `boarding_pass`. The web shows them under a collapsed **Advanced** section of the flight form, with the photo viewable, replaceable and removable. **The booking reference can manage the booking**, so the photo is served only through the owner-checked `GET /api/flights/<id>/pass/` (`flight_pass_api`, `no-store` + `nosniff`) and is never linked by its `/media/` path; `POST` there (multipart `image`, through `resize_photo` at 2000px so the barcode stays legible) replaces it and `POST /api/flights/<id>/pass/delete/` removes it. The flight write endpoints are the **app's too**, so they are `@csrf_exempt` + `_require_api_intent` like its other writes. **Creating a flight already in the log** (same number, date and route) returns **409 `{existing_id}`** unless `allow_duplicate` is sent — scanning one pass twice must not log the flight twice; the app answers with "Update it". Backup **v22** carries the pass fields and the photo path, and the photo travels in the zip's media tree; restore re-links a photo only when its path matches `_BOARDING_PASS_PATH_RE` (exactly what `resize_photo` writes), so a crafted backup cannot point a flight at another account's file.

**Recorded tracks** (migration `0106`). A logged flight is linked to its recording in the owner's history when there is one — the phone logging in the air, or a Flightradar24 KML imported through `/api/import/kml/` (those are ordinary `Location` rows). **The link is a device + window** (`track_device`, `track_start`, `track_end`), never copied points, so editing or deleting the points can't leave a stale duplicate; `track_distance_km` is the distance along the recording, beside `distance_km` (airport to airport). `flight_detect.match_track` searches the flight's time window (actual/scheduled times ±3h, or the departure-local day + 34h when there are none) on every device, and **anchors on the airports rather than on fast-hop runs**, because one duplicate fix (speed 0 between identical timestamps) splits a run: the track is the last point nearest the departure airport to the first point nearest the arrival airport after it, "near" being 30 km or 15% of the route (so a KML that starts already airborne still matches), with at least 5 points and 3 hops at flight speed; across devices **the densest recording wins** and endpoint closeness only breaks ties (a phone that caught a few fixes at the gates sits nearer the airports than a KML starting on the runway, and choosing it drew a 5-point line instead of the import) (a phone switched off for the flight is not a recording; a drive between the same airports fails the speed test). The match is then **extended through taxiing on the same device** (`_extend_taxi`): its ends are roughly the takeoff roll and final approach, so it walks outwards through the continuous ground movement at each airport (within `TAXI_RADIUS_KM` 8 km, no gap over 5 min, at most 45 min) and stops where the aircraft comes to rest (3 hops under 0.7 m/s — the gate), ending at the last moving point; no upper speed limit there, since the ends are often still at flight speed. The terminal walk and the drive home stay out. Takeoff/landing times are taken from the unextended core. Dense sampling (≤5 min hops) also fills a **blank** `actual_dep`/`actual_arr` from the first and last fast hop — never over AeroDataBox or the user. Matching runs on create, and on an update only when the flight has no track yet or the edit changed what matching depends on (`_flight_track_key`: date, airports, times) — re-matching on every save could swap or drop a track the user is happy with (`_match_flight_track`, best-effort, never fails the save). **Match tracks never touches a flight that already has one** (`track_device__isnull=True`); `POST /api/flights/<id>/track/` re-matches (overriding an unlink; the **Re-match track** button under Advanced on web and app), `/track/unlink/` detaches and sets `track_auto=False` so later saves leave it alone, `POST /api/flights/tracks/match/` matches every unlinked flight (for flights logged before their points were imported), and `GET /api/flights/tracks/` returns every linked track for the maps in one request, longitudes **unwrapped** across the date line and Douglas-Peucker-simplified (`activity_track.simplify`) to ≤400 points each. The web map draws a tracked flight along the recorded path (blue) and keeps the great-circle arc (orange) for a route's untracked flights; the app does the same, re-wrapping longitudes and splitting at the date line because osmdroid can't draw past ±180. Backup **v23** carries the link (device id + window); restore resolves the device through the restore's own `device_map`, so it can only ever point at the user's own points.

**OpenSky tracks** (`tracker/opensky.py`, migration `0107`). For a flight nobody recorded, the track is fetched from the **OpenSky Network** (free, non-commercial). Its track endpoint is experimental and reaches back **only 30 days**, so this runs **on save** (`_kick_opensky` → `opensky.kick`, a `db_thread`, so the save never waits on the network) and on a **three-hourly sweep** (`start_opensky_scheduler` from `apps.ready()`, advisory-lock namespace `0x52414d4b` 'RAMK', `wait_for_app_registry()` first), while the flight is between `SETTLE` (2h after landing) and `MAX_AGE` (29 days); `opensky.due` gates both, with up to `MAX_ATTEMPTS` (6) tries `RETRY_AFTER` (6h) apart. Tracks are indexed by the aircraft's Mode S address, **`Flight.icao24`**, which the AeroDataBox lookup now keeps (`aircraft.modeS`) and Advanced lets the user type; without it the flight is found on `/flights/departure` (the departure airport's list, a **nightly batch**, hence `DEPARTURES_SETTLE` 26h) by callsign (`UAL123` from `airline_icao` + number, or the IATA form) and arrival airport. The waypoints (`[unix_s, lat, lon, alt]`) are stored **on the flight** (`opensky_track`), **never as `Location` rows** — they are not the user's own movement and must not reach their map or distance — with `opensky_status` (`ok`/`pending`/`none`/`too_old`/`no_aircraft`/`error`) and a user-readable `opensky_message`. **Precedence: a recorded track (own points or an uploaded KML) always wins over OpenSky**, which wins over the great-circle route (`track_source` in the payload). An edit that changes the flight (`_flight_track_key` or `icao24`) clears the OpenSky result.

**Auth is OAuth2 client credentials**: the admin creates an API client on their OpenSky account and pastes its **client id + secret** into **Admin Panel → Flight data** (`POST /api/site/opensky/`, the secret masked like `turnstile_secret_key`); the server swaps them for a bearer token itself (`TOKEN_URL`, valid 30 min, cached as `opensky:token` until 2 min before expiry, one re-sign-in on a 401). **Credits are metered per endpoint family** (states/tracks/flights, 4,000/day each for a standard account; a track costs ~30): every response's `X-Rate-Limit-Remaining` is cached **per family** under `opensky:remaining`, and the Flight data tab's header shows the tracks and flights balances from it without spending a call; **Test** spends 4 credits on a live-track request in the tracks family to refresh it. A 429 stops the sweep for the day. Endpoints: `POST /api/flights/<id>/opensky/` (manual fetch, 40/day per account), `GET /api/flights/<id>/track/points/` (the one track that flight's map shows, `{source, coords}`), and **`POST /api/flights/<id>/kml/`** — a flight-form KML upload, parsed by the shared `_parse_kml_upload` (split out of `import_kml`), stored under the `flight-kml` device ("Imported flight tracks") and then force-matched, so it becomes the recorded track ahead of OpenSky. A Flightradar24 KML's **document header** is read too (`_fr24_kml_meta`: flight number from the `IB342/IBE03CY` name; airline, airports, STD/ATD/STA/ATA in UTC — never the ETA — aircraft model + type code and registration from the HTML card), filling **only blank** flight fields and warning instead when it is for a different route. FR24 point descriptions are `<span><b>Altitude:</b></span> <span>35,975 ft</span>`, so the altitude/speed patterns accept **any run of tags** before the value (requiring exactly one closing tag matched nothing, and every FR24 point lost both). `GET /api/flights/tracks/` returns OpenSky tracks for flights with no recording, with a `sources` map. **The flight form ends with a Flight track section** on web and app — **including the Add form** — with a mini map (recorded blue, OpenSky purple, great-circle dashed orange), where the track came from, and three ways to get one: **Find track** (OpenSky), **Upload file** (`_read_track_upload`: KML/KMZ through `_parse_kml_upload`, or CSV through `_parse_track_csv`, which reads Flightradar24's `Timestamp,UTC,Callsign,Position,Altitude,Speed,Direction` export — `Position` a quoted "lat,lon", feet, knots — and otherwise the importer's lat/lon/time aliases) and **Use existing locations** (re-match against stored points), plus Flightradar24 ↗ and Unlink. **The buttons are previews: nothing changes until Save.** They used to write to the flight immediately (and save a new flight first), so closing the form without saving still kept the result. `POST /api/flights/track/preview/` (`{action: match|opensky, flight: <form fields>, id?}`, run against an *unsaved* `Flight` built from the form by `_preview_flight`; `opensky.compute` is the side-effect-free half of `opensky.fetch`) and `POST /api/flights/track/preview-file/` (parses without storing; on a Flightradar24 KML also returns the `flight` its header describes, which fills an empty form) return the coordinates to draw plus a **one-hour token** holding the result server-side (`trkprev:{user}:{token}`). Save sends `track_token` — or `track_remove` for **Remove track**, which clears the recording *and* any OpenSky track and sets `opensky_status='removed'` so the sweep never re-fetches it (only clearing the recording left OpenSky's in its place, so the old Unlink looked like it did nothing) — and `_apply_track_change` commits it after the normal save-time matching; an expired token comes back as `track_note`. The only thing a cancelled preview costs is the OpenSky credits it spent. **A track file is checked against the flight before anything is stored** (`flight_detect.matches_points`, the matcher's rules run on the file's in-memory points): the preview gets the form's flight as a `flight` form field and answers `matches` + a worded `mismatch` (`_track_file_mismatch`), and Save — and the legacy immediate upload — import nothing for a file that isn't the flight. Storing first used to leave a different day's flight in the user's history. The usual cause is **Flightradar24 listing a flight's history by UTC date**: an evening US departure appears under the next day there, so its "Jun 17" row is the Jun 16 local flight; the web form says so and offers to switch the form to the file's flight. The same cause hides **already-imported** recordings from **Use existing locations**, which only searches the flight's own window: when nothing fits, `flight_detect.nearby_recording` searches `NEARBY_DAYS` (2) either side and the preview returns `other_day` (local date/time, day offset, a worded message); the web offers to use it and move the flight's date and times by that many days (`shiftFormDays`), the app explains and lets the user fix the date. The older immediate endpoints (`/track/`, `/track/unlink/`, `/opensky/`, `/kml/`, `/import-file/`) remain for app builds that predate the previews; `_attach_track_file` is their shared store-fill-match step. Backup **v24** keeps `icao24` and the OpenSky track (after 30 days it is the only copy). **New `Flight`/`SiteConfig` fields ⇒ build + migrate.**

**Detected flights in the notification bell** (`tracker/flight_detect.py`, migration `0104`). The GPS history is scanned for flights not yet in the log: consecutive hops between 50 and 340 m/s are merged into runs (which covers both a phone that logs in the air and one that goes quiet at one airport and wakes at another — a single long hop), the fix *before* a run is its origin, and a run counts when it covers ≥100 km at ≥60 m/s end to end (which is what keeps a 300 km/h train out: door-to-door it averages well under that) and both ends sit at an airport. `airports.nearest()` matches only **large and medium** IATA airports (within 8 / 5 km), preferring the larger — small fields and heliports were dropped because in a city they sit close enough to ordinary streets to claim them. Suggestions are **not stored**: the raw candidates are cached per user (`flight_suggest:{user}`, 12h) and built by a background `db_thread` (the scan walks the whole history, so it never runs on a request; a cold cache answers `[]` and kicks the scan). What the bell shows is filtered fresh on every read against the flight log (same route within ±1 day) and **`DismissedFlightSuggestion`** (user + `"<date>:<dep>:<arr>"` key; user intent ⇒ excluded from backups, like `DismissedSuggestion`), so saving the flight retires its suggestion at once. `notifications_api` returns them as **`flight_suggestions` + `flight_unread`, deliberately not in `items`/`unread`**, because the app's Tracker tab reads those and expects every entry to be an overlap; the web bell adds the two counts for its dot. **Add flight** links to `/flights/?add=1&dep=&arr=&date=`, which opens the form prefilled; **Not a flight** posts `POST /api/notifications/flight/dismiss/` (web-only, CSRF-checked).

**Auto-fill is AeroDataBox** (`tracker/flight_lookup.py`), because Flightradar24's own API is paid and its KML download needs a paid FR24 account. `GET /api/flights/lookup/?number=&date=` returns the legs for a flight number and local date **without saving** (a multi-stop number returns one leg per segment and the form asks which); answers are cached 30 days (`flightlookup:{number}:{date}`, a past flight does not change) and each account gets 30 lookups a day (`_rate_limited`, per account not per IP — the quota being protected is the instance's). The key is instance-wide on `SiteConfig.aerodatabox_provider`/`aerodatabox_key` (`rapidapi` → `X-RapidAPI-Key`; `apimarket` → sends both `x-magicapi-key` and `x-api-market-key`, since which one the marketplace expects could not be confirmed), edited from **Admin Panel → Flight data** (`POST /api/site/aerodatabox/`, `{"test": true}` spends one call to check the key). It is a paid server-side secret, so it is **masked** like `turnstile_secret_key` and never reaches a template — `flights_view` passes only `FLIGHT_LOOKUP_ENABLED`. The parser reads both the current nested `scheduledTime.utc` shape and the older flat `scheduledTimeUtc`, and prefers `runwayTime` over `revisedTime` for "actual". Flights **are** in the backup (`meta.version` **20**, `_build_flights_data`; restore skips a flight already present on `(flight_number, date, dep_iata, arr_iata)`); the AeroDataBox config is not. **New model + `SiteConfig` fields ⇒ build + migrate.**
