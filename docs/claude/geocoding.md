# Geocoding and boundaries

_Read when: Reverse geocoding, labels, re-geocode, Boundary import._

**Geocoding is local, never on the push path.** `push_location` (`/api/push/`) creates points with `city=''` and returns immediately; labelling happens in a background thread. Reverse geocoding lives in `tracker/offline_geocode.py`:

- **`local_reverse_geocode(lat, lon)`** — for US points, does **point-in-polygon** against the `Boundary` table (PostGIS `MultiPolygonField`, GiST-indexed): incorporated places / CDPs first (`kind='place'`), then county subdivisions (`kind='cousub'`), so a point resolves to the town that *contains* it, not nearest centroid.
- **`offline_reverse_geocode(coords)`** — international / no-US-match fallback: nearest city from the bundled-GeoNames `reverse_geocode` package (`cities1000`, numpy/scipy), no network. **This is deliberately the original matching, unchanged.** v0.82.0 swapped it for GeoNames `cities500` (places of 500+), and a nearer hamlet then beat the town people name (Silverdale over Sellersville, PA; Morrill's centre over Waldo); that was reverted.
- **Border check — the one addition.** Nearest-city ignores borders: Campobello Island, NB's villages are too small for `cities1000`, so it was labelled after the nearest town it had, Eastport, Maine. `zone_country()` asks the timezone polygons `timezonefinder` already loads for `tz_utils` (they follow real borders: Campobello is America/Moncton, Eastport America/New_York) and maps the zone to a country through IANA `zone.tab`. **Only when the nearest city's country differs from the zone's** does the label change: to the nearest place in the zone's country from **`tracker/data/places.json.gz`** (GeoNames `cities500` + zone→country map, built and committed by `scripts/build_cities.py`; small places are what a border crossing needs), or, if none is within `_BORDER_MAX_KM` (12), just that country's state and name with no town. Every other point is labelled exactly as before. The same check skips the US `Boundary` lookup when the zone is another country's, since the 1:500k polygons are generalised. Ocean (`Etc/*`) zones skip it. Country names in the data file come from `reverse_geocode`'s `countries.csv`, so they match stored labels.

Boundaries are loaded by **`import_boundaries`** (`tracker/management/commands/`): downloads US Census TIGER shapefiles (`cb_<year>_<fips>_{place,cousub}_500k.zip`) per state, transforms to 4326, `bulk_create`s into `Boundary`. `--states ME,VA` limits states; `--regeocode` runs the relabel below. **`--kinds county`** loads US counties (for Achievements) from the one **national** file `cb_<year>_us_county_500k.zip`, named by `NAMELSAD` ("Waldo County") so a county never collides with a town of the same name, filtered by `--states` after load. Without `--keep` it now clears **only the US kinds being imported**, not the whole table, because `Boundary` also holds counties and the geoBoundaries `adm1`/`adm2`/`adm3` rows (see Achievements). The geocoder reads only `kind` `place`/`cousub`, so none of the new kinds can change a label.

**Re-geocode** (`tracker/regeocode_tasks.py`) relabels the existing history with the current geocoder. Geocoding only ever labels `city=''` points, and the Reverse Geocoding job is that same backlog drain, so a geocoder improvement otherwise reaches new points only. Two entry points share `regeocode()`: `python manage.py regeocode [--user NAME]`, and **Settings → Background Jobs → Re-geocode All Points** for the signed-in account (`POST /api/geocode/relabel/`, `GET …/status/`, `POST …/stop/`). The web job runs in a `db_thread` with its state in the cache (`regeocode_job:{user}`, shared across gunicorn workers, no model). A heartbeat fails a run silent for 3 min (30 min during the final stats refresh), and a `cache.add` guard stops a double click starting two threads. It caches one lookup per ~111m cell, **writes only rows whose label changed**, then busts each changed account's cache and recomputes its `StatsSnapshot` (`refresh_after`).

**A re-geocode never swaps one guess for another** (`_should_replace`). v0.82.0 replaced any label that came out different, and with no `Boundary` rows loaded it relabelled 810k points at home in Waldo, ME (originally from a containment match) as neighbouring Morrill. By default a label is now replaced only when the new one is a **`'boundary'`** match, the stored one is empty/`Unknown`, or the stored country differs from the **timezone country** (Campobello labelled Eastport). **`rebuild`** (`--rebuild`, or the Settings checkbox "Rebuild every label") replaces every label that differs, except ones set by hand in the map editor unless "Overwrite labels I set by hand" is on too.

**Boundaries load themselves (`ensure_boundaries`).** Recovery used to depend on a manual `import_boundaries` the user had to get right, and a rebuild against the still-empty `Boundary` table turned the home points into Brooks, the nearest 1000+ town. Town boundaries are now loaded for **every US state the instance has points in**: `regeocode_tasks.boundary_states()` is a `GROUP BY state` over `Location` rows with `country_code='US'` (a state counts at `_STATE_MIN_POINTS`, 20, so a stray fix labelled across a border doesn't fetch a state; cached 1h as `boundary_states`). The stored *state* label is reliable even where the *town* fell back to the nearest one, which is what makes it usable for this. It was a hardcoded `{'ME': 'Maine'}`, which fixed home and left every other state on nearest-town. `ensure_boundaries` runs first in **phase 0 of every re-geocode** (job status `boundaries`): `import_boundaries --keep` for missing states only, raising `BoundaryError` (job fails, nothing changed) if one is still missing afterwards, since the command itself only prints `FAILED` and exits 0. The **geocoding worker** also calls it before labelling, adding the states of a random 200-point sample of the pending backlog (`pending_states`, offline geocoder) so a first trip to a new state is labelled against its towns rather than relabelled later; one attempt an hour per set of missing states. `counties=True` (the Admin Panel job) also loads the national US county file. A cache lock keeps it single-flight across workers. Loading a state changes its labels from nearest-town to containing-town (PA points outside Sellersville borough read Hilltown, the township they are in). `local_reverse_geocode` returns `source` (`boundary`/`nearest`) and `zone_cc` for this.

**A run is all or nothing.** Phase 1 only reads: it scans the history and collects every change in memory (one `array('q')` of ids per new label, 8 bytes per relabelled point). Phase 2 applies them inside one `transaction.atomic()`. Stop is honoured in both phases, and either way **no point changes**: before phase 2 nothing has been written, and inside it the transaction rolls back. The transaction covers only the short write phase, so it never holds row locks for the minutes the scan takes. Job states are `running` (checking) → `applying` → `refreshing` (stats; too late to stop) → `completed`/`stopped`/`failed`.

**Relabelled towns.** A `Tally` counts points per `place_name` before and after, plus old→new moves, from the rows the scan reads anyway. A completed run stores its summary in the job record, which is kept for 30 days: **Added** (labels no point had before), **Removed** (labels no point has now) and the top **Moved** pairs, each with point counts and capped at 200/200/100. The Settings card shows it as collapsible lists under the job.

`geocoding_tasks._geocode_worker` drains the `city=''` backlog in chunks (one UPDATE per place), busting user cache after each chunk. Kicked fire-and-forget from `push_location` via `ensure_auto_geocode(user_id)` (debounced, no-op while a thread already runs), and on demand from Settings. **Adding `reverse-geocode` dep + migration + boundary import requires `docker compose up -d --build`** (the new dependency needs the image rebuilt; the migration applies automatically as part of that — see "Running the app") **then a manual `import_boundaries --regeocode`**, since boundary import is a one-off data load, not something a migration can do on its own.
