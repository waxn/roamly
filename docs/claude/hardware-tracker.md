# Hardware tracker

_Read when: trackerhw/ firmware, pairing, upload, BLE._

## Hardware tracker (`trackerhw/`)

A pocket GPS logger (Adafruit ESP32-S3 Reverse TFT Feather + Seeed L76K GNSS module; the first build used a NEO-6M) for days without the phone. Firmware is a PlatformIO project in `trackerhw/firmware/`; its README, `PROTOCOL.md` and `POWER.md` are the reference for the device side. It logs to LittleFS and uploads **only while charging**.

**Server side is a pairing record, not a new location source.** Points land in `Location` under an ordinary `Device` (`hw-<mac>`), so map/stats/backups need nothing new. `HardwareTracker` (migration `0094`) holds the pairing: its **own** `APIKey` (OneToOne), `hw_id`, and the last status the tracker reported (display-only JSON). Unpairing deletes the key and the row; the `Device` and its points stay. Pairing state is **excluded from backups**, and tracker keys are left out of the backup's `api_keys` too (a restored copy would belong to no tracker). **`app_api_key` excludes tracker keys** (`hardware_tracker__isnull=True`): it hands the phone the account's *oldest* active key, and a phone that adopted a tracker's key would stop tracking when the tracker was unpaired.

**Pairing is a device-auth flow run backwards:** Settings → Data & Tracking → **Hardware Trackers** → `POST /api/hw/pair/start/` mints an 8-press code over the tracker's three buttons (`T`/`M`/`B`, cache-only, 10 min, single-use, unique via `cache.add`); the user presses it on the tracker, which `POST`s it to the public `hw_pair_claim` and gets a key back. 3⁸ codes is small on purpose (it has to be typed on three buttons), so it's bounded by rate limits: 20/IP/10 min **plus a global 60 failed claims/10 min** that IP rotation can't reset. Settings polls `/api/hw/pair/status/`.

**Upload confirms by read-back.** `POST /api/hw/upload/` (Bearer, `_require_json`) inserts with `bulk_create(ignore_conflicts=True)` and then **queries the rows back** (device + timestamps, matched on ts/lat/lon to 7 dp) to build `confirmed` — `bulk_create`'s return value can't be used, since with `ignore_conflicts` it returns every object whether or not it was written. The tracker deletes a point from flash only when its `seq` is in `confirmed`; anything unaccounted for is retried, then left on flash. Impossible points (`bad_coords`, `bad_time`: pre-2020 or >1 day ahead) come back in `rejected` and the tracker quarantines rather than deletes them. `GET /api/hw/hello/` is the pre-flight (401 = unpaired, 404 = old server) and also returns the user's zone as a **POSIX TZ string** read from the TZif footer (`_posix_tz`), plus `utc_offset_s` as a fallback. The tracker sends course/satellites/HDOP too, but `Location` has no columns for them, so they are dropped server-side for now. **Tracker-only cleanup at upload:** `_hw_zero_still_speeds` zeroes Doppler speeds under 2 km/h, and under 5.4 km/h when the position's implied speed to its neighbours is under 0.5 m/s (a NEO-6M at rest reports 0.3–1.5 km/h of noise; walking moves the fix, so it survives). `_flag_glitch_clusters` flags (`suspect`, reason `cluster`, so **hide outliers** hides them and distance skips them — never deleted) runs of 1–6 points that jump ≥80 m away and back within 15 min while their own Doppler says ≤1.5 m/s — a real trip carries speed, a glitch teleports while "stationary". It runs after each upload (over the batch plus 15 min of history) and again inside `_flag_suspicious_locations`, **whose window reset would otherwise wipe it nightly**; it's scoped to `HardwareTracker` devices because phones' fused location doesn't report Doppler reliably. Known ambiguity: a drive where only *parked* points were sampled looks identical to a glitch — hence a reversible flag. **Stationary anchor (firmware, `anchor.cpp`):** the server cleanup above can't catch the L76K's own indoor drift — a 60 m jump that slides back over minutes, too slow and too many points for a glitch cluster, while it reports 0.00 m/s and HDOP 0.5 (so `acc` stays ~2 m and Min accuracy is no help). The tracker therefore pins an anchor after 3 windows whose every Doppler reading is under 0.3 m/s, stores later still windows *at* the anchor (refined only by fixes within 10 m of it, so settling is followed but drift is not), and releases on a window whose slowest reading clears 0.3 m/s (or 2 windows > 200 m away; a >10 min gap drops it). Snapped points go through `classify()` too, which is load-bearing: the adaptive "≥40 m from the last point = moving" rule otherwise read the drift as walking and recorded it at 30 s cadence. The anchor's 0.3 m/s is deliberately tighter than `ADAPT_STILL_MPS` (0.8, sized for the NEO-6M's noisy Doppler) so a slow amble neither forms nor stays stuck to an anchor. **New model ⇒ build + migrate; firmware change ⇒ reflash (not part of the Docker image).**

**Bluetooth link + hand-off (app ↔ tracker).** The tracker runs a duty-cycled NimBLE beacon (6.5 s every `bleIntervalS`, default 60) that is **never scheduled inside a GPS fix window** — in standby modes only while the receiver sleeps and only if it ends before the next wake — plus a bonded GATT service (status / settings / command / console; GATT and advert layout in `trackerhw/PROTOCOL.md`). On Android, `tracker/TrackerLink.kt` (`@Singleton`) holds all BLE: a low-power filtered scan for presence (`near` = heard within `max(200 s, 3.5 × interval)`), on-demand GATT sessions while the **Tracker** tab is open, bonding via `createBond`. The bottom-nav **Tracker** tab (`Screen.Tracker`, `ui/tracker/`) appears only when `UserPreferences.trackerBleAddress` is set (`AuthViewModel.trackerPaired`); pairing starts from Settings → Roamly Tracker. **Hand-off:** `LocationTrackingService` collects `phoneShouldPause` (near ∧ tracker recording ∧ `handoff=tracker` ∧ tracker has a fix) into `handoffPaused`, and capture checks `capturePaused = isPaused || handoffPaused` — the user's own pause and the hand-off are separate so resuming one can't clobber the other; an activity recording is never handed off. With `handoff=phone` the phone sends a 5-min lease every 2 min and the tracker pauses while it is valid, so a vanished phone lets the tracker resume by itself. **Apart** is detected server-side (`DeviceOverlap.kind='apart'`, below) and surfaces in the bell and the Tracker tab. **Firmware change ⇒ reflash; mobile change ⇒ rebuild APK + tag.**
