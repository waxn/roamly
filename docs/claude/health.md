# Health Connect and Zepp

_Read when: Health tab, HealthSample/HealthWorkout, Zepp sync, health file import._

**Health Connect (steps, distance, calories, workouts).** A read-only bridge from Android's **Health Connect** — the on-device store every fitness app writes into — to a new top-level **Health** tab (`/health/`, `health_view` → `health.html`). Roamly otherwise infers movement entirely from GPS (`transport_mode`, `Visit` dwells, gated distance) and has no idea how many steps you took.

**Strictly additive, and that is the design constraint.** No map layer, distance figure, visit, stat, snapshot or transport mode reads or is read by any of this. Neither health model carries a `Device` FK, because health has to work on an account that never enabled GPS tracking at all.

**Raw records, not daily aggregates** (migration `0074`). `HealthSample` holds one row per Health Connect record (`kind` = `steps`/`distance`/`calories_active`/`calories_total`, `value`, `start_time`/`end_time`, `zone_offset_seconds`, `source`, `device_id`, `hc_id`, `last_modified`); `HealthWorkout` holds one manually imported exercise session with **denormalised totals computed on the phone** via Health Connect's `aggregate()` — deliberately *not* recomputed server-side from `HealthSample`, since steps aren't recorded for a bike ride, the user may not have granted every metric permission, and a session can predate the sample sync window, so a recomputation would quietly report zeros. Both dedupe on `unique_together = ('user', 'hc_id')` (Health Connect's own record UUID), which makes ingest idempotent under `bulk_create(ignore_conflicts=True)` — the same strategy `push_location_batch` uses on `Location`. Both are **non-spatial and therefore defined once**, not behind the `HAS_POSTGIS` branch: that split exists only to keep a geometry column and its GiST index off SQLite, and there is no geometry here. Storing `ExerciseRoute` polylines would change that, which is one reason it's out of scope.

**`HealthSample` deliberately has no `Meta.ordering`.** Django appends `Meta.ordering` columns to the `GROUP BY` of a `.values().annotate()` aggregation, which would shatter the daily rollup into one group per row. Every aggregation call site orders explicitly and ends in `.order_by()`. (`Location.Meta.ordering = ['-timestamp']` is a latent version of the same hazard.)

**Cross-source de-duplication is the one genuinely subtle piece.** Several apps — the phone's own step counter, Fitbit, Samsung Health, Strava — all write records for the *same* walk. Health Connect's `aggregate()` API resolves that against a user-configured priority list; **raw records carry no such dedupe**, so a naive `SUM` reports two or three times the real step count for anyone running more than one fitness app. Within a single writing package records *are* non-overlapping (Health Connect truncates an app's own overlapping writes), so per-source sums are safe and cross-source sums are not. `_health_daily_totals` therefore totals to `(day, kind, source)` first and then picks exactly **one source per `(day, kind)`**: `UserProfile.health_preferred_source` when it recorded anything that day, otherwise the source with the largest total. The chosen source rides back in the payload, and the page's **Data sources** card is what makes the whole problem visible to the user. It is a `<details>` collapsed by default (a long app list otherwise dominates the tab); the summary row shows the chosen source (or Automatic) and the app count. Done in Python (`.values_list(...).iterator()`) rather than as a `GROUP BY` because `TruncDate` is exactly where PostgreSQL and SQLite diverge on timezone handling, the per-source resolution is awkward in SQL, and the result is cached anyway.

**Auth: `@login_required` alone is correct**, for the browser *and* the app. `ApiKeyAuthMiddleware` already resolves `request.user` from an `Authorization: Bearer <key>` header when no session is present, so the app authenticates either way. `push_location`'s manual `get_api_key_user()` dance exists only because GPSLogger/OwnTracks put the key in a query param or JSON body, which the middleware doesn't handle — the Roamly app always sends Bearer. The ingest endpoints must still be `@csrf_exempt` (the app has no CSRF token), so `_require_json` requires `Content-Type: application/json` and 415s otherwise: that is not a CORS simple request, so a cross-origin forgery attempt triggers a preflight the app never answers.

**Health reads sit behind their own `health_gen:{user}` counter** (`_bust_health_cache`), never `cache_gen`. Both directions matter: a phone pushing GPS every 30 seconds bumps `cache_gen` constantly, so sharing it would mean the health cache never survives to be hit; and bumping `cache_gen` from a health sync would evict every cached track, tile, distance and locations response several times a day for a feature that changed none of them. Same reasoning that keeps `fog:{user}` and `StatsSnapshot` off `cache_gen`. `restore_backup` busts both.

Endpoints — ingest: `POST /api/health/samples/` (`{samples, deleted}`, cap 1000; `bulk_create(ignore_conflicts=True)`, then a bounded `bulk_update` for records Health Connect **revised in place** — same `hc_id`, newer `lastModifiedTime` — which `ignore_conflicts` would otherwise silently keep stale; then deletions by `hc_id`), `POST /api/health/workouts/import/` (cap 50), `POST /api/health/workouts/<id>/delete/`, `POST /api/health/delete/`. Reads: `GET /api/health/daily/` (array-parallel `{days, steps, distance, calories_active, …}`, shaped like `distance_api`'s `{days, distances}`, cached 600s), `GET /api/health/day/<YYYY-MM-DD>/` (24 hourly buckets + that day's workouts + the raw records — the payoff for storing raw rows, since an aggregate could never reconstruct *when* you moved; reuses `_journal_day_bounds` for the browser-offset → UTC window rather than writing a second converter), `GET /api/health/workouts/`, `GET /api/health/workouts/imported/`, `GET /api/health/status/`, `GET/POST /api/health/source/`. Every read takes `tz_offset` (browser `getTimezoneOffset()` minutes), because records are UTC instants and a "daily total" is a *local* day.

`health.html` reuses existing patterns rather than inventing any: the **Daily Steps heatmap** is a structural port of `stats.html`'s Daily Distance heatmap (53 Mon-first week columns, **quartile**-bucketed shading of the non-zero days — a linear ramp would flatten nearly everything to level 1 — always the trailing year, deliberately independent of the toolbar range), the charts are the hand-rolled Canvas helpers from `admin_panel.html` (`monotoneSpline`/`hexA`/`attachChartHover`, **no charting library anywhere in this app**), and distance respects `roamly_speed_unit`.

**The charts scale to the range, and the per-day arrays are not what they plot.** `_health_bucketed` buckets the daily series to **day / week / month** and hands it back as `buckets` alongside a `granularity`, chosen from the span of the *requested window* (≤70 days → day, ≤400 → week, else month) unless `?granularity=` names one; an explicit choice is still coarsened until the axis is under `_HEALTH_MAX_BUCKETS` (400), so `granularity=day` over ten years cannot ask for thousands of points. Two things make this more than cosmetic. The axis is **filled continuously** from `_health_axis_days` — the requested window wins wherever it is bounded, so a "last 30 days" chart is thirty buckets even when five of them recorded anything, instead of drawing those five evenly spaced as though they were consecutive. And the **per-day `days`/`steps`/… arrays are untouched**, still every day with a record: the heatmap reads them straight and therefore passes **`granularity=day`** explicitly on its `?all=1` fetch, which is the one thing that would silently break if bucketing were applied to the raw arrays instead of added beside them.

Axes are labelled, which they previously were not (the old chart drew four unlabelled gridlines and month ticks). **`niceAxis(max, ticks)` picks a round tick *step* — 1/2/2.5/5 × 10ⁿ — and multiplies**, rather than rounding the ceiling: 21,000 steps rounds up to a tidy 25,000, but quartering *that* puts gridlines at 6,250 and 18,750, which is what the labels actually read. X labels are thinned from the widest label against the real slot width, so a 24-hour day, a 30-day month and a 5-year monthly axis all label themselves without overlapping. One `drawChart()` serves all three charts (line for day granularity, bars for week/month and for the hourly breakdown) so their axes, hover and click behaviour can only ever agree.

**Clicking drills down, and a day's detail renders inline below the charts** — a card in the page flow, not the modal it used to be, since the detail is a drill-down *of* the chart above it and a dialog covers the thing being drilled into. A day point opens `openDay()`; a **week or month bar narrows the toolbar range to that bucket instead** (`pickBucket`), which redraws per-day — the only route from an aggregated bar to a single day. The panel shows total steps / distance / active calories (plus total calories and a workout count when present), an hourly bar chart, that day's workouts, and **the towns visited**: `_health_day_cities` walks the day's `Location` rows through the Visits page's own `_visits_dwell_gap` rule, so an hour reported here agrees with `/visits/` rather than being a second, differently-counted estimate of the same day. Health carries no `Device` FK by design, so the town list is a best-effort join on the day window and an account that never enabled GPS tracking simply gets none. The hourly canvas lives in the card statically rather than being rebuilt with the surrounding text, so its hover handler is attached once.

**Mobile** (`com.roamly.health`, `androidx.health.connect:connect-client:1.1.0`). `HealthConnectManager` wraps availability (`getSdkStatus` → available / update-required / unavailable, each surfaced distinctly — a phone with no Play Store is a genuine dead end and the UI says so), permissions, reads and `aggregate()`. `HealthSyncWorker` is a `CoroutineWorker` modelled on `UploadWorker` (same companion-object `enqueueUniquePeriodicWork` + `cancelUniqueWork` shape) at **6 hours**, not the uploader's 15 minutes — health data is daily-granularity. Two modes: **backfill** walks history in month-sized windows saving a cursor after each so a killed worker resumes, and **mints the changes token *before* reading** so records written during the backfill are caught by the first incremental run instead of falling in the gap; **incremental** drains `getChanges(token)`, which yields upserts *and* deleted record ids, and on `changesTokenExpired` (tokens die after ~30 days unused) clears the cursors and re-backfills rather than stalling forever. `ExerciseSessionRecord` is **excluded from the changes token** — workouts are manual, so a change stream for them would only build a queue of upserts the user never asked for.

Three manifest details are load-bearing and each fails silently if missed: **`READ_HEALTH_DATA_HISTORY`** (without it Health Connect returns only the trailing 30 days, so a deeper backfill comes back empty), **`READ_HEALTH_DATA_IN_BACKGROUND`** (without it reads only succeed while the app is foregrounded, defeating the periodic worker), and the **permissions-rationale entry point** — Health Connect refuses to show its grant sheet without one, and needs *two* declarations: an `intent-filter` for `androidx.health.connect.action.SHOW_PERMISSIONS_RATIONALE` (Android ≤13, where Health Connect is an installable APK) **and** an `activity-alias` with `VIEW_PERMISSION_USAGE` + `category.HEALTH_PERMISSIONS` (Android 14+), both targeting `HealthPermissionsRationaleActivity`. Plus a `<queries>` entry for `com.google.android.apps.healthdata`. The two optional permissions are requested **separately**, each with its own explanation, so declining either degrades the feature rather than breaking it.

**The Health setup flow calls `AuthRepository.ensureApiKey()`.** It was previously reached from exactly one place — `SettingsViewModel.createApiKey()`, on the start-tracking path — so a health-only user would have no API key and authenticate by session cookie alone, which `SessionGuardInterceptor` clears on expiry, silently killing background sync. **Permanent denial is handled explicitly:** Health Connect shows its request dialog at most twice per install, after which the launcher returns immediately with an unchanged set — the UI detects that and routes to `ACTION_HEALTH_CONNECT_SETTINGS` rather than re-firing a dialog that will never appear, the health equivalent of the battery-exemption escape hatch.

The screen is a page of the **Data** tab (it was a Settings button until the Data tab existed), **not** a bottom-nav tab of its own: the phone is the *source*, the website is where you look at it, and the nav already has six tabs. Its **Workouts** browser lists Health Connect sessions with a per-row Import button, aggregating each row's totals lazily as it scrolls into view (doing a whole 90-day window up front is slow enough to notice); which rows are already imported comes from `GET /api/health/workouts/imported/`, so the **server is the source of truth** — browsing on a second phone agrees, and a server-side delete shows up immediately, with no local Room table to drift. **Health adds no table to `TrackingDatabase`** — Health Connect is itself the on-device store, so there is nothing to cache locally.

Health data **is** in the backup format (`meta.version` **9 → 10**): it is user content, and Health Connect only serves the trailing 30 days without the history permission while a source app can retract records at any time, so the Roamly copy is the long-term archive. `backup_tasks._build_health_workouts_data` is shared by both builders; **there is deliberately no shared helper for samples**, since `_write_backup_json` streams them row-by-row (`.values_list(...).iterator()`, a `'Writing health'` stage) exactly as it does locations, and a shared list-builder would defeat that. `restore_backup` reads both keys with `.get`, so pre-v10 backups restore unchanged with no version branch. **New models ⇒ build + migrate; mobile change ⇒ rebuild APK + tag.**

**Zepp (Amazfit) health data.** Zepp is where a lot of people's step data actually lives, and its Health Connect integration is too patchy to rely on — so health has two Zepp-specific routes beyond the Health Connect sync above. Zepp's **official REST API is corporate-only** (their docs: data cooperation "only supports corporate users, not individual users", with a carve-out for academic research), so neither route can be an OAuth integration.

**`HealthSample.hc_id`/`HealthWorkout.hc_id` were renamed to `external_id`** (migration `0075`). The column was named for Health Connect when that was the only source; Zepp has no per-record UUID, so its rows carry a **deterministic synthesised key** instead — `zepp:steps:2026-08-27:540` (kind, day, start-minute) — which preserves the `unique_together` dedupe exactly: a re-sync of a day updates rather than duplicates. **The wire format still accepts `hc_id`**, and `/api/health/workouts/imported/` still *returns* `hc_ids`, because **mobile v1.21.0 shipped before the rename and is already installed** — so the ingest path reads either name and the mobile app needs no change at all. Backup `meta.version` **10 → 11**; `restore_backup` reads either key, so v10 backups restore unchanged.

**Route 1 — cloud sync (`tracker/zepp_tasks.py`).** Talks to the endpoint the Zepp app itself uses: `GET https://{host}/v1/data/band_data.json` with an **`apptoken`** header the user lifts out of the app (HTTPS proxy capture, or `hm_id_sdk_android.xml` on a rooted phone — Roamly cannot mint it), plus `query_type=detail`, `device_type=android_phone`, `userid`, `from_date`, `to_date`. Config on `UserProfile` (`zepp_enabled`/`zepp_token`/`zepp_user_id`/`zepp_host` + the `zepp_last_sync`/`zepp_last_error` cursors); the token is **masked as `••••••••` on read and only overwritten when the submitted value differs from the mask**, the same convention as `ai_api_key` and the Turnstile secret. `zepp_host` is configurable because **Zepp shards accounts by region and the wrong host authenticates but returns nothing** — `KNOWN_HOSTS` lists the four.

Each day's `summary` is a base64 JSON blob whose `stp` key carries a daily total (`ttl`/`cal`/`dis`) **and** a `stage` array of activity segments with start/stop minute offsets. `parse_day` writes the **segments** as individual samples, so Zepp data populates the intraday day view instead of landing as one flat daily total — then adds a **remainder row** for `ttl - sum(segments)`, since steps taken outside a detected activity would otherwise be lost and the day would silently under-report. Distance has no per-segment figure in the payload, so it is one day-spanning row. Sync resumes from `zepp_last_sync` **minus two days**, because a day pulled while still in progress would otherwise stay frozen at its mid-day figure; an explicit `bulk_update` pass corrects any row whose value changed, which `ignore_conflicts` alone would silently keep stale.

**Being unofficial is designed for, not hoped away.** Every failure is recorded in `zepp_last_error` and rendered in Settings, so a broken sync reads as broken rather than as an empty account; a 401/403 gets its own "re-capture the token" message, since an expired token is by far the likeliest failure. A daemon thread from `apps.ready()` sweeps every 6 hours (mirroring `alert_tasks`/`summary_email_tasks`), and `POST /api/health/zepp/sync/` kicks one on demand. Endpoints: `GET/POST /api/health/zepp/`, `POST /api/health/zepp/sync/`.

**Route 2 — file import (`POST /api/health/import/`).** The counterpart that cannot break: no credentials, no API. Takes a CSV (optionally gzipped) with a date column plus any of steps / distance / calories, matched through the **existing `_get_csv_field`** broad-alias helper the location CSV import already uses — because headers differ between Zepp's GDPR export, the community export scripts, and a hand-built spreadsheet. Rows key on `import:<kind>:<date>`, so re-importing an overlapping export corrects those days rather than duplicating them (same `bulk_create` + `bulk_update` pattern as the Zepp sync). Both routes land in `HealthSample` under distinct `source` values, so the existing **cross-source resolver picks one per (day, metric)** rather than summing Zepp and Health Connect together — the double-counting protection falls out for free.

**Gadgetbridge is deliberately not a route.** It is an either/or with the Zepp app, not an addition: Gadgetbridge's own docs say to pair with the vendor app, extract the auth key, then remove the vendor app, and that Zepp must not be running while Gadgetbridge is connected. **Python change ⇒ restart `web`; new fields ⇒ build + migrate. Mobile is unaffected.**
