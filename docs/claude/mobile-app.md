# Android app: design, updates, navigation, screens

_Read when: Anything under mobile/ except tracking capture._

**Mobile design system (Field Journal).** The app used a stock Material 3 look (dynamic Material You color, default typography, tonal-elevation cards) that didn't match the web app and wasn't well liked; it's now a port of the web's own Field Journal system (see **Design system (Field Journal, dark-first)** above) — same dark/light hex palette read directly from `base.html`'s `:root`/`[data-theme="light"]`, so the two stay in sync by construction rather than by convention. `ui/theme/Theme.kt` defines `DarkColors`/`LightColors` (`darkColorScheme`/`lightColorScheme`) from that palette; **dynamic color is deliberately removed** — Field Journal is a fixed brand palette, not a per-device Material You scheme. Radii are tightened to 6/8/10/12/14dp (`RoamlyShapes`), mirroring the web's crisp-not-pillowy `--radius-*` values. `ClayColors` (`Clay.colors`, via `LocalClayColors`) carries the values M3's `ColorScheme` has no role for: the earthy categorical accents `moss`/`rust`/`ochre`/`mauve`/`mapBlue` (matching the web's `clay-mint`/`coral`/`amber`/`lavender`/`sky` tokens) plus `success`/`warning` — read these instead of hardcoding a hex, since every consumer needs to stay light/dark aware. `ui/theme/Clay.kt`'s `ClayCard`/`ClaySurface`/`ClayButton` are flat (zero tonal/shadow elevation) with a 1dp hairline border in place of Material elevation; `ClayOutlinedButton`/`ClayTextButton`/`ClayIconButton` extend the same set to every control type so new screens have one centralized, themed place to reach for rather than raw M3 components. **`ElevatedCard` is the trap** — it reads as "0 raw `Card()` calls" in a codebase grep since it's a distinct composable, but it carries the exact tonal-elevation shadow the redesign removes; Stats and Diagnostics both used it extensively and were swapped to `ClayCard(contentPadding = 0.dp)`. Typography: `ui/theme/Font.kt` declares `FrauncesFamily`/`PlexSansFamily`/`PlexMonoFamily` from `res/font/*.ttf`, converted from the web's WOFF2s (`tracker/static/tracker/fonts/`) via fontTools (variable Fraunces instanced to static 400/600/700 weights at a fixed `opsz`, since Compose font resources need static instances) — regenerate by decompressing each WOFF2 with `fontTools.ttLib.TTFont(...).save(..., flavor=None)` and, for Fraunces, `fonttools varLib.instancer`. `RoamlyTypography` maps `displayLarge`…`titleMedium`/`titleSmall` to Fraunces (this is what makes every section header — `ClaySectionHeader` and the screen-local `SectionHeader`/`ResultHeader` composables, which all key off `titleMedium`/`titleSmall` — read as an editorial heading rather than body copy) and `bodyLarge`…`labelSmall` to Plex Sans. The bottom nav (`RoamlyNavHost`) drops the default M3 pill selection indicator for a flat colored-icon state plus a hairline top border. Icons stay Material Icons (`Icons.Rounded`, used consistently app-wide) — a new icon set was judged out of proportion to a code-only pass. **New brand color usage ⇒ add it to `ClayColors`, don't hardcode a hex; new card ⇒ `ClayCard`, never `ElevatedCard`.**

**Mobile branding:** Adaptive launcher icon — the orange Roamly mark (`drawable/roamly_favicon.png`, the same trail-blaze line-art mark as the website favicon/`roamlymark.svg`) on black background (`drawable/ic_launcher_background.xml`). `android:windowBackground` is black to kill the cold-start flash. `ui/SplashScreen.kt` shows a **procedurally-generated intro that differs on every launch**: a `SplashConfig` seeded from `System.nanoTime()` randomly picks one of four Canvas styles (`JOURNEY` wandering GPS route, `CONSTELLATION` fixes wiring together, `RADAR` sweep + blips, `GRIDZOOM` map fly-through) with random accent colors from the theme palette; the Roamly mark springs in at center in all of them. `RoamlyNavHost` plays it until intro time has elapsed and `isLoggedIn` has resolved.

**Mobile in-app updates.** The app is sideloaded (no Play Store), so it self-updates. CI (`.github/workflows/mobile-release.yml`) publishes a signed APK (`Roamly<version>.apk`) as a GitHub Release asset on each `mobile-v*` tag. Two **server** endpoints proxy that so the app only ever talks to its own configured server: `GET /api/mobile/version/` (`views.mobile_version_check`) fetches `releases/latest` from GitHub (repo = `settings.MOBILE_UPDATE_REPO`, default `waxn/roamly`, env-overridable), parses the `mobile-v*` tag → `version_name` + release notes + the `.apk` asset, and returns it — cached 15m in Django cache (`mobile_latest_release`) to stay under GitHub's 60 req/hr unauth limit (there's no invalidation on publish, so a new release is otherwise invisible until the entry expires; `?refresh=1` forces a fresh GitHub fetch, rate-limited by a 2m cooldown lock so the public bypass can't burn the GitHub quota); `GET /api/mobile/apk/` (`views.mobile_download_apk`) streams the APK, fetching it from GitHub into `MEDIA_ROOT/apk/` once and serving from disk thereafter (`media/` is gitignored + a Docker volume). Both are public (no auth). On the **mobile** side: `RoamlyApi.getLatestVersion()`/`downloadApk()` (`@Streaming`), `data/repository/UpdateRepository.kt` (semver-compares installed `versionName` vs server, downloads to `cacheDir/updates/`, installs via `FileProvider` + `ACTION_VIEW` package-installer intent — needs the new `REQUEST_INSTALL_PACKAGES` permission and routes to `ACTION_MANAGE_UNKNOWN_APP_SOURCES` if not yet granted), `ui/update/UpdateViewModel.kt` + `UpdateBanner.kt`. `RoamlyNavHost` runs a throttled (~24h, `UserPreferences.lastUpdateCheck`) on-launch check and shows a dismissible "Update available" banner; Settings → About has a manual "Check for updates" button (shared VM instance). Android can't silently install for a non-system app — the OS install-confirmation screen always shows. **Server change ⇒ build; mobile change ⇒ rebuild APK.**


**Mobile caching:** `data/cache/DiskCache.kt` — Gson-backed JSON file cache (`cacheDir/api_cache`) persisting last successful response per screen for cold-start / offline. Wired into Stats, Adventures, Pals, Journals VMs. Wiped on sign-out. `StatsCache` is the fast warm-cache layer; `DiskCache` is the cold-start fallback beneath it.

**Mobile navigation is Activity-scoped, and that is what makes a tab switch instant.** Each bottom-nav tab's ViewModel is resolved in `RoamlyNavHost` against **`activityOwner`** (the `LocalViewModelStoreOwner` captured *outside* the `NavHost`, where it still resolves to the Activity) and passed into the screen, rather than letting the screen take `hiltViewModel()`'s default. The default owner is the destination's own `NavBackStackEntry`, and the tab navigation pops with **`saveState = true`, which clears that entry's `ViewModelStore`** — so every switch destroyed the tab's ViewModel and the next visit re-ran its `init`: a **synchronous Gson read off disk on the main thread** (`DiskCache.get`) plus a fresh round of network calls, behind a spinner. `MapViewModel` was already hoisted this way for its retained `MapView`; the same treatment now covers Trips, Journals, Stats and Settings.

Two consequences are load-bearing and must be kept in step:

- **The owner is passed down, not the ViewModel.** `hiltViewModel()` constructs on the spot, and these `init` blocks fire network calls immediately — resolving them at the top of `RoamlyNavHost` would run them during the splash, against the placeholder base URL before login resolves, which is the exact trap `MapViewModel.init`'s own comment describes (it waits on `serverUrl.first { !it.isNullOrBlank() }`; the others do not). Handing the *owner* to each destination keeps construction lazy — first visit to that tab — while keeping the scope wide.
- **`SettingsViewModel` is deliberately excluded and must stay excluded.** It is the only one of these with *continuous* collectors, and two of them run against exactly the infrastructure tracking depends on — a Room `Flow` on the **tracking database** (`pointDao().unsyncedCountFlow()`, re-queried on every fix the service inserts) and `WorkManager.getWorkInfosByTagFlow` — on top of eighteen file-backed DataStore flows. Activity-scoped, those ran for as long as the app was alive, **including a whole drive with the screen off** (backgrounding does not destroy the Activity), in the **same process** as `LocationTrackingService` (the manifest declares no `android:process`), contending on the same SQLite database `savePoint()` writes into. That starved the capture loop — fix gaps stretched from a configured 10s toward the 45s `MIN_ALARM_FLOOR_MS` × `CATCHUP_MULTIPLIER` backstop, which is what a "tracking got slow and unstable" report looks like. **Before hoisting any ViewModel here, check its `init` for a collector that outlives the screen; a one-shot load is safe, a `Flow` on `TrackingDatabase` or WorkManager is not.**
- **A surviving ViewModel no longer refreshes by being recreated**, so each of those destinations carries a `LaunchedEffect(Unit)` calling the VM's own loader (`loadTrips()` / `refresh()` / `load()`). The composable is still recreated per visit, so that is once per visit, and each loader only raises a spinner when it has nothing cached to show — the switch stays instant and the data still catches up. **A new tab added here needs the same two lines, or it will show whatever it loaded the first time, forever.**

**Sign-out therefore recreates the Activity** (`onLoggedOut` → `Activity.recreate()`, falling back to the old `navigate(Login) { popUpTo(0) }` if the Activity can't be found). Routing to Login alone would leave the previous account's trips, journals and stats sitting in an Activity-scoped store for whoever signs in next, with nothing left to trigger a reload. Recreation drops that store wholesale and lands on Login by itself, since `logout()` has already cleared prefs; `splashDone` is `rememberSaveable`, so the splash does not replay. **`StatsCache` is `@Singleton` and outlives even that**, so `logout()` calls `statsCache.clear()` explicitly alongside `disk.clearAll()`/`store.clear()` — it was previously wiped by nothing at all, and leaked the prior account's figures across a sign-out.

**Map overlays cull in geographic space before projecting.** `HeatmapOverlay.draw` and `PointsOverlay.draw` run on **every** pan/zoom frame over the whole accumulated point set — `MapViewModel`'s `accumulator` keeps merging viewport detail (`BBOX_LOAD_LIMIT` 8k a time, on top of a `PERIOD_LOAD_LIMIT` 20k overview) and never prunes, so after some panning that list is tens of thousands of rows. Both loops used to project **every** point — allocating a throwaway `GeoPoint` per point per frame — and only then discard the off-screen ones, so the per-frame cost scaled with everything ever loaded and the GC churn is what made the map drag.

`ViewportCull` reads `mapView.boundingBox` once per draw, pads it by the sprite/dot radius converted to degrees (`pixelsToDegrees`), and rejects with two double comparisons before any projection happens; survivors are projected through a **single reused `GeoPoint`** (`setCoords`) and reused `Paint`/`Rect`/`RectF`/`Point` fields. Per-frame cost now scales with what is on screen. Two details matter: `contains` returns **`true` when the viewport could not be read**, so a bad frame falls back to drawing everything rather than to a blank map; and when the viewport straddles the antimeridian (`lonWest > lonEast`) the visible span is the **outside** of `[minLng, maxLng]`, hence the `or` rather than an `and`.

**The map camera auto-fit is keyed on the data, not on the composable.** `didAutoFit` lives on `MapViewModel` (reset in `setTimePeriod`/`setCustomDateRange`, the two places the dataset changes) rather than in a `MapScreen` `remember`, which dies with the composable — so every switch away from the Map tab and back re-ran the whole fit, both paying a full main-thread pass over the accumulated points and yanking the camera back from wherever the user had panned to. The bbox is also computed as a single min/max loop instead of materialising a `GeoPoint` per point to hand to `BoundingBox.fromGeoPoints` (note the constructor is `BoundingBox(north, east, south, west)`).


**Mobile local-first location store:** `data/local/LocationStore.kt` backs a Room table (`synced_locations`, keyed by server location id) in its own `MapCacheDatabase` (see **The capture loop is isolated from the UI** — it is rebuildable, so it is kept out of `TrackingDatabase`). Sync is incremental via the locations API cursor (`sort_dir=asc` + `before_value`/`before_id`; `has_more`/`next_before_value`/`next_before_id`). `sync()` runs on foreground and `MapViewModel` init; `MapViewModel` observes `store.state` (a `StateFlow<SyncState>`) and reloads on sync complete. Map paints from store: decimated overview (`id % stride`) + full-resolution viewport dots from local DB on pan/zoom. "Have I been here?" scans the entire local history. `SyncedLocationDao.inTimeRange(startMs, endMs)` supports custom date ranges. Wiped on sign-out.

**Mobile feature parity:** Map (map-options sheet: time periods incl. a custom date range via Material3 `DateRangePicker` + basemap selector; ‹ › range stepping and the "what I did today" pill + sheet, see `quick-notes.md`; refresh; heatmap; GPS dot tap → point detail dialog naming the recording device; "have I been here?"), Adventures (see **Mobile Adventures parity** below), Stats (monthly drilldown: tapping a month bar expands a daily Canvas chart with grid lines; tapping a day navigates map to that date), Journals (day track is a real osmdroid `MapView` with teal `Polyline`; tap card opens map for that date), Settings (with **Diagnostics** page: coverage bar chart from `/api/diagnostics/location/` pre-filled with device_id, CSV share via FileProvider; ; Location Data now lives in the Data tab — see below), **Search** (its own tab, sharing the slot with Ask via a segmented toggle; place results expand inline to show each day, tap a day → map date filter). **The legacy Pals feature (removed on the web in migration `0059`) is fully deleted from mobile** — `ui/pals/*`, `PalRepository`, the Groups Pals tab and all `api/pals/*` declarations are gone; the shared `PalMember` model was kept (it types `TripResponse.members`). `MapViewModel.navigateToDate(dateStr)` sets a single-day custom range and clears `focus` so MapScreen auto-fits the viewport; called from search, stats drilldown, journal track taps, and Ask date links. `setTimePeriod`/`setCustomDateRange` also clear `focus = null` so auto-fit always fires on new data. `MapViewModel` scoped to Activity (created outside `NavHost.composable` blocks in `RoamlyNavHost`) so Journal and Stats can trigger map navigation. The UI uses the Field Journal theme (see **Mobile design system** above; no dynamic color) with a `NavigationBar` + `NavigationBarItem`. Power-user/admin features remain web-only.

**Mobile Adventures parity (`ui/trips/`).** The mobile trip detail page (`TripDetailScreen.kt` + `TripDetailViewModel.kt`, backed by the same `GET /api/trips/<id>/` `_trip_detail_inner` response the web uses) now reads and writes most of what the web Adventure has. **Read:** the **Story** block document renders read-only via `StoryBlockRenderer.kt` (`StoryBlock` dispatches on `block.type` — heading/paragraph/divider/callout/photo_grid/location_card/timeline; `map_embed` is scoped down to a tap-to-open-full-map card rather than a live embed; unknown block types render nothing; `content` is read as a loose Gson `JsonObject` mirroring the web's untyped renderer; `[^pin:ID]` refs become inline numbered badges). **Day Log** and **Itinerary** render as sections (`TripSections.kt`), and blurbs show star rating + category badge + a photo/video thumbnail row. The trip map (mini + `TripFullMapScreen`) overlays each member's own track in the web-matched `MEMBER_TRACK_COLORS` palette (owner = index 0) with a swatch legend, plus the itinerary as numbered `Marker`s joined by a dashed `Polyline`. A shared `MediaThumbnailRow` (with a full-screen lightbox; videos open externally) is reused by story photo grids, blurbs, and day notes. **Write:** members create/edit their own **Day Log** entries (title/body/linked-place dropdown/up-to-10 photos or videos via `PickMultipleVisualMedia`), create/edit/reorder **Itinerary** stops (form + move-up/down buttons that swap `order` server-side; transport options match the web plan page), post richer **blurbs** (title/star-rating/category/photos, multipart), and creators get an **Invite** action (mint/show the `/adventure/join/<token>/` link with copy + native share + reset) plus a member list with per-member remove. New models (`BodyBlock`/`PlacePayload`/`MediaItem`/`PlannedStop`/`DayNote`/…) extend `TripResponse`; new `TripRepository`/`RoamlyApi` methods wrap the already-existing day-note/plan/invite/member endpoints. `trip_create_blurb` was made `@csrf_exempt` (matching its siblings) and taught to accept `rating`/`category` so a session-authed mobile multipart post works. **Story block *editing* is deliberately not on mobile** (the web block editor is a much larger effort; mobile gets full read parity without it). **Mobile change ⇒ rebuild APK.**

**Mobile Data tab + boarding-pass scanning (`ui/data/`, `ui/flights/`, `flights/`).** The bottom bar is **Map · Trips · Search · Data · Settings** (+ **Blog** after Map while a trip blog is featured, + Tracker when paired; Simple Mode stays Map + Settings). **Data** (`DataHubScreen`) holds **Stats · Flights · Health · Location data** behind a chip row — Health and Location data used to be buttons buried in Settings — and **Trips** (`TripsTabScreen`) holds **Trips | Journal** behind a segmented toggle, the `SearchTabScreen` pattern. Both hosts take their pages as **slots**, so `RoamlyNavHost` still decides every ViewModel's scope: Stats/Trips/Journal stay Activity-scoped, Health and Location data stay back-stack scoped (Health's ViewModel is not a one-shot load). `HealthScreen`/`LocationTableScreen` take `onBack: (() -> Unit)? = null` and hide their back arrow when hosted.

**Flights in the app** (`FlightsScreen`: List | Map | Stats, mirroring the web; map lines are osmdroid `Polyline`s with `setGeodesic(true)`; distance follows the phone's region since the app has no unit setting) and **scanning**: `flights/Bcbp.kt` parses the IATA **BCBP** barcode (Resolution 792: fixed-width mandatory fields per leg, then optional conditional blocks addressed by 2-hex-digit sizes — read only as far as they exist, never throwing; the flight date is a **day of year with no year**, resolved to the match nearest today within −330/+35 days). JVM tests in `app/src/test/.../BcbpTest.kt` build passes field by field to the spec's widths; `mobile-check.yml` runs `testDebugUnitTest`. `flights/PkPass.kt` reads `pass.json`'s barcode text out of an Apple Wallet pass. `flights/PassDecoder.kt` decodes images with **ML Kit's bundled barcode model** (`com.google.mlkit:barcode-scanning`, the model in the APK) rather than the Play-Services variant, so scanning works on de-Googled phones — the reason `LocationSource` exists; only PDF417/Aztec/QR/Data Matrix are enabled. `ScanPassScreen` (route `flights/scan?uri=`) runs CameraX (`LifecycleCameraController` + `MlKitAnalyzer`), with torch, a screenshot picker and a wallet-pass picker; the preview frame becomes the pass photo, and a multi-leg pass asks which flight. `FlightEditScreen` (route `flights/edit`) confirms and corrects everything; after a scan it runs the AeroDataBox lookup automatically when the server has it (`lookup_enabled` on `GET /api/flights/`), picking the leg that matches the pass's route and **never overwriting** what the pass said. The draft crosses the two routes on an Activity-scoped `FlightsViewModel` (no collectors). **Sharing** an image, or sharing/opening a `.pkpass`, into Roamly (`MainActivity` intent-filters → `flights/IncomingShare`, offered on a fresh launch or `onNewIntent` only, so a rotation can't reopen it) opens the scanner on it once signed in. `CAMERA` is requested at runtime and declared `required=false` — without a camera the pickers still work. **Mobile change ⇒ rebuild APK + tag; deploy the server first** (the app needs the 409 + `lookup_enabled` + pass endpoints).

**Mobile Location Data screen (`ui/settings/LocationTableScreen.kt`).** The mobile mirror of the web `/data/` page — a server-backed, sortable, filterable, paginated list of raw GPS points with per-row delete, now a page of the **Data** tab (see Mobile Data tab below; it used to be a Settings button). Reuses `GET /api/locations/` read as the flat `locations` array (new `getLocationsTable` call + `LocationTableRow`/`LocationTableResponse`, leaving the map-sync `LocationsResponse` path untouched), with the same keyset-cursor pagination (`before_value`/`before_id` → `next_before_value`/`next_before_id`) and `sortBy` direction rules as the web table (default desc for timestamp/speed/battery, asc otherwise; the server's echoed `sort_key`/`sort_dir` are trusted over local intent). Card-per-row layout with device/range dropdowns + a sort-selector; delete hits `DELETE /api/locations/<id>/delete/`. **Mobile change ⇒ rebuild APK.**

**Mobile map controls (`MapScreen.kt`).** The top bar is two plates: a **range chip** top-left (icon + `periodLabel`, tap to open the options sheet — the active range is the one thing that must be readable without opening anything) and a grouped **refresh + tune** pair top-right. Everything else is in `MapOptionsSheet`, a `ModalBottomSheet` with two `FilterChip` `FlowRow`s — **Time range** (`6h`/`24h`/`7d`/`30d`/`90d`/`All` + a `Custom…` chip that shows the picked range once set) and **Basemap**. Any selection animates the sheet out (`sheetState.hide()` then act — dropping it from composition outright skips the exit transition) since the map it changes sits behind the scrim. **Refresh** (`MapViewModel.refresh`) forces a full `LocationStore.sync()` — not the throttled `syncIfDue()` — then clears the pan-accumulated detail dots and repaints period + stats, holding its inline spinner until the repaint lands (hence `loadDataNow`, the awaitable body split out of `loadData`). The **point-detail dialog names the recording device**: the locations API nests points under their device rather than repeating it per point, so `LocationPoint.deviceId` is a non-Gson field filled in by `LocationStore.toPoint()` (the Room row already stored it — no migration) and by `MapViewModel.flatten()` on the server-fallback path; `MapUiState.deviceNames` maps it to a display name from `GET /api/devices/` (now typed as `DevicesResponse` rather than a raw `ResponseBody`), falling back to the raw id. Zoom FABs and the bottom stats strip are unchanged; "Have I been here?" is a rounded-rectangle `Surface`, not a pill.

**Mobile "Search" tab (search + Ask).** The middle bottom-nav slot is **always present** and labelled **Search** (`Screen.Search`, route `search`) — search moved off the map, so gating the tab on AI config would have left users without a provider unable to search at all. `ui/search/SearchTabScreen.kt` hosts it: with AI Ask configured it shows a `SingleChoiceSegmentedButtonRow` toggling **Ask** / **Search**; without, the toggle is hidden and the tab is search-only (and a config change to off while sitting on Ask falls back to search). `AskScreen`/`SearchScreen` are the same composables as before, embedded — `AskScreen(showHeader = false)` and `SearchScreen(onClose = null)`, with the status-bar padding moved up to the host. `com.roamly.ui.ask.AskScreen`/`AskViewModel` mirror the web AI Ask feature (`ask_api`). `GET /api/profile/ai-config/` (extended alongside its existing `POST`, mirroring `profile_mapbox_token_api`'s GET/POST split) returns `{ai_ask_enabled, configured}`; `AskViewModel` caches `configured` in `UserPreferences.askEnabled` (paints immediately from cache, refreshes from the server on launch) so the toggle doesn't flicker in/out. Chat itself is `POST /api/ask/` — `AskRepository.sendMessage` sends the full message history + `tz_offset` (JS `getTimezoneOffset()` convention: UTC minus local, minutes) and gets back `{reply}`. `AskScreen` renders the reply's markdown-lite (`**bold**` + `[label](/path)` links) itself; only `/map/?date=YYYY-MM-DD` links are actually clickable, navigating to that date via `MapViewModel.navigateToDate`. **Mobile change ⇒ rebuild APK.**
