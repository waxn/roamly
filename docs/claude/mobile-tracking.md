# Android app: location capture and tracking

_Read when: LocationTrackingService, LocationSource, filters, upload, survivability._

**The capture loop is isolated from the UI, and that isolation is load-bearing.** `LocationTrackingService` declares no `android:process`, so it shares a process — and until 1.25.0 a SQLite file — with the Compose UI. Three separate paths let ordinary UI work degrade GPS capture, and all three are now closed:

- **`synced_locations` (the map's mirror) lived in `TrackingDatabase` alongside `cached_points` (the capture queue)**, so one write lock served both. It now has its own **`MapCacheDatabase`** (`roamly_map_cache.db`, migration `TrackingDatabase` v2 → v3 drops the table rather than copying it — every row is keyed by server id and `LocationStore.sync()` rebuilds it). **`fallbackToDestructiveMigration` moved with it**: on the capture queue it contradicted that file's own KDoc and would have wiped un-uploaded fixes on the first version bump without a migration; on a rebuildable cache it is correct. **Never put a UI-read table back in `TrackingDatabase`.**
- **`savePoint()` did its Room insert, CSV append and upload check inline, and only then advanced `filter.commit()` and `lastAcceptedAtMs`.** A slow database therefore did not merely delay a point: fixes arriving meanwhile were judged against a stale de-dup window and **rejected outright**. Persistence now goes through a single-consumer `Channel` drained off the capture path, and `savePoint` advances filter state *first*, under a `captureLock` that also re-checks `accept()` (closing a real race between the stream's HandlerThread and the fix cycle's IO dispatch). Lock order is always `captureLock` → `LocationFilter`.
- **The per-fix exact alarm is delivered to `onStartCommand` on the main thread**, where it did `runBlocking { prefs.trackingEnabled.first() }` — a blocking DataStore read per captured point. `TrackingEnabledMirror` (SharedPreferences, written from `setTrackingEnabled`) answers it synchronously; DataStore stays the source of truth and is still consulted, asynchronously, before actually stopping, so a stale mirror can never kill tracking. `runFixCycle` is dispatched off-main at all three main-thread-reachable call sites.

**The `streaming` flag was one boolean carrying three meanings, and that was the root of the accuracy loop.** It was *assigned* "should the wake lock be pinned" (`screenOn || recording`) but *read* as "is a stream armed". Since `startLocationUpdates` is unconditional, screen-off the stream keeps running while the flag reads false — so the freshness skip in `runFixCycle` could never fire there, and **every alarm launched a full 10s `acquireBestFix` burst on top of a healthy stream**. That burst landed inside `LocationFilter`'s de-dup window, counted as a cycle miss, and two misses flipped the `auto` priority to `BALANCED` — coarser, and frequently **no Doppler**, which also disables `DriftAnchor`'s speed-based release and freezes the adaptive-interval speed. It is now split into **`streamArmed`** (what `startLocationUpdates` actually got back; drives the skip, behind `SKIP_ON_STREAM_FRESHNESS`) and **`pinWakeLock`** (the old assignment verbatim, so battery is unchanged).

**The stream is deliberately NOT stopped screen-off.** `MIN_ALARM_FLOOR_MS` (15s) floors the alarm path *above* a 10s user interval, so the ~10s median this app has always produced comes from the stream running through screen-off. Deep Doze suspends it and ignores the wake lock anyway, so it is self-limiting. Anything that "fixes" the screen-off stream by stopping it will silently halve the cadence.

**Screen-off the stream is batched, which cuts wake-ups without changing the track — but only while Android Battery Saver is on** (`powerSave`, kept current by an `ACTION_POWER_SAVE_MODE_CHANGED` listener on the screen receiver, which re-runs `applyCapture`); with Battery Saver off the stream delivers per fix even screen-off, since batching made overnight capture look like one point a minute. `streamBatchMs` asks the provider to hold fixes and deliver them together at most every `BATCH_WINDOW_MS` (60s) while `!screenOn`; fixes are still produced and stamped every interval, so the app processor wakes once per window instead of once per fix. Only the **fused** source actually defers delivery (hardware/FLP batching, chip-dependent) — `PlatformLocationSource` delivers as produced, which is harmless. `BATCH_SCREEN_OFF_STREAM` is the rollback lever. Everything that assumed per-fix delivery had to move with it, and each is load-bearing: `LocationFilter.batchAllowanceMs` widens the stale-age limit by the window (otherwise every fix but the newest in a batch is rejected as stale); `runFixCycle`'s `freshWindow` adds the window (otherwise every alarm sees "stale" between batches and bursts on top of a healthy stream — the failure `streamArmed` exists to prevent); stream fixes go through the single-consumer `streamFixes` channel rather than a `scope.launch` each (concurrent launches let a later fix win `captureLock` and get earlier ones rejected as older duplicates); and `FusedLocationSource`'s `FixStream.cancel()` **flushes before removing** a batching request, or switching the screen on drops up to a minute of held track. While the stream is delivering, the backup alarm relaxes to once per window (`LAZY_ALARM_SLACK_MS`) and the catch-up scales with it; the first check that finds the stream stale falls back to the 15s cadence. Worst-case cost: entering deep Doze can lose up to ~2 minutes before the alarm path takes over, at a point where the phone is stationary. The point writer drains whatever is already queued into one `insertAll` + one CSV open + one upload check (`persistPoints`) — it never waits, so there is no buffer to lose. Screen-off notification rebuilds are throttled to 30s. **Verify with `points.csv` `gap_ms` (median/p95 must stay ~10s) and that the `STALE`/`CYCLE_MISS` counters don't rise.** Mobile change ⇒ rebuild APK + tag.

**"Slow down while still"** (`UserPreferences.slowWhenStill`, Settings → GPS, default **off**). Once every real fix for `STILL_AFTER_MS` (5 min) has stayed within `STILL_RADIUS_M` (75m) of where the stillness began, `captureIntervalMs` returns `STILL_INTERVAL_MS` (60s) — used by both `buildRequest` (the stream) and `effectiveIntervalMs` (the alarm); the first real fix outside the radius flips it back. `updateStillness` runs under `captureLock` in `savePoint`; a flip re-runs `applyCapture` *outside* the lock. **Displacement only, never Doppler** — the garbage-Doppler phones this app has met report travel speeds while parked, which would keep it from ever engaging. Distinct from adaptive interval (Doppler-driven 1/5-min cadence that replaces the user's interval outright); `filter.minTimeBetweenMs` deliberately stays the user's interval so the first moving fix is never de-duped. Mobile change ⇒ rebuild APK + tag.

**Miss-counter correctness.** `consecutiveMisses` drives both the retry ladder and the accuracy degrade, so it must mean what it says: only the **chip returning nothing** counts (a fix our own de-dup window rejected says nothing about GPS health); **any real save resets it**, including stream-delivered ones, which previously never did — a phone capturing perfectly could sit pinned in `BALANCED` indefinitely; a **dwell point is neutral**, where it used to count as a success and reset to `HIGH`, which is what made the damage oscillate rather than stick. Retries are floored **outside** `filter.dedupWindowMs()`, since a retry inside it is structurally incapable of producing an accepted fix. `DEGRADE_AFTER_MISSES` (4) plus "no real fix for two cadences" gates the drop to `BALANCED`.

**`acquireBestFix` seeds its plateau timer on the first improvement, not at entry.** Seeded at entry, `ACQUIRE_STALL_MS` (3.5s) was already satisfied when the first fix arrived on any slow cycle, so exactly the coldest cycles kept a single — usually worst — fix.

**Capture is measurable.** `SaveSource` (stream/cycle/dwell/seed) rides through `saveOrDwell`/`savePoint` into a **v2 `points.csv`** carrying `source, fix_accuracy, consecutive_misses, streaming, screen_on, recording, gap_ms, fix_count`. `gap_ms` is comparable to the server-side gap percentiles *and* sliceable by `screen_on`/`source`, which the server never can be — it only sees points that were captured **and** uploaded, with no idea which were dwell substitutions. The file rotates to `points.csv.1` on a header change. New `CaptureStats` counters split what used to be one number: cycle skipped (stream fresh), chip gave nothing, fix arrived but filtered, save lost a race. `DiagnosticsScreen` iterates `Counter.entries`, so a new counter needs no UI change.

**Mobile tracking:** Android app (`mobile/`, Kotlin + Jetpack Compose) uses the Field Journal design system (`ui/theme/Theme.kt` + `ui/theme/Clay.kt` — see **Mobile design system (Field Journal)** above). Login is **session-based** — no API key needed at login. API key is needed **only for tracking**, set up lazily via idempotent `POST /api/keys/app/` (returns existing active key or mints one named "Roamly Android"). One key per account, never expires, never duplicated on re-login.

**Location comes from `tracking/LocationSource.kt`, not from Play Services directly.** Every fix the app had ever recorded came from `FusedLocationProviderClient`, which records **nothing at all** on a de-Googled build (GrapheneOS, CalyxOS, /e/OS, LineageOS without GApps) — and fails *silently*, which is what made it hard to spot: `getFusedLocationProviderClient` returns a client regardless (the classes ship inside our own APK, only the backing service is absent), so the foreground service starts, `startForeground` succeeds, the notification says "tracking", the alarms fire on schedule, and every `requestLocationUpdates` fails into a `runCatching { }` while `lastLocation` resolves to null. Perfect-looking tracking, zero points, no crash and no error anywhere.

`LocationSource` is the narrow interface the service actually used — arm a stream (`requestUpdates` → a cancellable `FixStream`), read the last known fix (`lastKnown`), take one fresh fix (`currentFix`) — with two implementations chosen once per process by `LocationSource.get()`:

- **`FusedLocationSource`** — the original path, behaviourally unchanged, used when `GoogleApiAvailability.isGooglePlayServicesAvailable` returns exactly `SUCCESS`. Missing, disabled, out-of-date and invalid installs all fall through to the platform source: a working coarse tracker beats a fused client answering every request with a failure nobody sees. The check is `runCatching`-wrapped so a build with the Play artifacts stripped degrades rather than crashing the service at startup.
- **`PlatformLocationSource`** — `android.location.LocationManager` through androidx's `LocationManagerCompat`/`LocationRequestCompat`, so one code path covers `minSdk 26` through current.

**The platform has no fusion layer, and this deliberately does not reinvent one.** It arms every usable provider *at once* and lets the existing machinery merge them: `acquireBestFix` already keeps the most accurate fix of a cycle and `LocationFilter` already drops stale/duplicate/teleporting fixes — fused delivers interleaved GPS and network fixes into that same funnel, so multi-provider input is not a new case for them. `providersFor` picks GPS+network for HIGH, network+GPS for BALANCED, passive+network for LOW, filtered to what is present *and* enabled — with a **last-resort clause that is the load-bearing part**: a de-Googled phone frequently has no network provider at all (there is no Google network-location service behind it) and `PASSIVE_PROVIDER` yields nothing unless another app is requesting location, so an empty list would reproduce the exact bug this file exists to fix. GPS is therefore armed even while switched off, and the service's existing `PROVIDERS_CHANGED` receiver re-arms capture the moment the user turns location back on.

`FixRequest` is the source-neutral request; its defaults (`minIntervalMs`/`maxDelayMs` both equal to the interval) reproduce the fused stream's semantics exactly, and `acquireBestFix`'s burst overrides all three to 0 to take every fix the chip can emit. `FixAccuracy` (HIGH/BALANCED/LOW) replaces the raw `Priority` int, so `accuracyForCurrentState`'s auto-degrade-after-two-misses drives both sources identically. **Play Services types now appear in `LocationSource.kt` and nowhere else in the app** — including the map's "have I been here?" (`MapScreen.checkNearHere`), which had the same silent-null failure and now goes through the same source. Diagnostics → Tracking settings shows a **Location source** row (`describe()`, e.g. `Android system · gps, network`), because a phone recording nothing because it has no provider must not look identical to one that simply can't see the sky.

`PlatformLocationSource.currentFix` is built on `requestUpdates` + a timeout rather than `LocationManagerCompat.getCurrentLocation`: that helper carries two overloads differing only in which `CancellationSignal` they take, so a bare `null` argument is an overload-resolution ambiguity. **Mobile change ⇒ rebuild APK + tag.**

`tracking/LocationTrackingService.kt` is a foreground service. **Capture uses two layers** (`applyCapture`):

- **Primary: continuous `requestLocationUpdates` stream + `PARTIAL_WAKE_LOCK`** — delivers smooth per-interval cadence when not in deep Doze (screen on, charging, or moving). Doze suspends the stream and ignores the wake lock, so it only runs when the device is already awake.
- **Backup: exact-alarm cadence** (`runFixCycle` → `scheduleNextFix`) via `setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP)` + `ACTION_TAKE_FIX` (FGS-start exemption). `runFixCycle` skips cheaply while the stream is fresh, takes over in Doze. Alarm cadence clamped to `MIN_ALARM_FLOOR_MS` (15s); next-fix delay measured from cycle start so acquiring time counts toward the interval.
- **`acquireBestFix`** — streams fixes for `min(interval, 10s)` budget, keeps most accurate, stops early on `maxAccuracyM` met or `ACQUIRE_STALL_MS` (3.5s) plateau. Logs best fix rather than gapping.
- **Dwell points (`dwellPointFrom`)** — when no fresh fix arrives (fused provider returns cached location, dedup rejects it), re-logs last known position stamped now (zero speed). Only while last real fix is within `DWELL_MAX_AGE_MS` (10 min).
- **Catch-up backstop** — `scheduleNextFix` arms a second alarm at `CATCHUP_MULTIPLIER` (3) × interval so a dropped alarm recovers within 3×. `runFixCycle` force-resets a `fixInProgress` flag stuck longer than acquisition budget.

**`LocationFilter.accept()` is a pure check; `commit()` is what advances its state**, called from `savePoint` once the row exists. When `accept()` did the advancing itself, a fix later discarded by the accuracy gate in `saveOrDwell` still moved `lastAcceptedTimeMs` to ~now — so the dwell point substituted in its place was rejected by the de-dup window (80% of the interval, 24s at the default 30s), and so was every fast retry, since 4s and 10s both fall inside it. Anywhere accuracy degraded, capture went **completely silent** rather than dwelling. The window now measures from the last point actually *saved*. Both methods are `@Synchronized` — the stream callback thread and the fix-cycle coroutine both reach them.

`savePoint(loc, isDwell)` distinguishes a real fix from a dwell re-stamp: only a real fix advances **`lastRealFixAtMs`**, which is what `DWELL_MAX_AGE_MS` is measured against (checking `lastAcceptedAtMs`, which a dwell save refreshed, meant the ceiling never expired and an outage fabricated an endless parked track). Dwell points also **skip the drift anchor** — their synthetic `speed = 0f` would otherwise let an outage *while moving* plant a false stationary anchor.

**`streaming` tracks the screen** (`streaming = screenOn` in `applyCapture`), not a hardcoded `true`. `screenOn` was maintained and then read nowhere, so: `runFixCycle`'s "recent point ⇒ interval already covered" skip applied in Doze where it must not (halving the cadence — the one thing its comment says must never happen), the untimed wake lock was never released, and the watchdog re-armed a stream the OS had suspended.

Callbacks run on `HandlerThread` ("RoamlyLocCb"). No-fix retries: quick (4s × 3) → medium (10s × 3) → `MIN_ALARM_FLOOR_MS`. Priority "auto" degrades `HIGH_ACCURACY`→`BALANCED` after 2 misses; explicit priorities honoured exactly; HIGH stays first so airplane mode (GPS-only) still works. Falls back to `fusedClient.lastLocation` when budget exhausted. Coarse 15-min heartbeat (`TrackingAlarmReceiver`) remains as the ultimate liveness check.

**Battery exemption is gated, not optional.** Without it, `setExactAndAllowWhileIdle` throttles to ~9 min in Doze. Starting tracking is blocked behind the exemption gate in `SettingsScreen` (with a "Track anyway (gaps)" escape hatch). While not exempt, a coral warning banner and notification line appear. `LocationFilter` is the **single accept() authority** — never movement-gated or accuracy-gated; rejects stale (> 2× interval), duplicate/older timestamp, or teleport (> 357 m/s). **Stationary-drift suppression (`tracking/DriftAnchor.kt`, default ON, toggle in Settings → GPS "Suppress stationary drift" → `UserPreferences.suppressStationaryDrift`).** The teleport guard only catches the *physically impossible*; a parked phone whose GPS wanders off at ~30 mph is plausible and consistent, so it slips through. `DriftAnchor` uses the tell that the chip's **Doppler speed (`Location.speed`) stays ≈ 0 while stationary even as the position estimate drifts**: after a short streak of low-Doppler fixes clustered within `ENTER_RADIUS_M`, it drops an anchor at their centroid and thereafter returns drift fixes **snapped** to the anchor (speed 0), so a parked device logs one stable point per interval instead of a drift spider. It releases the anchor three ways, and each threshold is load-bearing: Doppler showing real movement (**`MOVE_SPEED_MPS` = 0.8 m/s**, `EXIT_MOVE_STREAK`) — deliberately *below* walking pace of 1.2–1.4, since at the original 1.5 a walk away from a parked anchor never cleared the bar and was snapped back until the hard break 300m later; **sustained displacement** (`DEPART_RADIUS_M` 60m × `EXIT_DISPLACE_STREAK` 3), the only escape available to the speed-less fixes `PRIORITY_BALANCED` returns, which is exactly what the auto-degrade after two misses produces; and a **corroborated** large relocation (`HARD_BREAK_M`). The corroboration matters: releasing on the *first* fix past `HARD_BREAK_M` let a lone glitch through unmodified, before any speed check, and it then became the baseline for everything after — that is the isolated far-away, high-speed point that appears beside a stationary cluster. A break now needs a second fix also beyond `HARD_BREAK_M` and within `BREAK_CLUSTER_M` (150m) of the first; a real departure still releases one interval later, a spike is snapped and never recorded off-position. Wired at the single write chokepoint — `resolve()` runs at the top of `savePoint`, so the stream, fix-cycle, and dwell paths all flow through it; `driftAnchor.reset()` on pause. No new permission (reuses `Location.speed`). Points cached in Room, uploaded by `UploadWorker` (offline-first; `replace=true` for user-initiated syncs). **Batch upload:** tries `POST /api/push/batch/` (up to 100 points, `bulk_create(ignore_conflicts=True)`), falls back to single `POST /api/push/`. **Wedged-backlog recovery:** `savePoint` escalates to `replace=true` when backlog is non-empty and no successful delivery for `UPLOAD_STUCK_AGE_MS` (120s). Count backstop `UPLOAD_STUCK_THRESHOLD` (~40) kept as ceiling. `MainActivity.onResume` force-pushes (`replace=true`) any unsynced backlog on foreground.

**Tracking survivability stack:**
1. *Triple-defensive `startForeground`* — `goForeground()` called three times in `onStartCommand` and on boot.
2. *START_STICKY + persisted resume* — null-intent recreation reads `prefs.trackingEnabled` and resumes or stops.
3. *Self-resurrection* — `receiver/RestarterReceiver` (action `com.roamly.RESTART_TRACKING`) restarts service; service broadcasts to it from `onDestroy`/`onTaskRemoved` when torn down while enabled.
4. *Doze-piercing alarms* — two independent `setExactAndAllowWhileIdle` + `ELAPSED_REALTIME_WAKEUP` alarms (fall back to inexact when exact-alarm permission denied): (a) per-point fix alarm (`scheduleNextFix`, `ACTION_TAKE_FIX`), (b) 15-min liveness heartbeat (`TrackingAlarmReceiver`).
5. *Boot + app-update* — `receiver/BootReceiver` handles `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`/`MY_PACKAGE_REPLACED`/QUICKBOOT.
6. *Battery-optimization exemption* — `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` dialog from Settings → Reliability.
7. *OEM-killer onboarding* — Settings → Reliability links to `dontkillmyapp.com/<manufacturer>`.
8. *Multi-provider re-arm* — `PROVIDERS_CHANGED` receiver re-arms capture when providers toggle. `start()/stop()` wrapped in `runCatching` so a blocked FGS-start degrades to heartbeat retry.

**Stopping cleanly.** `trackingEnabled` = tracking should be running (gates START_STICKY resume, heartbeat, restarter, app-launch `resumeTrackingIfNeeded`). `autoStartTracking` = user-facing "Start on boot" option (the only thing `BootReceiver`/`MY_PACKAGE_REPLACED` keys on). `TrackingCoordinator.stopCompletely()` clears both + `trackingActive`, cancels heartbeat and periodic `UploadWorker`, kicks a final flush, stops service. Stop button requires confirmation dialog in both in-app Settings and notification Stop action (`EXTRA_CONFIRM_STOP` via `singleTop` `onNewIntent`). Starting sets `autoStartTracking=true` by default.
