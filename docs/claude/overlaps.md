# Device overlaps and notification bell

_Read when: DeviceOverlap, hide/unhide, bell notifications._

## Device overlaps + notification bell

With the hardware tracker in a pocket and the phone still tracking, one trip is recorded twice, and every per-device aggregate (distance, visit time, point counts) counts it twice. `tracker/overlap_tasks.py` finds those windows and the navbar **notification bell** asks which device to hide (migration `0096`).

**Detection is hourly and incremental by `Location` id** (`UserProfile.overlap_scan_last_id`; NULL = never scanned, so the first sweep covers the whole history once). New points are compared against **every** point the user's other devices have in the same time window, whatever its id — the tracker uploads hours of history at once while charging, so its points are new while the phone's matching ones are old, and an id-only comparison would never pair them. That is also why the cursor is an id, not a timestamp. Daemon thread from `apps.ready()`, per-user advisory lock namespace `0x52414d4f` ('RAMO'), `wait_for_app_registry()` first.

`find_runs` pairs each new fix with the other device's nearest fix within `MATCH_WINDOW_S` (90s): **near** within `max(75m, acc_a + acc_b)` (capped 250m), **far** beyond 3× that — which ends a run, since the devices are demonstrably apart. A fix with no counterpart in time says nothing either way, so a tracker with a sparser cadence than the phone still pairs. A run opens a record at `MIN_RUN_S` (10 min) and `MIN_RUN_MATCHES` (10). Suspect-flagged points are ignored on both sides.

**Apart runs** (`DeviceOverlap.kind='apart'`, migration `0101`, backup v19) are the opposite case: `find_apart_runs` looks for stretches where a phone and a `HardwareTracker` device were both recording but more than `max(APART_MIN_M` (500m)`, 3× radius)` apart, with the same 10 min / 10 match bar. Only one of them was with the user, so the bell (and the app's Tracker tab) asks which — "I had X" hides the *other* device for that window through the same hide path. Only tracker pairs are checked: two phones apart is ordinary (a partner's phone), not a question. `_record_run` merges by kind, so a same and an apart episode never absorb each other. The overlap actions are `@csrf_exempt` + `_require_api_intent` so the app can call them.

**One `DeviceOverlap` per episode, in every status.** A run within `MERGE_GAP_S` (15 min) of an existing record for the same pair extends it rather than creating another: a `pending` one grows; a `dismissed` one absorbs it silently (the user already said "keep both"); a `hidden` one also hides the newly covered points of its hidden device (a late upload into a window already decided). The last two are load-bearing — unhiding re-inserts points under **new ids**, which the next sweep re-scans, and without the merge they would re-prompt.

**Hiding moves the points out of `Location` into `TrashedLocation` with `reason='overlap'`** (+ `overlap` FK) rather than flagging them in place. `Location` is read from ~110 places with no shared queryset helper, so a flag would only be honoured where explicitly taught; moving the rows makes every surface (map, distance, stats, visits, search, AI) drop them with no per-query change. Hiding also deletes the hidden device's `Visit` rows touching the window and resets `processed_for_visits` across their span so the visit job rebuilds the parts outside it; both hide and unhide bust `cache_gen`, kick a stats recompute and the visit job (`_after_change`). Unhide restores via `editor_tasks.restore_trashed` and sets the record `dismissed`.

Overlap rows are **not trash**: the hourly purge only expires `reason='deleted'`, and the Trash tab (`_trash_visible_q`) lists/restores/empties only real deletions — plus overlap rows whose `DeviceOverlap` is gone (the kept device was deleted, cascading it away), which would otherwise be unreachable. They **are** in the backup (v18): `device_overlaps` is a small section keyed by a `ref` (export-time id), and the hidden points stream inside `locations` tagged `hidden: "overlap"` + `overlap_ref`, so restore puts them straight back into the hidden table and they count toward the `locations` total. `DeviceOverlap` and the scan cursor are otherwise operational.

**The bell** (`base.html`, `.notif`, next to the username, click-to-open, also on mobile as a fixed sheet below the navbar). Notifications are **not stored**: `GET /api/notifications/` derives items from state that needs a decision (pending `DeviceOverlap`s, plus the 20 most recently hidden ones with **Unhide**, plus detected flights in their own `flight_suggestions` key — see Flights), so an item disappears by itself once resolved. `?summary=1` is a single `COUNT` for the badge dot, polled on page load and when the tab returns to the foreground. Actions: `POST /api/notifications/overlap/<id>/{hide,dismiss,unhide}/` (hide takes `{device_id}`; web-only, so `X-CSRFToken`, not `@csrf_exempt`). **Clear all** (`POST /api/notifications/clear/`, `notifications_clear_api`, web-only) answers **Keep both** for every pending item at once — the non-destructive choice, so clearing never hides a point; the hidden list is undo history and is left alone. A new notification kind is a new item builder in `notifications_api` plus a renderer in the bell script. **New model ⇒ build + migrate.**
