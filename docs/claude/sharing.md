# Adventure membership and location share links

_Read when: Adventure consent model, LocationShare links._

**Adventure membership is consent-based** (migration `0082`). `AdventureMember` gained **`accepted_at`** (NULL = invited, not yet accepted) and **`share_track`** (accepting is not by itself consent to share a GPS track). This closes a total cross-tenant disclosure: `trip_add_member` inserted a membership from a bare username with no consent step, and the adventure payload then returned that member's own device track for the adventure's window — so creating an adventure with `start_time` 1970 (and no `end_time`, which defaults to **2099**), adding any username, and GETting it returned that account's **entire location history**, publishable via `toggle-public`.

`member.track_window(start, end)` clamps the window to the period since acceptance, and **`_member_track` is the single path both the authenticated and public payloads use**, so they cannot drift on what was consented to. Pending invitees are not listed as participants on the public page. `trip_join_view` is where acceptance happens and now requires a **POST** from a page that explains what sharing a track means — it was a state-changing GET, so a prefetch or a lured click enrolled you. `restore_backup` is attacker-authored input, so it may carry consent **only for the restoring account's own membership**; every other member restores as pending. Backup `meta.version` **12 → 13** (the shared `_build_adventures_data` carries the new fields, so both builders stay identical). Migration `0082` grandfathers existing memberships as accepted — they predate the model and blanking a live adventure would read as data loss.


**Location share links** (migrations `0084`, `0097`, `LocationShare`). A link that shows the sharer's live position, and optionally history, to anyone holding it — the token **is** the credential, same trust model as `Adventure.invite_token` and `email_unsub_token`. Managed from Settings → **Sharing** (its own tab; `buildSettingsPages` `sharing` entry).

**Temporary and permanent are one row, not two code paths:** a permanent share is one with `expires_at` NULL, which is only safe because `revoked_at` exists. Revoking sets the timestamp rather than deleting.

**Protection is per link** (migration `0097`): `require_login` (any Roamly account) and/or `pin_hash` (4 digits, `make_password`). `_share_gate()` returns `ok`/`login`/`pin`: the owner always passes; login-only needs an authenticated viewer; **login+PIN asks the PIN once per account and remembers it as a `LocationShareGrant`**; PIN-only is remembered in the viewer's session (`share_ok`, a list of `"<share id>:<last 12 chars of pin_hash>"` markers, so **changing the PIN invalidates every remembered unlock**; editing the PIN also deletes the grants). `POST /api/share/<token>/unlock/` (`share_unlock_api`, `@csrf_exempt` + `_require_json`, public) is throttled three ways — `_rate_limited` per IP and per link, 5 wrong PINs/15 min per IP+link and 30/hour per link (a per-link global cap, so IP rotation cannot brute-force 10k PINs), a hidden honeypot field, and Turnstile via `_verify_turnstile(request, allow_app=False, token=…)` when the admin enabled it (the function gained an optional `token` so JSON bodies work). Both the page and the data API enforce the gate, so skipping the page gets nothing.

**History windows are the sharer's choice**: `allowed_windows` (subset of `_SHARE_WINDOW_CHOICES` 1/6/24/72/168/720 h), `default_window_hours`, and `view_style` (`lines`/`dots`/`both`). Window `0` (live position only) is always allowed; any other value not ticked → 400. `window_hours` is kept as the max for older code. Existing shares were backfilled to `[window_hours]` and stay open.

**Data**: `GET /api/share/<token>/data/?window=H` (`share_data_api`; the old `/track/` URL aliases it) returns `current` (newest fix across the shared device(s), per-device index seek, with accuracy), `points` (newest-first up to budget, stride-thinned to ≤2000), `windows`, `style`. Cached 15 s per share+window so many viewers cost one query; `no-store` toward the browser. Payload stays minimal: coordinates and timestamps only. The sharer's username is shown in the page header (rendered into the template, not returned by the data API).

**Viewer page** (`share.html`, standalone, mobile-first): large pulsing blue dot (animated between fixes), a History button opening a bottom sheet (floating panel ≥720px) with the allowed windows and a Dark/Streets/Satellite basemap picker (remembered in `roamly_share_base`), recentre button, status pill (live / stale after 15 min / offline). Polls every 45 s while visible and never re-fits on a poll (the old page reset the viewer's pan/zoom every minute); layers are re-added on `style.load`/`styledata` after a basemap swap. Gate screens: sign-in prompt, 4-box PIN entry (auto-submit, paste, shake on error).

**Access log**: `LocationShareView` rows (username if signed in, time — **no IP**), written once the viewer is through the gate (page load or successful unlock), deduped to one row per viewer per share per 10 min via cache so a tab left open does not flood it; the owner previewing their own link is not logged. `view_count`/`last_viewed_at` still bump alongside. Shown per link in Settings (`GET /api/shares/<id>/views/`). Edit with `POST /api/shares/<id>/update/` (device is fixed after creation).

The page carries `noindex, nofollow, noarchive` and `referrer: no-referrer`, and `/share/` is `Disallow`ed in `robots.txt`. All three tables are operational ⇒ **excluded from backups**. **New models/fields ⇒ build + migrate.**
