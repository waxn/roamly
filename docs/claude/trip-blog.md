# Trip blog

_Read when: Trip blog models, share links, posts, video, digest, Android._

**Trip blog** (migration `0109`; `tracker/trip_blog.py` logic, `tracker/trip_blog_views.py` views, `trip-blog.js`/`trip-blog.css` + `_trip_app.html` UI). A shared travel blog for a family on a long trip, followed by grandparents and friends — the replacement for "a Google Site with today's city and a daily video". **Deliberately not an Adventure**: an Adventure's public page draws every member's GPS track; a trip blog shows **posts**, and GPS only ever feeds the header and a fuzzed spot per traveller. **A viewer never receives a coordinate from the history** (`test_status_never_contains_raw_fix`).

- **Members** (`TripBlogMember`, the `FamilyMembership` consent shape: `accepted_at` NULL = invited, `share_location` a separate opt-in, invite-by-link only via a POST-gated `/trip/join/<token>/`) all post. **Only the owner may change the dates** (a member's request saves the rest and echoes `ignored`), and the header's country list reads each member's history only from `max(start_date, accepted_at)`, since the dates decide how far back every traveller's history is read. One `featured=True` per user drives the nav: **"Trip"** on the web (`FEATURED_TRIP` from the context processor, `trip_blog_views.featured_for`, cached `tripfeatured:{user}`) and a **"Blog"** tab on Android (not "Trip": the Adventures tab is labelled "Trips"). Created from the **Trip blogs** card at the top of `/adventures/`.
- **Viewers** come in through `TripShareLink` (`/t/<token>/`), which copies LocationShare's trust model and PIN unlock (`_rate_limited` + honeypot + per-IP/per-link lockouts + Turnstile + `check_password`) and adds **`max_uses`**: each new *browser* (`rly_tv` cookie, stored hashed as `TripShareUse.viewer_key`) spends one use and keeps access; a conditional `UPDATE … use_count < max_uses` is the race guard. `trip_blog.link_gate` → `ok`/`enter`/`pin`/`full`. **The page GET never spends a use**: it renders a shell and its JS POSTs `/enter/`, because chat apps fetch link previews and would otherwise burn a one-time link. The data APIs require `ok`, so calling them directly cannot bypass the limit. Members always pass. Removing a `TripShareUse` (Who viewed → Remove) revokes one browser.
- **Header** (`status_payload`, cached 60 s on `tripblog_gen:{blog}`): **"Staying in"** = the ~220 m cell with the most fixes 00–05 local over the latest of the last three nights (`home_city`, same cell size as Achievements' home), then each sharing member's latest-fix city grouped into "Everyone in Kyoto" / "Linus, Mom in Kyoto · Dad in Osaka" (`_group_line`), stats (day N, countries, places, posts). After `end_date` the blog is an archive: no spots, no "now".
- **Spot fuzz** (`fuzz_spot`): the dot is the fix snapped to a ~250 m grid, moved by an HMAC(SECRET_KEY, blog, user, grid cell, tier) bearing/distance. It is **fixed per cell and tier**, so neither polling nor returning to the same place after a day trip yields fresh samples to average away and the radius widens while still (500 → 750 → 1000 m at 0/2/6 h); a fix >1.5 km away starts a new stay. The true position is always inside the drawn circle. Post pins are exact — posting a location is deliberate.
- **Posts** (`TripPost`, `TripPostMedia`, idempotent on `(author, client_id)`): drafts first, so media uploads before the author decides where it was. **Photo EXIF is read from the raw upload before re-encoding** (`process_photo`: GPS + DateTimeOriginal, then `exif_transpose`, 2048 px JPEG — the stored file carries no GPS); the composer offers it as a chip, alongside ⌖ (`my-location`, the poster's latest fix) and a map pick. The map pick opens at city zoom on the current spot, else the poster's latest fix, else a traveller, else the newest post (web `pickOnMap`, app `pickerArea`). A naive EXIF time is read in the zone of the post's location. `local_date` is stored for day grouping; the feed is 5 days a page, grouped "Day 23 · Tue, Mar 4 · Kyoto", and each post carries `local_time` (the wall clock where it happened) so a viewer in another zone reads Kyoto's time.
- **Video**: chunked upload (`/posts/<id>/video/`, 8 MB chunks, idempotent by index — `duplicate` / 409 `next_chunk`, the activity-track protocol) because a Cloudflare tunnel refuses bodies over 100 MB; `tracker/video_tasks.py` then transcodes to **1080p H.264/AAC MP4 + poster** with ffmpeg (single-flight `tripvideo:lock`, `nice`, 2 threads; **ffmpeg is in the Dockerfile**), replacing the original on success and keeping it on failure. H.264 rather than AV1 because pre-2023 iPhones/iPads cannot play AV1. A 10-minute sweep (`start_trip_video_scheduler`) recovers stuck rows and deletes abandoned drafts (7 d) and half-uploads (2 d).
- **Comments + reactions**: viewers comment with a remembered name (honeypot + 20/15 min per IP), members as themselves; members delete any comment, a viewer their own (`viewer_key`). Reactions are a fixed set (`TripReaction.EMOJI`) toggled per viewer key.
- **Daily digest** (`tracker/trip_digest_tasks.py`, hourly, advisory lock **`0x52414d54` 'RAMT'** per blog): double opt-in `TripSubscriber` (confirm and unsubscribe are GET-shows-a-button, POST-acts, since mail scanners follow links), one email after 19:00 trip-local when there are posts with `published_at` past the subscriber's cursor; nothing for a revoked/expired link. SMTP-gated.
- **Endpoints**: members `/api/tripblog/<id>/…` (posts, photo, video, media delete, links, views, invite, members, cover, my-location), viewers `/api/tripblog/v/<token>/…` (enter, unlock, name, subscribe); status/feed/comments/comment/react exist under **both** and go through `_audience`, so they are written once. App writes are `@csrf_exempt` + `_require_api_intent`; public writes `_require_json`. `/t/` and `/trip/` are `Disallow`ed in `robots.txt`.
- **Backup** `meta.version` **25** (`_build_trip_blogs_data`: blogs the user created, with members, posts, media paths, comments; media in the zip). Share links, uses, subscribers (third parties' addresses) and reactions are excluded; restore applies the Family Circle consent rule and `_restored_media` to every path, and re-queues an unfinished transcode.
- **Android** (`ui/tripblog/`, `tripblog/`): the Blog tab (Activity-scoped `TripBlogViewModel`, one-shot loads only) with Feed | Map, and `TripComposeScreen`. **Posting goes through an outbox**: `TripPostOutbox` copies the picked media into `filesDir/tripblog_outbox/<clientId>/` at once (a photo-picker read grant dies with the process) and `TripPostWorker` drains it — draft, each photo, each video in chunks, publish — recording progress in `post.json` so any retry resumes. EXIF GPS needs `ACCESS_MEDIA_LOCATION` + `MediaStore.setRequireOriginal` (asked when picking; declining only loses the chip). Videos play in an external player.

**New models + migration ⇒ build + migrate (ffmpeg arrives with the rebuild); mobile change ⇒ rebuild APK + tag; deploy the server first.**
